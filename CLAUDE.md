# Git workflow

This folder is a git repo connected to https://github.com/KerlitTheDog/zenofit (branch `main`).

**Never push automatically. Always ask first.**

After editing files, stage and commit them if useful, but stop and ask the user before running `git push`. Summarize what's about to go up (which files, what changed) so they can decide. Wait for a clear yes.

This applies even to small or routine changes, and the user wants a say in what reaches GitHub every time.

Also always ask first for anything destructive to git history (force-push, `rebase`, `reset --hard`), and never force-push over a rejected push.

Note: this local folder is the source of truth. Editing files directly on the GitHub website risks those edits being overwritten by the next push from here.

# Project overview

Powerbuild Tracker (product name "Zenofit") is a mobile-first powerbuilding/progressive-overload tracker: workouts, planned sessions, weekly volume, PRs, and body measurements. It's a **faithful port of a spreadsheet** ("AbsoluteMain.xlsx"): the header comment in `app.js` maps each spreadsheet formula to its JS equivalent (week number, muscle-group lookup, est. 1RM, cardio score, "vs. Your Best" badges, dashboard rows, weekly volume, deload radar, body trend). When changing any of that logic, check the comment block at the top of `app.js` for the spreadsheet formula it's meant to reproduce.

The one deliberate departure from the spreadsheet is the **1RM estimate**. The sheet used Epley, which reads a single at 30 kg as a 31 kg max; the app now uses Wathan's equation divided by its own one-rep value, so one rep is exactly the weight lifted (`rmCurve`/`est1RM`, with the reasoning and the formula bake-off written up in the comment above them). Everything downstream (best set, PRs, goals, the progress graph, the calculator tab, the set suggestions) reads that one curve, so it is the only place to change it.

**The formula is a code detail, not a caption.** The bake-off, the comparison with Epley and the name "Wathan" belong in that comment and in exactly one place in the UI: the *Estimated 1RM* accordion in Home → How this works (`acc.rm.body`). Nowhere else in the interface says anything about it: not the calculator's result line or footer, not the entry form, not the set editor. There is no longer even an "exact at 1 rep" caption beside the number, because nobody logging a set of eight needs to be told what the curve does at one rep. Don't add a caption when adding a surface that shows an est. 1RM; the label and the number are the whole thing.

It's a installable PWA (see `manifest.webmanifest`): standalone display, portrait-locked, with home-screen install providing real orientation lock on Android and enabling timer notifications on iOS.

# Home → How this works

The accordion stack at the bottom of Home (`acc.*` in `i18n.js`, wired in `renderHome`) is a **reference, not a tour**. The test for whether something belongs there is: *does the app fail to answer this by being tapped?*

- **In:** rules that decide what happens to someone's data or what a number means: what counts toward PRs and volume and what is silently dropped, that a preset saves exercises and never numbers, that units live per-exercise and history is never rewritten, that a parked day counts for nothing until saved, that a plan counts for nothing until the day is actually logged and what a preset is instead, that there is no volume bar without a target, why the est. 1RM can hold still on a session that went well and where that improvement is shown instead, where the data physically lives and what can destroy it.
- **Out:** narration of the interface. Nobody needs to be told that ＋ adds an exercise, and the same sentence volunteered *mid-set* is noise. That is the standing complaint behind both this section and the removal of the 1RM caption.

Titles are questions a user would actually ask, so the collapsed list works as an index; a collapsed accordion costs one row, so being specific is cheaper than being comprehensive in fewer sections. Keep bodies tight, and when a feature changes, fix the copy here in the same commit, since this section going stale is how the app starts lying about itself.

# Running / testing

There is no build step, package manager, or test suite: this is plain HTML/CSS/JS loaded directly by the browser. To work on it, just open `index.html` (or serve the folder with any static file server) and reload after edits. There's no linter or formatter configured; match the existing style in the file you're editing.

# Architecture

Everything lives in five files: `index.html` (shell + theme-flash-prevention inline script), `styles.css` (all styling, theme-driven via CSS custom properties), `i18n.js` (every string, in three languages), `standards.js` (pure data: the StrengthLevel strength-standards tables), and `app.js` (the entire application).

**Every dimension that answers to the device goes through the viewport engine, and nothing else measures the screen.** `applyViewport()` in `app.js` (the VIEWPORT ENGINE block above `render()`) is the only code that reads the device: it writes `--pb-scale` and `--pb-frame-w` onto `<html>`, and the matching block in `styles.css` derives everything else from them: the frame's height, the safe-area insets in the frame's own units (`--pb-sat` / `--pb-sab`), and the chrome measurements stacked on the bottom nav (`--pb-nav-h`, `--pb-header-pt`, `--pb-content-pb`, `--pb-fab-b`, `--pb-toast-b`). Three rules keep it honest:

- **Never write a raw pixel offset against the top or bottom of the screen again.** A top bar's first padding is `var(--pb-header-pt)`, not `14px`; anything sitting above the nav is `calc(<clearance> + var(--pb-sab))` or one of the `--pb-*-b` tokens. Those numbers are what the notch and the home indicator are subtracted from, and a hand-written `14px` is a control the user cannot reach on a notched iPhone, which is exactly the bug the engine was written for.
- **A phone renders at scale 1, by design.** The frame takes the full width it is given up to `--pb-fluid-max` (480pt) and only scales past that, so every handset draws the design at the size it was authored at; scaling exists for tablets and desktops, which are the only screens wider than that. If you change `VP_FLUID_MAX`, `VP_REF_H` or `VP_SCALE_MAX`, you are changing what happens on a tablet, and you should check a phone anyway.
- **Pointer coordinates arrive in screen pixels; the frame is laid out in its own.** Anything doing arithmetic between an event's `clientX`/`clientY` and a laid-out size (`offsetHeight`, `clientWidth`, an SVG coordinate) has to divide the event side by `vpScale` first, see `moveRowDrag` and the chart gesture handlers. On a phone this divides by 1 and on a tablet it is the difference between a drag that tracks your finger and one that does not.

# Languages

English, Українська and Svenska. `i18n.js` holds `UI[lang]` (all interface copy, keyed by dotted name), `EX[lang]` (the 41 built-in exercises as `[name, equipment, alternatives, note]`, in the same order as `DEFAULT_LIBRARY`) and `STD_EX[lang]` (the 71 strength-standards lifts, keyed by **slug** rather than by position, because that list is data the app doesn't own and a row in it could move). English lives in `UI.en`, in `DEFAULT_LIBRARY` and in `STD_EXERCISES` itself. `T("key", vars)` looks a string up and falls back to English then to the key, so a partial translation is always safe; `TN("day", n)` picks plural forms (one/other for en+sv, one/few/many for uk). Long copy carries its own `*bold*` and `_italic_`.

Adding or removing a language means editing `LANGS`, `LOCALES` and the matching `UI`/`EX`/`STD_EX` blocks. `resolveLang()` coerces anything not in `LANGS` to English, so a saved setting for a language that has since been dropped degrades quietly, and `migrate()` rewrites it on load.

**The rule that keeps data safe: translations are display only.** Everything persisted stays in English, because those strings are identity: a log entry points at `"Bench Press (Barbell)"`, a goal is filed under it, an exercise sits in the group `"Chest"`. Switching language must never orphan a logged workout. So:

- `exLabelOf(ex)` / `exLabel(name)` / `exFieldOf(ex, field)` translate built-in exercises via their stable `default-N` id; a custom exercise, or a built-in field the user has edited, is shown exactly as typed. **That includes the name**: `exLabelOf` translates a built-in only while `ex.name` is still the shipped one, so a lift the user renamed reads back as theirs in every language. And because the edit form is prefilled with the LABEL, `actions["exwin-save"]` treats a name typed back exactly as it was shown as untouched, or a built-in opened in Svenska and saved for its colour would freeze into Svenska.
- **Renaming an exercise is a cascade, not a field edit.** The name IS the identity, so `actions["exwin-save"]` carries it through `log`, `plans`, `dayDrafts`, `presets` and `goals`, plus the open workout sheet, the open entry form and `ui.progressSelected`, exactly as `actions["group-save"]` does for a group. Writing it into the library alone left every one of those pointing at a lift that no longer existed: the session still rendered in the day, and opening it found nothing to edit. **Anything added later that stores an exercise name has to be added to that sweep.** A name already in the library is refused rather than merged, since two rows under one name is the same desync arrived at from the other end.
- `groupLabel(name)` translates a group while it still carries a `key` **and still wears the name we shipped it under** (`DEFAULT_GROUP_NAME`); rename it and it reads back as typed, in every language, exactly as a renamed built-in exercise does. **The key is identity and rides through a rename**, which is the whole point: it used to be dropped to stop "Pecs" coming back as "Chest", and that threw the group's identity away along with the claim about its name. Same trick for seeded timers (`timerLabel`, `key: "rest"`).
- **A group declares WHAT IT IS FOR, and the name is just a name** (`KIND` at the top of `app.js`, `groupKind` / `exKind` / `kindOf`). The Cardio group used to be identified by being called "Cardio", so calling it "Hell" broke the form. Four kinds now: **strength** (sets of reps × weight), **bodyweight** (sets of reps), **hold** (sets of seconds), **cardio** (minutes × effort). A kind earns a place in that table only by passing both halves of one test: **it changes what you write down, AND it has one axis on which more is unambiguously better.** The second half is the strict one — the PR badge, the graph, beat-last-time, the set verdicts and the suggestion card all need a direction to point in. Two shapes people ask for fail it and are deliberately absent: **rounds**, where "5 rounds for time" wants less time and "AMRAP 20" wants more rounds, and **distance**, where a longer run and a faster run are both better. Neither is hard to store; both would make the app decide what you meant. Don't add them without solving that first.
- **Everything that differs between the set-shaped kinds is three questions**, and every call site asks one of them rather than testing the kind: `setHasData` (is it filled in), `setScore` (what is it worth), `setLine` (how is it written). `sets: false` is the real fault line — cardio is the only kind not logged set by set, which is why so much of the app reads `kind === "cardio"` and stays correct, and why bodyweight and hold got the set list, dropset chains, ghost rows, last-time verdicts, PR badges, the graph and sets-per-week for free. `metricOf` is the converted, cross-session number and `setScore` the raw one you read back; `metricUnit` / `metricLabel` name it, since "est. 1RM" is a claim only the strength curve gets to make.
- **The kind lives at three levels, and only two of them store anything.** A group ALWAYS carries one. An exercise carries one only while it is an EXCEPTION to its group (`withKind` writes it, `exKind` reads it): **absent means "whatever my group is for"**, which is what makes filing a lift under a cardio group make it cardio and what carries a group's exercises along when the group is re-declared. v13 stamped a kind onto every row instead, which made the group setting inert — every exercise already had its own answer and never asked — and v14 undoes that, keeping a stamp only where it disagrees. Tapping the group's own option in the exercise editor CLEARS the exception rather than setting one. An entry, by contrast, has its kind frozen on it when logged: **re-declaring anything never reaches back into the log.** That is also why the seeded pull-ups and plank are still strength — flipping them would change the form under everyone who already has reps × weight on record for them.
- **A lift is READ in the kind it is logged in today, and only sessions in that kind are compared** (`readKind`, and the kind filter in `earlierOutings`). Change what an exercise is logged in and its old sessions do not change with it, which leaves two sets of numbers under one name; a rep count is not a kilo. So the graph, the best-ever, the PR flags (`computeBadges` keys on lift AND kind), the Progress row, the suggestion card, "last time" and the set verdicts all read one kind only. **The older sessions are still listed** in the exercise window, labelled with how they were logged and carrying no number or badge, with a line saying how many are off the graph: they happened, and a ledger that hides them is worse than one that labels them. Presets follow the same rule — `presetToEntries` takes the kind from the LIBRARY, never from the copy stored on the preset — and a plan hands over its target only while it still fits the lift's current shape (`planTargetUsable`).
- **Volume counts cardio in minutes and everything else in sets, and never adds the two together.** `volumeForWeek` / `volumeInRange` return `{sets, minutes}` per group. A group is free to hold both (declare it cardio and make one lift an exception, or the reverse), and summing them produced "32 sets" out of two sets and half an hour on a bike. The group's own kind picks which figure is THE number — the one a target grades and the one compared with last period — and the other is shown beside it when there is any of it. They also land under the entry's OWN group: filing every cardio entry under the literal key `"Cardio"` put a session done in "Hell" somewhere else entirely.
- **Search reads the label as well as the stored name** (`exMatches` / `exIsNamed`). Filtering on `ex.name` alone meant the library search and the exercise picker found nothing at all in Ukrainian or Svenska, and the picker, seeing no exact match either, then offered to add a lift you already had under its translated name as a second row keyed by a name nothing points at. Any new search over exercises has to try both.
- **`data-*` attributes are lookup keys and must carry the stored English name**, never a label. Translating one silently breaks the click handler that resolves it.
- Dates go through `fmtDate`/`fmtShort`, which use `localeTag()` so they follow the app's language rather than the device's.

**`app.js` is a hand-rolled single-file SPA framework**, with no React/Vue/build tooling. Key pieces, in the order they appear in the file:

- **`DEFAULT_LIBRARY`**: the seeded exercise library (name, muscle, kind, equipment, alternative, cue notes), ported verbatim from the spreadsheet's Exercise Library sheet.
- **Pure calculation helpers** (`bestSet`, `syncEntry`, `computeBadges`, `dashboardRows`, `weeklyTotals`, `volumeForWeek`, `deloadRadar`, `bodyTrend`, etc.): these are the spreadsheet-formula ports; keep them side-effect-free.
- **`state`** (persisted) vs **`ui`** (transient, in-memory only): two separate global objects. `state` holds workout log, library, muscle `groups`, presets, timers, goals, body measurements, `dayDrafts`, settings; it's loaded via `loadState()`/`migrate()` and written to `localStorage` under key `powerbuild-tracker:v1` via `persist()`/`writeNow()` (debounced autosave, flushed on visibility change / pagehide / beforeunload). `ui` holds open sheets, form drafts, filters, etc., and is never persisted directly, but in-progress drafts (open workout sheet, entry form, set form, body form) are snapshotted into `state.drafts` so a killed/reloaded tab restores exactly where the user left off (see `snapshotDrafts()` and the `restoreDrafts` IIFE at the bottom of the file).
- **Three stores hold a day that is not (all) history, and they are not the same thing.** `state.drafts` is the crash/lock snapshot of whatever form is open right now. `state.unlogged` is what a SAVED day left unfilled (see the bullet below). `state.dayDrafts` is deliberate: backing out of a half-built workout parks the whole day there (`closeWorksheet()`/`stashDayDraft()`), it renders above the history in the Log tab, and nothing in it counts toward sets, PRs, volume or the charts until the day is actually committed. **There is only ever one workout for today**, which is what `actions["log-exercise"]` (the Log exercise button in the exercise detail window) has to respect: it opens the sheet you already have open, else today's parked draft `draftId` and all, else a fresh day (it never starts a second one) and then drops straight into that exercise's entry form. It is a shortcut past New Workout → Add exercise → find it in the picker, not a second way to write to the log.
- **Set suggestions are built on last time, not your best ever** (`setSuggestion`, and the `SUG_*` constants above it). The card at the top of the entry window, above *Add set*, deliberately, because that window is where you decide what to do while the set editor is where you write down what you already decided, offers two ways past the previous session's best set: one more rep at the same weight, or the smallest real weight step (`weightStep`) at the same reps. Holding the reps on the heavier option is deliberate: dropping reps as weight goes up is normal training but would not raise the estimate, and the card only ever offers something that scores higher (every option is filtered through `metricFor`). **Neither option is recommended over the other**: they render identically, and `bySmallestStep` only ranks them by the one thing the app can compute exactly: which raises the estimate least, tagged `sug.smaller` (and tagged on neither when they tie). That lands on the extra rep in the 8-12 range and on the extra weight down on heavy triples, where one more rep is worth far more than a plate. This replaced an inferred double progression that was broken twice over: mechanically (the rep ceiling was a median of a window including last session, so "you're under your range" required your reps to have just *dropped*, which following the app could never cause, making the answer "add weight" forever) and in principle (**a rep range is an intention, and the log only records what you did**, and crowning an option on a guess about someone's programming is the same mistake as a progress bar filling toward a goal they never set). If you reintroduce double progression, it has to run off a range the user actually set, not one read out of their history. The set editor shows the same two buttons, minus whichever the open set already *is*. **Under that card sits `renderLastTime`, the session it is arguing from, set by set** (`lastOuting`). The card names one set because that is the bar it offers two ways over, but four sets that fell apart and four that held share a best set and were not the same day’s work, and it is the second and third you are stood there trying to match. Read-only (everything else tappable in that window puts a number in the log) and in the unit each set was *logged* in, never converted; it renders under a plan target too, since a plan does not make last time less worth knowing. **Both are tap-to-load, never auto-filled**: the log records what you did, never what the app hoped you would do.
- **A new set opens on last time's set in the same position** (`openingSetFor`, read off the same `lastOuting` rows the panel above draws). Set three opens on last week's set three, converted into the unit this entry is being logged in. It used to open on the set above it, which is right exactly once (the first set, where there is nothing above) and wrong from the second onward: somebody working up 60/80/90 was handed 60/60/60 and retyped two thirds of their own session. Past where last time ran out it falls back to the set above, which is that old behaviour and the only honest guess left, and with no history at all it opens blank. This is a starting point in an editor, not a number in the log (nothing is written until the set is saved) so it does not violate the tap-to-load rule above, which is about the app never *committing* a number a finger did not put there. The suggestion card still overrides it, because taking the card is a decision and the default is only a guess.
- **Unticking a set is an edit, not a refusal, and a not-done row stays in the log.** `entryOnRecord` says whether the entry in the window is already a record: a card in the open day sheet (`isDraft`) *or* a row in `state.log`, which is what the Log tab opens when you tap a history row. Anything on record may be emptied and saved again (the button relabels to `entry.saveNotDone`) because unticking is someone taking back a claim about their own training and the app has no business refusing to write that down. Nothing is turned away any more: a brand-new entry with nothing in it is a lift *lined up* for later (see the bullet below). Both routes into that window must stay covered; for a long time only the sheet one was, and the Log-tab route silently greyed out at exactly the moment it was needed. The row that comes back is blank but **keeps its `plan`**, so the lift reads as planned-and-not-done, the day chip drops to 0/n, and the ghost rows are still there to tick again later. That means **`state.log` can contain entries with no numbers on them**, which is a real invariant to hold: `earlierOutings` filters them out (a not-done row is not a session you had, and leaving it in let it become the "last day you trained this" and come back empty, hiding the real one behind it), and anything rendering a row has to guard `entrySummary` with `entryHasData`. Note `commitWorkout` still drops blanks when a whole *day* is saved, and there the same lift reverts to the plan via `prunePlans` instead, which reads the same way to the user and is why both are "planned, not done".
- **A lift can be lined up with nothing in it** (`lineUp` in `entryComputed`). The entry form used to refuse a brand-new entry carrying no numbers, on the grounds that a blank row is a row nobody asked for. That was wrong about who was asking: halfway through the hamstring curls you decide the calf raises are next and you want them on the day NOW, with the numbers to follow. Being made to type 1 rep at 1 kg to get past the button and correct it afterwards turns a note into a false record. **This is not a plan**: a plan is a dated intention that can sit in the calendar for weeks and is counted by nothing, while a lined-up lift is a card in the day you are training right now and becomes an ordinary logged lift the moment you fill it in. `commitWorkout` still drops whatever is blank when the DAY is saved, so a lift you lined up and never did leaves no empty row in your history, and the sheet's footer already says so before you save.
- **Supersets and dropsets are the same idea at two levels** (`isDrop`/`isSuper`, `linkMarks`, `dropMarks`, `superMarks`). A dropset is one exercise straight into a lighter set of itself; a superset is one exercise straight into a different one. Both are a single boolean on the item that CONTINUES the one above it: `set.drop` and `entry.superWith`. **Nothing stores a group id**, deliberately: an id is a second source of truth about an order the list already knows, and both lists are draggable, so the two would start disagreeing the first time somebody rearranged one. Runs are read upward from the order instead, a mark on the first item means nothing and is ignored, and deleting or reordering silently reshapes the runs into whatever the new order says. `commitWorkout` clears a link left stranded on what became the day's first entry, which is tidying the record rather than fixing a read. **Neither does any arithmetic**: no volume multiplier, no intensity adjustment, no fatigue discount. A drop is a set and counts as one set; a supersetted lift is a lift. est. 1RM, PRs, weekly volume, the graph and the last-time comparison all read exactly what they read before, because the app does not know what a dropset is worth and neither does anybody else. They say what you DID, which is the only claim the log is allowed to make. Drawn as an indented chain off the row above, with the label on the head of a run only, in the set list, the day sheet and the history rows alike.
- **A profile is a whole `state`, and there are several of them** (`loadProfiles` / `switchProfile`, Settings → Profiles). Trying a different block without giving up the one you are in, or logging for somebody whose phone is at home, needs a second everything: log, library, groups, presets, timers, goals, body, plans, settings. So a profile IS a state, the same object the backup file carries, and switching swaps it whole. **Storage is one small index plus one key per profile** (`powerbuild-tracker:profiles`, `powerbuild-tracker:state:<id>`) rather than all of them under one key, because every save rewrites its key and localStorage is a few megabytes with exercise photos already in it: writing four profiles because one gained a set would be four times the quota risk on every debounce. The single-key save everyone was on becomes profile one and is **only let go of once the new key reads back**. Export and Import act on the profile you are in, unchanged, since `state` is still `state`.
  - **THE LIST ITSELF IS ACCOUNT DATA, NOT DEVICE DATA** (the ROSTER block in `app.js`: `rosterSync` / `rosterPushOrder` / `dropLocalProfile` / `profileIsUntouched`, `profiles.position` and `profiles.name_updated_at` in migration `0005`, `GET /v1/profiles` and `POST /v1/profiles/order`). Sync used to reach exactly as far as the INSIDE of a profile: every set travelled, and the list those profiles sat in did not. A name lived on the phone that typed it, the order lived on the phone it was dragged on, and whether a profile existed on a device at all was a decision each device made for itself with a button — so signing in on a laptop gave you the right training under the wrong names, in a different order, with two of them called "Profile 1" and one missing entirely. `profiles` on the server IS the roster now, and every device builds its list from it and pushes its own changes back, which is the deal the items inside a profile have always had, one level up. **What stays local, deliberately: which profile you are LOOKING at** — that belongs to the person holding the phone, and syncing it would mean opening a laptop changed what the phone was showing mid-set.
  - **Offline is untouched, which is the only reason this is safe.** Nothing in the roster is on the path of anything the app does: a profile is still a whole `state` under its own key, a set is still written to disk the moment it is typed, and every roster call fails soft and retries on the next pass. Train for three hours in a basement and the list reconciles itself when the signal returns, exactly as the log does.
  - **There are exactly two ways two devices can disagree, and both are settled without inventing anything.** A NAME carries the moment it was typed (`nameAt` locally, `name_updated_at` on the server) and the later one wins — not the last device to reconnect, which would let a phone coming back from a week in flight mode silently undo yesterday's rename on the laptop. A rename refused as stale comes back **200 with the name that won**, not an error, so the client takes that as the answer instead of retrying forever. The ORDER is whatever the server says and dragging pushes it (`reorderProfiles` → `rosterPushOrder`, one call for the whole list because a drag renumbers every row after the one that moved); positions the server never set sort **last**, so a list that predates all of this does not shuffle itself.
  - **Adoption is automatic and so is enrolment.** A profile in the account that this device does not hold becomes a local profile (a read grant arrives live, as joining one does); a profile on this device that the account does not hold goes up. That second half is why **signing in now says so before the password field** (`acct.signInAdds`): it is the act that puts this phone's training into the account. The one thing never enrolled is the **first-run blank** (`profileIsUntouched`: no link, no name, nothing in it) — every install makes one, and uploading it is exactly how an account ends up with a stray "Profile 1" for every device that ever signed in.
  - **Removal takes a profile out of the list and leaves the save on the disk** (`dropLocalProfile`). A profile deleted on one device leaves the account and therefore every device's list — that is what "the same everywhere" means — but its key stays, so Storage check lists it as an unreferenced save and offers Recover. That is the difference between "gone from your account" and "gone". An **empty** one is removed key and all, because a trail of blank keys is how that screen stops being worth reading. A removal only ever acts on a profile a listing has confirmed present before (`rec.seen`), so a listing that predates another device's enrolment cannot delete what it simply has not heard of yet, and the list is never emptied below one.
  - **Turning sync off has to survive a roster that would re-adopt it** (`noSync` on the record, `zenofit:dropped`). `syncForget` alone left the very next pass free to bring the same profile back, which is a Turn-off button that turns nothing off. Hence `syncLinked()` beside `syncFor()`: a record can now exist **without** a link, so everything asking "is this in the cloud" has to ask for the `remoteId` rather than for the record.
- **A save that will not OPEN must never become a save that gets replaced** (`unreadable` / `allowOverwrite` beside `readProfileState`, checked in `writeNow`). This was the one way the app could destroy a training history entirely by itself, with no bug anywhere else: a stored state that would not parse — a write cut off by a dying battery, a browser truncating under quota — came back from `readProfileState` as `defaultState()`, the app came up blank and perfectly happy, and the very next autosave wrote that blank over the only copy. One bad read, permanent loss, no warning. Now a key that is THERE and will not parse poisons the WRITE instead: `unreadable` holds that profile's id, `writeNow` returns without touching its key (saying so once, the way the quota warning does), and the bytes stay exactly where they are for Storage check to hand back out — it lists one as DAMAGED and exports it raw. **A MISSING key is not this**: a first run and a new profile have no key and must not be flagged, or nothing could ever be saved. The app still runs rather than refusing to open, because a locked-out user cannot reach the screen that rescues them. The lock is deliberate, not absolute: `importBackup` and `reset-all` call `allowOverwrite()` because both are the user saying "replace what is there" out loud, behind a confirm. What is forbidden is the app deciding that quietly on their behalf — so anything added later that can write a whole profile belongs on that short list, and nothing else does.
- **An app whose only copy is one origin's localStorage owes its user a way to look at that** (`storageScan` / `adoptStorage` / `renderStorage`, Settings → Data → Storage check). When the app comes up empty, three very different things look identical from the inside: the data is gone, the data is fine but this is not the address it was saved at, or the data is fine and right here while the profile index no longer names it. The third is one tap from fixed and used to be indistinguishable from the first, which is the worst way for it to fail — somebody grieves a year of training that is sitting in the same browser, unreferenced. So the screen reads **every** Zenofit key (`STATE_PREFIX`, `STORE_KEY`, `PROFILES_KEY`), says how much training each holds and whether the index knows about it, and prints the origin first, because that is the one thing the screen can be silently wrong about. **Recover is the only write on it and it only ever ADDS**: an orphan is named in the index again, a legacy key is COPIED to a state key of its own (never moved, so a failure half-way leaves the original where it was), then `switchProfile` parks and flushes whatever is open. Nothing there overwrites, deletes or merges, because a repair tool that can destroy what it was opened to rescue is worse than no repair tool. **Every row also carries Export, and Share where the platform takes files** — damaged saves included — and that pairing is the point: a full store is precisely the state that stops Recover from finishing (`switchProfile` flushes, the flush hits quota, and the user is told the device is out of space), which is also the moment the file matters most. So `storageFileFor` reads and nothing else: no flush, no write, nothing that can fail for want of room. The ACTIVE save is written from memory (`backupText`), since that is the fresher of the two and costs no write; every other goes out exactly as stored, in the envelope Import reads; one too damaged to parse goes out RAW under a `-damaged` name, because Import will rightly refuse it but those bytes are the only thing left to repair by hand and are worth more on a laptop than stranded on a phone. `downloadText` and `shareFile` are shared with the Settings buttons, so the file the two routes produce can never drift apart. Anything added later that can strand a save belongs in this scan.
- **Switching is a bigger event than it looks.** `ui` is full of things belonging to the profile being left — an open workout, a half-typed set, a chart selection — so `closeEverything()` clears the screen back to Home rather than leaving it pointing at rows that no longer exist, and an open day is **parked first** (`closeWorksheet`, the same back-out its own arrow does) so it is waiting in the Log tab rather than living on invisibly inside the crash snapshot. Every profile operation flushes with `writeNow()` before it touches anything, because `state` is only written on a debounce. **Deleting the last profile is refused**, not quietly recreated: there would be nothing left to load.
- **A variation is a library row of its own** (`variantOf` / `variantName`, `exWindowVariations`). A wide-grip pulldown and a close-grip one are the same movement and not the same lift: the weights differ, and averaging them into one history describes neither. So each gets its own row, its own log, its own best set, PRs and graph, and everything downstream keeps working because everything downstream only ever knew about library rows. What the link buys is the two things separate rows cannot do for themselves: they are **shown together** (nested under the parent in the library, listed in each other's window), and **the label is composed live** — `exLabelOf` builds "Pulldown · Wide grip" from the parent's current label, so renaming the parent re-labels every variation at once while not one stored name moves. Stored name is identity and must never shift under the log; the label is display, exactly as it is for a translated built-in. `exwin-save` composes the stored name from the parent so it stays unique. A variation of a variation attaches to the ROOT, since nobody wants a tree of grips, and **deleting a parent never takes its variations with it** — they are separate lifts with their own history, so they simply stop being listed as a family.
- **Sync is a copy, never the store** (the SYNC block above `backupText`: `SYNC_COLLECTIONS` / `syncLocalItems` / `syncApply` / `syncPull` / `syncPush` / `syncNow`, with the sheets in `renderSyncSheet` / `renderJoinSheet`). Everything local-first stays exactly as it was: nothing waits on a network to be counted and the app works the same in a basement. It is also **off until somebody turns it on, per profile, behind a confirm that says what leaves the phone** — a training log is the most personal thing in here and it does not start uploading because an update landed. Locally a profile is a whole `state` under its own key; on the server it is a row plus items of `{collection, itemId, json}`, and the bridge is a `remoteId` in **`zenofit:profiles`, outside `state`** for the same reason `zenofit:device` is: `backupText` serialises `state`, a backup is a file people share, and restoring one onto a second phone must not hand it the keys to the original. **What travels is `SYNC_COLLECTIONS` and nothing else**, and the server enforces the same list and refuses an unknown collection *by name* rather than dropping it, so the two disagreeing is loud. Deliberately absent: `drafts` (a photograph of a half-typed set editor) and `timers` (they carry a `cloudId` naming a push alarm booked for ONE device). Of `settings` only the training half goes — `units`, `startDate`, `weekMode`, `sex`, `name` — because theme and language are properties of a phone, not of a person's training. **Change detection is a hash per item** (`marks`, in the sync record), because nothing in this app stamps an edit — a log entry has `createdAt` and has never had an `updatedAt`, and adding one would mean touching every one of the hundreds of places that write. A push is whatever no longer matches its mark, plus a tombstone for any mark that outlived its item; that cannot miss an edit made by code that has never heard of sync, and a second push with nothing changed sends zero. The `clientUpdatedAt` beside it is stamped when the change is **detected**, which is honest for the one thing the server uses it for (refusing to go backwards) and is **not a merge policy**: two people editing the same set between two syncs is not a case this resolves, and dressing it up as one would be worse than saying so. `syncNow` **pulls before it pushes**, since writing over the server before reading it is how an edit made elsewhere disappears unseen. **`syncApply(items, into)` and `syncPull` can target a profile that is NOT on screen**, which is what makes a freshly signed-in device arrive holding real profiles rather than a list of empty names: an off-screen profile is read off its own key, filled, and written back with `writeProfileState` (same two guards as `writeNow` — a save that will not parse is not written over, a full store is reported); `state` is never touched for one, and a LIVE profile is never pulled this way at all, since the whole point of one is that nothing of it is on this phone. The three lists whose order the user set and can see (`groups`, `presets`, `library`) carry their index as `__i` and are sorted back into it on the way in, because an item store has no order; `__i` is stripped before the row reaches `state`.
  - **One oversized row must not stop the other four hundred** (`SYNC_MAX_ITEM`, the `tooBig` list in `syncPush`). The server validates a whole batch before writing any of it and refuses all of it if one item is bad, which is right there — a push that half-lands leaves the client unable to say what it still owes — but the consequence on this side was total: a single exercise photo over 512 KB meant the profile **never uploaded at all**, so the person it was shared with opened it, saw an empty log, and had nothing on either screen naming the one row responsible. A photo is 1000px of JPEG in base64 (`readImageScaled`), routinely 200-500 KB and sometimes past it, so this is not an exotic case. Anything over the limit is now left behind and **named** instead: everything else syncs, the sheet says how many did not and why, and the row is deliberately NOT marked as sent, so shrinking or removing the picture sends it next time with no extra bookkeeping.
  - **The server's message is the useful half, and it used to be thrown away** (`syncErrText`). Errors were reported as `e.code` alone, so `bad_item` appeared on screen while the message beside it read "library/default-0 is 700 KB, over the 512 KB limit" — the app knew exactly which row was the problem and said none of it. The code is now only substituted where the raw word actively misleads: **`not_found` on a profile you are linked to does not mean it is gone**, it means THIS device cannot see it, which is what happens when a share is withdrawn or the phone is signed in as somebody else; same for `read_only`. Everything else keeps the server's own sentence.
  - **A profile's name on the server is set once and has to be kept up** (`renameProfile` from `profile-form-save`). Renaming locally never reached it, so the account sheet listed profiles under names that existed nowhere on the phone. It is fire and forget — the name is display only, nothing is filed under it — and the account list **prefers the name this phone knows a profile by** wherever it is on this phone at all, so a rename that has not reached the server yet cannot make that list disagree with the Profiles screen two taps away.
- **Sync runs itself** (`syncTouch` / `syncQuiet` / `syncPollStart`, hooked into `persist()` and `visibilitychange`). The button is still there and still does the same thing; nothing depends on anybody pressing it. **Pushing is debounced**, not immediate: saving one workout writes state a dozen times in a minute and a push per write would be a dozen requests for one session, so `SYNC_PUSH_AFTER` waits for the typing to stop — and a push that finds nothing changed sends zero rows anyway, so being slightly eager costs one cheap request while being late costs an upload the phone may close before making, hence the `pagehide` flush. **Pulling is polled** (`SYNC_POLL_EVERY`, only while the app is on screen, plus straight away on coming back, throttled by `SYNC_PULL_GAP`), because nothing pushes us: a rest timer gets a real web push, a set logged on the other phone does not. The one hook is `persist()`, which every mutation already goes through, so automatic sync sees every change without a single call site knowing it exists — and `syncApplying` stops a pull's own `writeNow` from scheduling a push straight back. **Nothing here re-renders unless something landed, and not even then while a field has the caret in it** (`syncTyping`): `render()` rebuilds `#app` wholesale, and a sync that repainted mid-word would throw away the input somebody was typing in, from a timer they cannot see. It is silent by design — an unattended failure that raises an alert is a phone interrupting a set to say the wifi is bad — so errors are recorded for the sync sheet and nothing else.
- **A live profile is not on this phone at all** (`syncLive` / `liveEnter` / `liveAdopt`, with the `writeNow` guard). This is the one deliberate exception to local-first, and it exists for a real person: a phone too full to save anything and a training log she still wants to look at. `state` is filled from the server into memory on switching in, `writeNow` refuses to write its key, and closing the app forgets it entirely — there is no clever eviction, just a profile the save path declines to save. **Only ever a READ grant**, never a profile you own: the trade is that no signal means no profile, and losing your own log to a dead connection is not a trade anybody would take, while somebody else's log is still whole on the phone that owns it. Read-only is what makes it safe — with nothing of yours in there, a failed fetch can lose nothing. It starts from a **blank state and no cursor**, so what you end up looking at is exactly what the server holds, tombstones and all, rather than a merge with leftovers; and a failed fetch **puts back whatever was on screen** rather than leaving somebody staring at an empty log and drawing the obvious wrong conclusion, with the strip at the top saying so and offering Retry. `liveAdopt` moves an existing read-only copy over on first launch **without deleting its key** — `liveEnter` drops that only once a fetch has proved the server hands the same thing back, so a phone with no signal on the day this ships still opens the copy it already had. It is also reached mid-session now: a pull that reports the grant has dropped to read hands `syncDemoted` the profile, which adopts it and re-enters it, and a pull that reports the opposite clears `live` so the save path starts keeping it again.
- **An account is a device that got claimed** (`api/src/auth.js`, migration `0004_accounts.sql`, `register`/`signIn` in `zenofit-cloud.js`, `renderAccountSheet` in `app.js`). Identity started as one row per browser install: a token in `zenofit:device`, no way back in once it was gone, and a synced profile stranded on the server the moment a phone died. A username and a password are that **same user row**, claimed — nothing is moved and there is no second users table, so `profiles.owner_id` keeps pointing at what it always pointed at and somebody who registers today keeps what they synced yesterday. Registering *with* a device token claims it; registering without one makes a fresh account, which is what a second person on a shared phone wants. **The password never reaches the server.** A Worker on the free plan gets 10ms of CPU per request, which is less than any honest password hash needs, so the browser runs PBKDF2-SHA256 at 210,000 iterations and sends 256 bits of derived key; the server salts and SHA-256s that once, which is cheap and sound because the thing it hashes is no longer guessable. **The client's salt is the lower-cased username**, not a random value, so a login needs one request instead of two and there is no endpoint that answers "does this account exist" before a password is offered — the cost is that two identical passwords under different names share nothing, which is fine, and usernames are unique so no two people share a salt. If `PBKDF2_ITERS` ever changes on one side, `test/smoke_auth.py` must change with it or every login fails while every test passes. **Tokens moved to their own table** in the same migration: `users.token_hash` held exactly one, which was right while a user WAS a device and wrong the moment you can sign in somewhere else — the second phone's login would have silently signed the first one out. The migration back-fills every existing device's token into a row of its own, so deploying it signs nobody out. `username_lc` carries the UNIQUE index because nobody remembers the case they typed. **There is no password reset** — there is no email to send one to, and the sheet says so before you pick one.
- **Signing in does not drag anybody's training onto the phone** (`refreshCloudProfiles` → `acct-pull`). It lists what the account owns and each one is fetched by hand, as a NEW local profile, the same rule `join-go` follows: merging somebody else's log into a profile that already holds yours is the one outcome here nobody could undo. Signing out forgets the credential and **nothing else** — every profile stays exactly where it is and simply stops syncing.
  - **The account sheet lists EVERY profile on the phone, not only the ones the server knows about** (`renderAccountSheet`, signed-in branch). It used to draw the server's answer and nothing else, so a profile made here and never synced was simply absent — and with the heading saying *Your profiles* and the Profiles screen two taps away saying four of them, the only available reading was that the list had failed to refresh. It had not; it was answering a different question and never said which. Every local profile now appears, in the Profiles screen's own order, each saying where it actually is (*yours* / *can edit* / *read only* + **on this phone**, or **on this phone only**), with the profiles in the account that this phone does not hold listed under them carrying *Get it*. Both of those rows are **rare now rather than routine**: the roster adopts and enrols on its own, so *Get it* and *Back up* are the manual paths for the two states it will not reach by itself (a grant somebody has not accepted, and a profile whose sync was deliberately turned off), and the hint under the list says which of the three situations you are in. A profile that is linked and absent from a listing that **did load** says so too (`acct.notInAccount`), which is what a revoked grant or a second account looks like from here.
  - **Back up is Sync → Turn on, offered from the list where you can see it is missing** (`acct-backup`). It is the same confirm and the same move, and it deliberately does **not** require the profile to be the one on screen. That restriction exists on `sync-enable` because `syncNow` PULLS and a pull writes into `state`, which is whichever profile is open; a first push has nothing to pull, so it reads that profile's own saved state (`profileStateFor` → `syncLocalItems(from)`) and stops. `syncLocalItems` taking a state object is the only reason any of this is safe: nothing here writes to a profile that is not in front of you.
- **One control means "show me what is actually there now"** (`refreshNow` / `swRefreshShell` / `refreshBtn`, the circular arrow in both headers, and the `refresh-shell` message in `sw.js`). Two different things go stale in here and both used to be fixed the same way — close the app, open it again, and if that did not do it, once more. **The training**: a live profile is fetched on the way in and then polled every few minutes, which is right for a phone in a pocket and no use to somebody stood there having just been told a set was logged on the other phone. **The app itself**: `sw.js` answers from cache first and re-fetches behind you, which is what makes it open instantly and work with no signal, and it also means a deploy appears on the SECOND launch — nothing on screen ever said so, so what it taught was exactly that habit. From the user's side those are one request, so they are one button: a waiting worker is taken (which reloads), otherwise the shell is re-fetched past both caches and the page reloads **only if something really came back different** (ETag first, an exact body comparison where there is none), and otherwise it pulls the profile in front of them. It is read-only in every sense — it is on `READ_OK`, and the debounce is flushed before a reload can happen — and it holds its spin for 450ms even when the answer is instant, because a spinner that flashes for 40ms is the same thing to a finger as a button that did nothing.
- **A join code types itself** (the `joinCode` branch of `handleBind`). Ten characters from a 32-letter alphabet, printed `XXXX-XXXX-XX`, and usually copied off another phone a character at a time while somebody reads it out. So the field upper-cases, inserts the dashes after the fourth and eighth, and refuses an eleventh. None of it is *required* — `normalizeSeed` on the server already forgives lower case, missing dashes and the excluded letters — it is there so the thing being typed looks like the thing being read. **The caret is placed by hand**, because rewriting `value` sends it to the end, which on a phone means the cursor jumping past a dash the field just inserted and the next backspace eating the wrong character.
- **A read grant is a constraint, not a label** (`syncReadOnly` / `READ_OK` / `toastReadOnly`, checked in the one click dispatcher). Enforcement is an **allowlist** rather than a list of things to block, so it fails the safe way: an action added next year is refused until somebody decides it is safe, instead of quietly becoming a hole. On the list is navigation and looking — tabs, sheets, filters, the chart, the calculator, the accordion, Storage check, export — plus the sync sheet itself, because *Leave* has to stay reachable from inside a profile you cannot write to, and the timers, which belong to the phone rather than to the training. A strip at the top of every tab says whose profile it is, on Home too, where there is no header to hang it under. The server refuses the write as well; this side is the courtesy that stops somebody logging a session into a profile that will throw it away on the next pull. **Joining always makes a NEW local profile** (`join-go` → `addProfile`), never a merge into one that already has your training in it: that is the one outcome here nobody could undo; your own code typed on the phone that made it is refused outright (`alreadyMine` → `sync.joinOwn`) rather than becoming a second, read-only, live copy of a profile already in the list.
  - **THE LEVEL IS DECIDED BY THE CODE SOMEBODY CAME IN ON, IN BOTH DIRECTIONS** (`/v1/join`). This is the bug that made read-only look like a lie. `ON CONFLICT` used to keep the better of the two levels — a write grant survived a later join on a read code — on the reasoning that only revoking should take access away. But it is the OWNER who mints a code, so handing somebody a read code IS the owner taking write access away, and nobody can promote themselves with a code they were never given. Getting it backwards meant sharing read-only to somebody who had *ever* been given write changed nothing at all: her app said "read only" because that is what the code said, the server kept taking her pushes because the grant still said write, and her sets landed in his log. `PUT /v1/profiles/:id/grants/:userId` is the direct version of the same decision, owner only, wired to *Move to read only* / *Let them edit* in the people list, because "I'd rather she just looked at it now" should not cost her the profile and a new code.
  - **Making a code RETIRES the old ones** (`sync-make-code` → `rotateSeeds`, not `createSeed`). The line under those two buttons always said so and the code never did: every profile is minted with a write seed it never shows anybody (`POST /v1/profiles`), a read code made afterwards left that one live, and nothing in the app had ever revoked a seed. So a profile "shared read-only" still had a working write code hanging off it. Nobody already in is touched — a grant is a person, a seed is only the doorway, which is the difference between this and *Remove*.
  - **A change of level is learned on the next pull, and acted on** (`syncPull`'s `demoted` / `syncDemoted`, and the `live` half of the same patch). Dropping to read turns the local copy into a live profile there and then: the screen locks on the next frame, the copy leaves the phone, and it is re-fetched from the server. Rising above read does the reverse and **clears `live`**, or the profile would be one `writeNow` refuses to save, and a week of her sessions would exist only on the server.
  - **A DRAG IS NOT A CLICK, AND THE ALLOWLIST ONLY GUARDS CLICKS** (`DRAG_READ_OK`, checked in the `pointerdown` handler). Reordering arrives as `pointerdown`, so on a profile whose every button said no, dragging the library, the groups or the presets into a different order went straight through and the next pull silently put it back. Only `profile` and `pinnedTimer` are allowed, which is the same line `READ_OK` draws: the profile index and the timers belong to the phone. It is refused *before* the gesture starts, because a row that picks up, follows your finger and springs back reads as a bug rather than as a rule.
- **A backup is `state`, not a list of things to back up** (`backupText` / `importBackup`, Settings → Data). Everything the user has is one object under one localStorage key, so the export is that object serialised and nothing is enumerated, which is the point: a hand-listed backup silently stops covering whatever is added next, and the first anyone hears of it is a restore missing their custom exercises. **Adding a field to `defaultState()` is all it takes to be included.** The one exclusion is `drafts`, the crash snapshot of whichever form was open at the moment of export: it is a picture of the UI, not of anyone's training, and restoring it drops the person on the other end into a half-typed set editor from a session they were never in. `dayDrafts` is not that and travels. Import goes through the same `hydrate()` the first load uses, so a file written by an older version comes up exactly as that data would if it had been sitting in localStorage, since a restore must never be a downgrade. It accepts a bare state object as well as the envelope, refuses anything without a `log` array and a `settings` object, and asks before it writes, because overwriting a training history with a file that merely parsed is the one failure here that cannot be undone.
  - **The same file goes out two ways, and there is only one file** (`backupName` / `backupText` feed both `exportBackup` and `shareBackup`). Download is the wrong shape for what people do with a backup on a phone — send it to somebody — so the bytes also go to the system share sheet (Web Share Level 2), where a chat or a mail is one tap instead of Downloads plus a file picker. **Never add a second export format for it**: the share and the download must stay the same file or a restore starts depending on which button was pressed. Whether the sheet takes files is *asked*, never assumed: `shareFileType()` probes `navigator.canShare({files})` with a real `File` (it needs a secure context, and some platforms take a `.json` only as `text/plain`, so it tries both and the winner is what the file is built with), memoises the answer, and the button is not drawn when the answer is null — a share button that cannot share is worse than none. `navigator.share` is called with nothing awaited before it, or the browser drops the tap's activation and refuses. A dismissed sheet is `AbortError` and says nothing, since that is an answer; any other failure says so once and falls back to the download, because the sheet is a convenience on top of the file and the file still has to arrive.
- **Muscle groups are records, not a colour map.** `state.groups` is `[{name, key?, color, kind}]`, seeded from `DEFAULT_GROUPS`; `colorFor()` reads it, so recolouring a group repaints every surface at once. **Its order is the order groups appear in everywhere**, and the user sets that by dragging in the group manager (see *Drag to reorder* below). Renaming a group in `actions["group-save"]` has to carry the library, log, **plans, day drafts**, presets, volume goals and the active filter with it, the same sweep the exercise rename does and with the same standing rule: **a new place that files something under a group name belongs in that list.** The log's `muscle` is only a fallback (`muscleOf` reads the library row first), which is why a miss there stayed invisible for so long and exactly why it is worth keeping true, since the fallback is what answers for an exercise no longer in the library at all. There is no sweep of the open workout sheet or entry form as there is for a rename of an exercise, because the group manager opens from the Library tab only and nothing of the sort can be on screen. **Note what a rename does NOT carry: `isCardioEx`/`cardioType` still test the literal name "Cardio"**, so renaming that one group stops new exercises in it being logged in minutes (the built-ins keep their `type` and are unaffected). Fixing that means deciding where a lift's cardio-ness really lives, which is a design question, not a missing line here; deleting a group never takes exercises down with it, and tips whatever is still in it into the bucket rather than refusing, over that same list and unconditionally, since `groupUseCount` counts library rows only while a logged entry can still name a group after its exercise has gone. **`group-delete` rebuilds the survivors from their RECORDS, never from a list of names**: mapping names back into fresh `{name, color}` objects dropped every remaining group's `key`, so deleting one group you invented un-translated all seven shipped ones and lost track of which was cardio. Migration v12 repairs that damage with the same back-fill v5 used.
- **Drag to reorder is one gesture serving several lists.** `startRowDrag`/`moveRowDrag`/`endRowDrag` use pointer events rather than HTML5 drag-and-drop, which never fires on touch, and run entirely on inline transforms without a re-render (`render()` rebuilds `#app` wholesale and would drop the node mid-gesture), committing only on release. A row declares which list it is in with `data-dragrow="<kind>"` and carries a `[data-drag-handle]`; **`DRAG_COMMIT` maps that kind to the function that persists the new order**: `group` → `reorderGroups`, `preset` → `reorderPresets`, `pinnedPreset` → `reorderPinnedPresets`, `pinnedTimer` → `reorderPinnedTimers`, `entry` → `reorderDraftEntries` (the lifts inside the open day), `libExercise` → `reorderLibraryExercises` (one group's lifts inside the flat library, via the same `reorderPinnedIn` move, keyed off the row's `data-group`), `set` → `reorderSets` (the sets inside the open entry, the one list whose order is read as data rather than shown as a choice). Another reorderable list is a row attribute plus one line in that table, not another gesture. The two pinned strips share `reorderPinnedIn`, since "rearrange a filtered view of one master list without disturbing what it filtered out" is the same move either time. **`DRAG_READ_OK` is `READ_OK`'s other half**: the click dispatcher's allowlist never sees a drag, so a new reorderable list has to be decided about in both places, and the default in both is no.
- **A dial is a control, so reordering is a mode.** The pinned strips (presets on Home, timer dials on Home *and* at the foot of the workout and exercise windows) swap their cards/dials for compact drag rows while `ui.presetOrder` / `ui.pinnedOrder` / `ui.timerOrder` is on, rather than wearing a permanent grip handle. You tap a preset card to start a workout and a timer dial to start a rest; a handle living on either is one mis-tap from doing the wrong thing mid-set. `orderToggle()` draws the Reorder/Done control into a `sectionTitle`'s right slot. Note the timer list renders **twice at once** when the entry form sits on top of the workout sheet: two independent containers of the same three rows, which is fine because a drag only ever walks `row.parentElement`.
- **Preset order is user-set, and the pinned strip is a slice of it.** `state.presets` order is the order presets appear in the Library, the picker and on Home. Both lists are rearranged in a *mode* (`ui.presetOrder` on Library → Presets, `ui.pinnedOrder` on Home) rather than by a permanent grip handle, because the cards themselves are what you tap to start a workout and a handle on them would be one mis-tap from starting the wrong day. Home shows `presets.filter(pinned)`, so `reorderPinnedPresets` rewrites **only the slots the pinned presets already occupy** and leaves unpinned ones exactly where they sit, since arranging your home screen must not shuffle the library behind it.
- **Planning is a second ledger that nothing counts.** `state.plans` is `[{id, date, name, entries, createdAt}]`, one dated session you have decided on and not done. Its `entries` are **ordinary entry objects**, the same shape the log uses, which is why the plan builder is not a screen: `renderWorkoutSheet` takes a `draft.planning` flag and the same picker, presets, set list, set editor and "beat last time" card write a plan instead of a day (`commitPlan` vs `commitWorkout`). Two rules make it a plan rather than a log row with a future date, and both matter: **nothing in `state.plans` is ever counted** (not sets, PRs, volume, weeks or charts, and that is the whole point, since a future-dated *log* entry is believed by every calculation downstream), and **a plan may keep entries with no numbers on them** ("Wednesday: these six lifts, weights on the day"), where `commitWorkout` drops blanks. Backing out of a planning sheet saves it; emptying one deletes it, exactly as for a parked day. One plan per date, kept true in `handleBind`'s `draft.date` branch rather than argued about on save.
- **A plan is consumed lift by lift, not by the day.** `plan-start` turns each planned entry into a *blank* entry carrying `e.plan`, a frozen target snapshot (`planTargetOf`: `{sets:[{reps,weight}], unit}`, or `{minutes,intensity}` for cardio), and stamps `draft.planIds` plus, on each entry, a transient `planFrom`/`planIx` back-link that `stripPlanLink` takes off again on the way into the log. The targets ride into the log inside the entries, so "did I do what I said I would" is answerable from `state.log` alone, forever, with no second source of truth about whether a day happened. **Saving a day is not a declaration that the session is over**: people save after the first lift and carry on, so `prunePlans` leaves whatever is still blank *and still in the sheet* on the plan, stamped `startedOn`, and `edit-day` hydrates those back in when the day is reopened; a lift you deleted from the sheet leaves both, because taking it out is the decision not to do it. The plan only disappears once nothing is left of it, and `renderPlanResult` waits for that same moment rather than scoring a session its user is still in the middle of. The back-link is what makes any of this possible: `e.plan` alone cannot tell a planned lift from an ordinary blank, because a plan that named the exercise and left the weights for the day hands over no target at all. `stashDayDraft` carries `planIds`/`planName`, and the back-links ride along on the cloned entries, so parking a session mid-way does not lose the link either. **Planned numbers are never copied into the log**: they appear as *ghost rows* at the end of the set list (`ghostSetRow`), where ✓ (`plan-tick`) logs one exactly as planned and the row itself (`plan-load-set`) opens the set editor with the target loaded. That is the same tap-to-load rule the suggestion card lives under, and it is what buys the smoothness (a session that went to plan is one tap per set) without ever writing a number into the log that a finger did not put there.
- **A saved day keeps what you did not log, and scrapping one is a separate decision** (`state.unlogged`, `unloggedOn` / `unloggedWith` above `commitWorkout`, `actions["scrap-draft-entry"]`). Blank entries used to be dropped on save, which read one gesture as two decisions: *I skipped that lift* and *I forgot to write it down* produced the same result and only the app knew which had happened — and the one you actually did was the one you lost. So `commitWorkout` now files them under `state.unlogged` as `[{date, entries, savedAt}]`, one row per date, and `edit-day` hydrates them back into the sheet after the logged rows and the plan ghosts. **It is not the log and it is not history**: nothing in it is a set, nothing is counted toward volume, PRs, weeks or a chart, and the Log tab does not draw it — the same promise `plans` and `dayDrafts` make. The other half is the bin on a waiting card: no confirm (a blank holds no numbers) and nothing is written until the day is saved, so backing out of an edit undoes it, and on a plan-linked blank it gives up the plan's claim exactly as deleting one from the sheet always has. **Plan-linked blanks are deliberately absent from it** — `prunePlans` already leaves those on the plan and `edit-day` reads them from there, so storing both would deal the same lift into the sheet twice. Two paths unmake a day and both must clear its row or it is orphaned where nothing can reopen it: `delete-day`, and `commitWorkout` when the save leaves the day with no filled rows at all. Being a plain `defaultState()` array it travels in a backup and defaults to `[]` on an older save with no migration, and because it files things under an exercise name *and* a group name it is in all three rename/delete sweeps (`exwin-save`, `group-save`, the group delete).
- **Planned vs done is three verdicts and no cleverness.** `setVerdict` says **beat** (more on one axis, short on neither), **hit** (matched) or **under**, matching planned set *i* to logged set *i* by position, with anything past the end of the plan a bonus set. It deliberately does **not** judge on estimated 1RM: a heavy triple outscores the eight you planned, and calling that "target hit" would be the app deciding what you meant. **That rule is for plans only** (see the next bullet: measured against last time, the same trade reads as the improvement it is). `entryPlanResult`/`dayPlanResult` aggregate it for the set list, the entry card, the history row, the day chip and the result sheet (`renderPlanResult`), which is shown once on saving a planned day and never volunteered again. Under is never scolded anywhere it appears.
- **The verdict, pointed at last time** (`setProgress` / `lastTimeSets` / `entryLastResult`, drawn in `renderSetList`). Est. 1RM speaks for an *exercise* through its BEST set, which is the right answer to "what could I lift for a single" and the wrong answer to "did today go better than last time": match your top set, add a rep to your second, and the headline estimate does not move even though the session was strictly better. So with no plan to answer to, each set is compared with **the set in the same position last session**. It is graded by `setProgress`, **not** by the plan's `setVerdict`, and that distinction is the whole point: the two-axis rule calls a set under the moment it is short on either axis, so 14 × 60 kg followed a week later by 11 × 65 kg read **under** on the strength of the reps alone — while that set is 88.5 kg of estimated max against 87.4, and the est. 1RM card open on it said "1.1 higher than set 2" in gold at the same moment. Trading reps for plates and coming out ahead is the shape of getting stronger, not a step backwards, and the app was contradicting itself on one screen to say otherwise. `setProgress` asks the per-set score instead, **rounded, so the verdict is checkable against the two numbers actually printed**, and the one-axis kinds are unaffected because for reps and for seconds the score IS the axis. **Against a plan the two-axis rule stays**: a plan is a sentence you wrote down and 11 reps is not the 14 you said, which is a different question with a different right answer. Sets past where last time ran out are simply **unjudged**: no verdict, no penalty, so a session can never score worse for containing more work, which is the trap any average over sets falls into (adding a real back-off set drops a mean by several kg and quietly teaches people not to log it). A plan outranks last time where both exist, cardio and first outings return null, and last time's weights are brought into the unit being typed in by **`weightAs`, which rounds to TWO decimals**, so a kg set and the same set logged in lbs cannot disagree by a float hair. That rounding used to be one decimal, and it invented verdicts of its own: 26.25 kg came back as 26.3, so a set that repeated last session exactly was logged as less than the number it was being measured against and read **under**, with the card above it simultaneously reporting a *higher* estimate off the same rounding. Two decimals hold every step a plate tree can make (1.25 kg, 2.5 lb), which is all the precision a weight off the log ever claims; `weightAs` is now the one road every past weight travels to sit beside a present one (`lastTimeSets`, `openingSetFor`, `setSuggestion`), so they cannot round differently from each other again, and the row's own "last time 7 × 26.25" prints at that same precision. **Under is never counted up at you**: the tally above the list names only what was beaten or matched. Nothing here touches the exercise's est. 1RM, the PR badge or the graph.
- **The entry card names two numbers, and no longer offers an opinion** (`entryComputed` → `entryRefCols`, kept live by `updateEntryPreview`). Beside the exercise's est. 1RM sit **LAST TIME** and **BEST EVER**, in that order because that is the order they are useful in: last week's number is the one you can do something about tonight, and putting the all-time ceiling first would make every ordinary session read as a failure. Each wears the set list's own `VERDICT_COLOR` against its own bar — gold once today's figure is past it, green when level, muted until then — so *did I beat it* is answered by the colour and *by how much* by the two numbers, with no sentence in between. This replaced a single word out of `BADGE_TEXT` ("Beat your best 💪", "Below best, normal, keep going"), which is gone along with those strings: **encouragement is not information.** It never said what the best actually WAS, so the one question it provoked was the one it could not answer, and the only bar it implied was an all-time one that most sessions are nowhere near. A bar that does not exist yet prints an em dash rather than vanishing, so the row keeps its shape the moment history arrives, and no unit is repeated on either — they are the same quantity as the figure beside them, whose label already carries it. **The window is filtered by KIND as well as by name**, which the word never was: that mattered less when the output was a sentence and matters completely now that it is a number, since `metricOf` answers in kilos for a strength session and in reps for a bodyweight one, and pooling them put a rep count in a kilo column. It is otherwise deliberately wider than `earlierOutings` — it includes the entries in the open day sheet, which are not in `state.log` yet — so a lift logged twice in one session is measured against its own earlier card. `BADGE_SHORT` is untouched and still labels the rows in your history, which is a label on a list rather than a verdict delivered mid-set.
- **The est. 1RM in the set editor is measured against the set in the same position, with the all-time best beside it** (`lastSetMetric` / `bestEverMetric` / `vsLastLine` / `bestEverBlock`, kept live by `updateSetPreview`). On its own that figure answers nothing, because nobody carries last week's estimate around in their head, and the whole point of typing your own numbers is that you did not want either option the suggestion card offered. Two references, because they answer two different questions and conflating them was the bug. **The main one is positional**: set two is measured against last session's *set two*, on the same per-set score `setProgress` grades the row behind the sheet with, so the number and the beat/under badge on the row can never disagree. It used to be measured against last session's **best** set, which made the card say "1.2 lower than last time" on a back-off set that had just beaten the back-off set it was actually repeating: true statement, wrong question. It therefore names the position as well as the number ("set 2 last time 29.1 · 23 Aug"), or the figure reads as the session's, which is exactly what it stopped being. Sets past where last session ran out are **unjudged**, the same rule `entryLastResult` follows, and the card says so in a faint line rather than going blank, because a card that silently drops its comparison reads like a bug. **The side one is all-time**, small and muted: the best this lift has ever been worth, over the same strictly-earlier window the PR badge reads (`earlierOutings`), so the two can never disagree about what "best" was. It is the ceiling and not a target, which is why it is second and quiet, and it goes gold and says *new best* the moment the set in the boxes clears it, which is the same claim the badge will make when the entry is saved. Both are read in the unit being typed in (the positional one through `lastTimeSets`, the all-time one through `weightAs`), because a kg estimate held against an lbs one is not a comparison. Both are computed **once per render** and parked in the module-level `setRefs`: neither can move while the sheet is open (typing does not write to the log, and the unit select does a full render), and each otherwise costs a sort of the whole log per keystroke. It wears the set list's own `VERDICT_COLOR` (beat/hit/under), stays put under a plan because it states a fact about a number rather than proposing one, and is text and colour only, no icon, because it is rewritten in place while you type and a freshly injected lucide placeholder has nothing to turn it into a glyph.
- **Set order is data, which is why the set list is draggable** (`reorderSets`, `data-dragrow="set"`). Everywhere else an order is presentation; here `entryLastResult` reads it, so a session worked up and logged bottom-first comes back as a row of "under" verdicts describing nothing but the order it was typed in. Dragging it into the order the sets actually happened is what makes those verdicts mean anything. Reordering is a **mode** for the same reason it is one everywhere else (a set row is what you tap to correct a number), and `ui.setOrder` holds the ENTRY'S ID rather than a boolean, so opening a different lift stops matching instead of leaving a mode for twenty call sites to remember to clear. Nothing derived moves with it: `bestSet()` takes the highest estimate wherever it sits.
- **A plan is not a preset, and the difference is load-bearing.** A preset is a bundle of exercises with **no date and no numbers**: the shape of a session you repeat, and what the pinned strip on Home is for. A plan is **one dated session with the weights you are going for**, which is why today's plan gets its own card above the pinned strip and is gone again tomorrow. They compose, and *Add exercise → Presets* inside a planning sheet is the normal way to start one. Don't let either grow into the other.
- **The Calendar tab is where a plan is born and started** (`renderCalendarTab` = month grid → day card → plans list → deload planner → `renderVolume`). Tapping a day now means two things at once: it still picks the period the volume numbers are read over, and it selects `ui.calDay` for **the day card** (`renderDayCard`), the one surface that answers "what is on this day" in the same shape past or future: what you trained, what you planned, the parked draft if there is one, and the one or two things worth doing about it. Which button is the big one follows the calendar, not the feature: *Start* on today or earlier, *Edit plan* on a day you cannot train yet. On the month grid a **solid dot is a group you trained and a hollow one a group you have planned**, with anything already trained dropped from the planned row.
- **Deloads are planned, never inferred.** `state.deloads` is `[{id, start, end}]` with inclusive ISO dates, set by tapping two days on the Calendar tab. `deloadStatus()` decides what the home banner says: nothing, a countdown once the start is within `DELOAD_HEADSUP` days, then a day-N-of-M badge while it runs. The old five-hard-weeks radar is gone, since it was guessing at something only the lifter knows.
- **A week is seven days from your start date, or the last seven days, the user's call.** `settings.weekMode` is `"program"` (default, and what every existing save migrates to) or `"rolling"`, read through `rollingWeeks()`. Program mode is the spreadsheet's: `weekOf()` counts from `settings.startDate` and every seventh day turns the page. Rolling mode replaces that with a *window*, `windowEnding(day)`, for lifters whose split simply comes round in order and for whom a Sunday and a Monday session are the same session. In rolling mode: the Calendar tab reads `ui.volAnchor` (the LAST of its seven days, set by tapping a calendar day, stepped a whole window at a time by the arrows) and sums with `volumeInRange` instead of `volumeForWeek`; the Progress tab's bar chart uses `rollingSetBlocks` (seven-day blocks counting back from today) instead of `weeklyTotals`; and **the program-week chips disappear** from the header, the history day cards and the workout sheet, because in that mode there is no program week to name. `volumeForWeek`/`weekOf` are deliberately kept for program mode rather than expressed as a date range: `weekOf` floors everything before the start date into week 1, and a range would silently drop those rows. **Deloads are untouched by the setting** and must stay that way: they are dates the user put in the calendar, not something derived from a week number.
- **A volume bar is a promise of a target.** In the Calendar tab's volume list a group only gets a progress bar when the user has set a target for it (`state.volumeGoals`). Without one there is no bar and no grading. The old behaviour filled the bar against the biggest group trained that period and flagged others "Low", which made a bar move for reasons that had nothing to do with the lifter, and called a rest day a failure. An untargeted group instead states the one fact available without a plan: how the period compares with the one before it (`vol.more`/`vol.fewer`/`vol.same`). Don't reintroduce a default target.
- **The Calendar tab's month grid** (`renderCalendar`) layers four independent things on each day cell: a tint for the program week whose numbers are shown below (or a `--raise` tint plus a border for the selected `ui.calDay`), a dashed gold band for a deload, solid dots for the muscle groups trained, and hollow dots for the ones a plan has lined up. Calendar maths is all ISO strings (`isoOf`, `monthOf`, `addMonths`, `monthGrid`, `weekRange`) built from local date parts, so a daylight-saving shift can't move a day.
- **`UNCATEGORIZED` is a bucket, not a group.** It is never in `state.groups`, and exercises land in it two ways: their group got deleted, or they were quick-added mid-workout and the muscle question was skipped (`pick.skipMuscle` → `quick-add-muscle` with the bucket as its `data-g`). Two list functions keep the distinction: **`libraryGroups()`** is what the user can *choose* (filter chips, the muscle dropdown, quick-add chips, the group manager) and never contains it; **`allGroups()`** is what must be *shown* (library sections, the exercise picker) and appends it last when anything is in it. It has no target control in the volume list, its name is refused in the group editor, and it disappears on its own once every exercise has been re-filed. Adding an exercise *from the Library* still requires a group, and Skip exists because you were mid-set, not as a way to leave the form blank.
- **Numbers accept a comma or a period.** Every numeric field is `${NUM}` (a text input with `data-num`, not `type="number"`, which discards the "wrong" separator). `handleBind()` strips non-numeric characters and stores the value period-separated via `decimalize()`; the field itself keeps whatever the user typed. Add new numeric fields with `${NUM}`, never `type="number"`.
- **`migrate(s)`**: schema migration for `state` loaded from localStorage. Bump/extend this whenever the persisted shape changes, rather than assuming a fresh shape.
- **`render()`**: rebuilds the `#app` innerHTML from `state`/`ui` on every change. Sub-renderers per tab/screen (`renderHome`, `renderLog`, `renderHistory`, `renderCalendarTab`, `renderProgress`, `renderCalc`, `renderLibrary`, `renderBody`, `renderTimers`, `renderProfile`, etc.) return HTML strings that `render()` assembles. `patch(p)` is the standard way to mutate `state` (shallow-merges, then persists + re-renders).
- **Event delegation, not per-element listeners.** Clicks are handled by a single `document.addEventListener("click", ...)` that dispatches on the closest `[data-action]` ancestor to the `actions` object (a big lookup table of action-name → handler, defined right before the click listener). Typed input is handled by delegated `input`/`change` listeners keyed on `data-bind` attributes, routed through `handleBind()`. When adding new interactive elements, follow this pattern (`data-action="my-action"` + an `actions.my-action` entry, or `data-bind="path.to.field"` + a branch in `handleBind`) rather than attaching listeners directly to DOM nodes, since nodes are thrown away and re-created on every `render()`.
- **`data-stopprop`** marks elements (sheet backdrops, nested editors) where an outer `data-action` must not fire when a click lands on an inner one, see the click listener for the containment check.
- **Sheets/overlays** (`sheet()`, `fullScreen()`) are modal-style panels layered via `ui` flags (e.g. `ui.showProfile`, `ui.showBody`, `ui.workoutSheet`, `ui.entryForm`, `ui.groupSheet`) rather than routing. Body measurements is one of these windows, opened from the ruler button next to the header gear, and it is not a bottom-nav tab.
- **Timers** run on their own interval engine (`startTimerEngine`, `sweepTimers`, `fireTimer`) independent of `render()`, with Notification API integration (`askNotifyPermission`, `notifyDone`). One timer can be on screen several times at once: its card on the Timer tab, and its round dial (`pinnedTimerDial`) both on Home and at the bottom of the workout and entry windows, where `renderTimerList()` repeats the same up-to-3 `pinnedTimers()`, so `paintTimers()` addresses every copy by `[data-tmr-time]` / `[data-tmr-ring]`, never by a single element id. Every dial carries the same pause/reset pair the Timer tab's cards have, wherever it appears; an *idle* dial has nothing to pause, so it stays bare and the row doesn't jump when one of three timers starts. Because those dials sit inside overlays, the timer editor sheet sits at `z-index` 120, above all of them.
- **A rest timer is two alarms, and the local one wins wherever it can** (`cloudTimerStart` / `cloudTimerCancel` beside `startTimer`). `startTimerEngine` ticks every 250ms and `fireTimer` does the chime, the buzz and the notification, all of which need a living tab — so locking the phone mid-rest, which is exactly what people do, throttles that tab and then discards it, and the alert the timer existed for never happens. So every start also books the same deadline with the server (`ZenofitCloud.scheduleTimer`), which pushes a notification whether this app is alive or not. Three rules keep the pair from both going off in your ear: **the local one is scheduled to win** — the server's copy is booked `PUSH_GRACE_MS` (2s) late and `fireTimer` cancels it on the way past, so the push only ever speaks when the page was not there to; the gap is already in our favour, since the server starts counting when the request lands and we started when we sent it, but leaning on network latency for correctness is not a plan. **It is a second chance, never a prerequisite**: nothing is awaited, every failure is silent, and every degraded path (no `ZenofitCloud` at all, push blocked, push not enabled, the call throwing, a timer longer than the API's one-day ceiling) leaves the local timer running exactly as before — a rest timer starts the instant it is tapped, in a basement gym with no signal. **The deadline goes as a duration, never a wall-clock moment** (`inMs`, which the client puts on the wire as `durationMs`): a real phone tested here was 2.8 seconds off the server, and `inMs` means the phone's idea of the time never enters the arithmetic. Every transition that stops a countdown hands the server's copy back — pause, reset/stop, `fireTimer`, editing a running timer's length (`timer-save` restarts it, so the old deadline is stale), and `timer-delete` before the row leaves state. The handle is `t.cloudId`, which **persists in state on purpose**: start a rest, let the app die, reopen, tap Stop, and that is the only way the stray push can still be called off. Because it persists, `backupText` strips it next to `drafts` — it names an alarm booked for THIS device, on a server that will only cancel it for the device that booked it, and a backup is a file people share.
- **Alert sounds are synthesised, never files.** `SOUND_LIB` is a dozen alerts written as note lists (`[start, freq, length, waveform, gain, glideTo?]`) that `playSound(id, volume)` schedules on the Web Audio context, with no mp3s to download, cache, miss offline or license. **Sound and volume are per timer** (`t.sound`, `t.volume`, defaults `DEFAULT_SOUND`/`DEFAULT_VOLUME`, which live in the storage section because `seedTimers()` runs before the audio code is reached), edited in `renderSoundPicker()` inside the timer sheet, and read through `soundOf()`/`volumeOf()` so a malformed or missing value can never silence a timer. Volume 0 is a real choice and schedules nothing.
- **Charts** (`drawBarChart`, `monotonePath`, `niceTicks`) are hand-drawn SVG, no charting library. The progress line chart (`drawLineChart` → `paintLineChart`) is the interactive one: pinch/wheel zoom, drag to pan, tap a dot to open the entry behind it, and a fullscreen copy (`renderChartFull`). Its view (`ui.chartView`) and selection (`ui.chartSel`) live in `ui` so a re-render never resets them, in-flight pointer state is module-level (`chartPointers`/`chartGesture`) because a gesture redraws the chart underneath itself, and **every `[data-linechart]` of the same scope is painted from the same state**: the card and the fullscreen window are one chart drawn twice. Selecting a point deliberately patches `[data-linedetail]` in place rather than calling `render()`.
- **The graph does not stop at your data.** `ui.chartView[scope]` is `{lo, hi, yLo?, yHi?}` in *index* space (x) and *value* space (y), and `chartWindow`/`setChartView` deliberately allow it past both ends of the series, out to `chartMaxSpan(n)` and far enough either side that the history is nearly, but never quite, off screen. The empty space in front of the last session is the feature: a graph that ends at your best set reads as a ceiling. `yLo`/`yHi` absent means the vertical axis is still auto-fitting to whatever is on screen (`niceTicks`), which is what makes a zoomed-in plateau readable; a pinch or a vertical drag freezes it and hands it over (`ticksWithin`, which fits ticks *inside* a given domain rather than rounding the domain outward). Vertical dragging is fullscreen-only (the card in the tab has `touch-action:pan-y` because the page under it has to stay scrollable), which the paint reads off `data-chartfull` on the wrap. `chart-reset` (or a double-click) is the one way back to auto.

**There are two of that chart, told apart by scope.** `"main"` is the Progress tab's; `"ex"` is the copy at the bottom of the exercise detail window (`exWindowProgress`, fed by `exerciseHistory`), which can sit on top of the Progress tab. The scope is the value of the `data-linechart` / `data-linedetail` / `data-charttoolbar` attribute and the `data-scope` on every chart button, and it keys the series (`chartState.line` / `.exLine`), the zoom (`ui.chartView[scope]`), the selection (`ui.chartSel[scope]`) and which one `ui.chartFull` has blown up. Anything new that touches the chart has to carry the scope with it, or the two graphs will start redrawing each other.
- **Under that graph is the ledger it was drawn from** (`exerciseHistory().sessions` → `exWindowHistory`). The graph says where a lift has got to; the list says what you actually did, newest first, every set written out in the unit it was logged in. **A row is a DAY, not an entry**: two entries of the same lift on one day are one session's work and nobody remembers them as two, so they are merged, and the session's headline number and its PR flag are taken from the FIRST of its points to reach the day's best (taking the last would call a day that opened with a PR and then backed off a "match" of itself). Both readings come out of the one `exerciseHistory` call for the same reason the two graphs share a scope: a list and a graph answering different questions about one set of facts must never answer them from different facts. Rows past `EX_HISTORY_PAGE` are folded away behind one tap (`ui.exHistAll`), because somebody who has benched for two years has a hundred of them and a hundred cards would make the graph the thing you scroll past. The sets themselves come from **`outingRows`, shared with `renderLastTime`**, which is the same question ("what was that session") asked from two places.
- **Tapping a session goes to that day in the log** (`open-log-day` → `ui.logJump` → `flashLogDay`), because a date is a session you trained and the rest of what you did that day is most of what you came back for. Sending someone to a date is not the same as showing it to them, so the Log tab's history card carries `data-day` and the arriving frame scrolls to it and lights it for a moment; the marker is spent on that frame and the class goes on the node rather than into the HTML, or `render()` would replay the flash on every keystroke afterwards. A workout window in the way is closed the way its own back arrow closes it, parking the day, which is why the hint under the list says so *before* it is tapped and why the destination is set after that back-out rather than before (a plan saved on the way out lands on the calendar and would otherwise overrule the jump).
- **The 1RM calculator tab** (`renderCalc`) is stand-alone: nothing it does is logged. Its maths is `calcPct`/`calcReps` at the top of `app.js`, the same anchored Wathan curve the log runs on, read forwards and backwards, and its tables are built from the *unrounded* max so they round exactly once. The curve flattens onto an asymptote near 49.6% of the max, so `calcReps` returns `Infinity` below that and the percentage table prints `30+` rather than inventing a rep count.
- **Strength standards are a lookup, not a feed** (`renderProgStandards` and the STRENGTH STANDARDS block in `app.js`, data in `standards.js`). The Progress tab's second segment, the old `PLACEHOLDER_RANKS_SLOT`, answers one question about one lift: pick it, say what you weigh and what you lifted, tap. Seventy-one lifts × two sexes × nineteen bodyweights is 12,780 numbers, and **any amount of it on screen at once is a wall nobody reads**, which is why there is no ambient rank anywhere in the app and why anything new that shows one still has to go through `stdCheck()`. Nothing here is logged and nothing here writes to history, exactly like the calculator tab.
  - **The lift field takes a max OR a set, and they are the same answer** (`f.mode`, `stdMode` / `stdSetMax` / `stdLiftValue`). The tables are written in one-rep maxes and nobody trains in them, so *What you lifted* switches the field between a 1RM and reps × weight, and a set is folded into a max by `est1RM` — the log's own anchored Wathan curve, reps rounded exactly as `calc-run` rounds them. **That identity is the point**: the rank from 5 × 135 is the rank you would have got by working the max out on the 1RM tab and typing it back in, which is the trip the switch exists to save, and a second curve here would be a second answer. The running est. 1RM beside the two boxes is patched in place while typing like the hints are, and is label-plus-number only — no caption about the formula, per the rule above. The two routes keep their own fields, so flipping the switch overwrites nothing and only throws the last verdict away, and `stdCheck` records the set on `res.set` so the card can name it (`std.fromSet`): a rank quoting a number nobody typed cannot be checked by hand. A rep-count standard has no max to estimate and never sees the switch.
  - **The five levels are renamed in the labels only.** The source's beginner/novice/intermediate/advanced/elite are `STD_LEVELS` = wood/gold/diamond/titanium/vibranium, drawn in `--tier-*` (per theme, in the THEMES block of `styles.css`, because a tier name has to read on a near-white card too). Nothing about a tier is persisted, so the words can change freely.
  - **It refuses to guess two things.** `settings.sex` starts `""` and the check stays disabled until it is answered, because the tables are split and a default is not a preference, it is the wrong table. It is asked in the one place it is used and is deliberately *not* in Profile. And the lift number is only ever pre-filled from the log where `STD_MATCH` ties a built-in library id to a slug, never for a rep-count standard: the log stores every set as reps × weight, so "your best set of pull-ups at bodyweight" is not in there to be read. The pre-fill is an est. 1RM, so it fills the 1RM route only; the set route starts blank, because it is for the set in front of you rather than one already on record.
  - **A pre-fill hint is a claim about provenance.** "Your best from the log" / "your check-in on 12 Aug" stop being true the moment the field is typed over, and typing never causes a render, so `handleBind` retires both hints in place (`stdLiftHint` / `stdBwHint`). Bodyweight is read from the latest Body check-in and never written back; typing over it is a what-if.
  - **Thresholds are converted and rounded once, on the way out** (`stdThresholds`), so the ladder and the verdict can never disagree. Bodyweights between two 5 kg rows are interpolated; past either end of the grid the end row is used, because there is no data out there to extrapolate from.
- **Compound vs isolation is gone, and so is `type`.** What a lift is logged in is `kind` (see above), declared by its group and overridable per exercise. `type` is only still READ, as the legacy path in `exKind` for library rows saved before v13 that carried `"Cardio"` there; nothing writes it any more, and old `"Compound"`/`"Isolation"` values are read by nothing at all.
- **Theming** is entirely CSS custom properties (`--bg`, `--text`, `--gold`, etc.) swapped via `data-theme="dark"|"light"` on `<html>`, set by `applyTheme()` and mirrored by the anti-flash inline script in `index.html` (reads the last saved theme before first paint to avoid a flicker).
- **Images** (exercise thumbnails, etc.) are downscaled and re-encoded client-side in `readImageScaled()` before being stored, to stay under the localStorage quota, so don't store raw uploaded file data.

One placeholder slot is still called out in the top-of-file comment (`PLACEHOLDER_BODY_GRAPH_SLOT`, body measurement graphs) marking an intentionally-deferred feature, so grep for the token before assuming it is simply missing. `PLACEHOLDER_RANKS_SLOT` is gone: the Progress tab's second segment is the strength standards now.
