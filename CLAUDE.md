# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

# Git workflow

This folder is a git repo connected to https://github.com/KerlitTheDog/zenofit (branch `main`).

**Never push automatically. Always ask first.**

After editing files, stage and commit them if useful, but stop and ask the user before running `git push`. Summarize what's about to go up (which files, what changed) so they can decide. Wait for a clear yes.

This applies even to small or routine changes — the user wants a say in what reaches GitHub every time.

Also always ask first for anything destructive to git history (force-push, `rebase`, `reset --hard`), and never force-push over a rejected push.

Note: this local folder is the source of truth. Editing files directly on the GitHub website risks those edits being overwritten by the next push from here.

# Project overview

Powerbuild Tracker (product name "Zenofit") is a mobile-first powerbuilding/progressive-overload tracker: workouts, weekly volume, PRs, and body measurements. It's a **faithful port of a spreadsheet** ("AbsoluteMain.xlsx") — the header comment in `app.js` maps each spreadsheet formula to its JS equivalent (week number, muscle-group lookup, est. 1RM, cardio score, "vs. Your Best" badges, dashboard rows, weekly volume, deload radar, body trend). When changing any of that logic, check the comment block at the top of `app.js` for the spreadsheet formula it's meant to reproduce.

The one deliberate departure from the spreadsheet is the **1RM estimate**. The sheet used Epley, which reads a single at 30 kg as a 31 kg max; the app now uses Wathan's equation divided by its own one-rep value, so one rep is exactly the weight lifted (`rmCurve`/`est1RM`, with the reasoning and the formula bake-off written up in the comment above them). Everything downstream — best set, PRs, goals, the progress graph, the calculator tab, the set suggestions — reads that one curve, so it is the only place to change it.

**The formula is a code detail, not a caption.** The bake-off, the comparison with Epley and the name "Wathan" belong in that comment and in exactly one place in the UI: the *A note on the 1RM estimate* accordion in Home → How this works (`acc.rm.body`). Nowhere else in the interface names the formula — not the calculator's result line or footer, not the entry form, not the set editor — because reminding someone which equation you used every time a number appears is noise, not transparency. Don't reintroduce it when adding a surface that shows an est. 1RM.

It's a installable PWA (see `manifest.webmanifest`): standalone display, portrait-locked, with home-screen install providing real orientation lock on Android and enabling timer notifications on iOS.

# Running / testing

There is no build step, package manager, or test suite — this is plain HTML/CSS/JS loaded directly by the browser. To work on it, just open `index.html` (or serve the folder with any static file server) and reload after edits. There's no linter or formatter configured; match the existing style in the file you're editing.

# Architecture

Everything lives in four files: `index.html` (shell + theme-flash-prevention inline script), `styles.css` (all styling, theme-driven via CSS custom properties), `i18n.js` (every string, in three languages), and `app.js` (the entire application).

# Languages

English, Українська and Svenska. `i18n.js` holds `UI[lang]` (all interface copy, keyed by dotted name) and `EX[lang]` (the 41 built-in exercises as `[name, equipment, alternatives, note]`, in the same order as `DEFAULT_LIBRARY`). English lives in `UI.en` and in `DEFAULT_LIBRARY` itself. `T("key", vars)` looks a string up and falls back to English then to the key, so a partial translation is always safe; `TN("day", n)` picks plural forms (one/other for en+sv, one/few/many for uk). Long copy carries its own `*bold*` and `_italic_`.

Adding or removing a language means editing `LANGS`, `LOCALES` and the matching `UI`/`EX` blocks. `resolveLang()` coerces anything not in `LANGS` to English, so a saved setting for a language that has since been dropped degrades quietly — and `migrate()` rewrites it on load.

**The rule that keeps data safe: translations are display only.** Everything persisted stays in English, because those strings are identity — a log entry points at `"Bench Press (Barbell)"`, a goal is filed under it, an exercise sits in the group `"Chest"`. Switching language must never orphan a logged workout. So:

- `exLabelOf(ex)` / `exLabel(name)` / `exFieldOf(ex, field)` translate built-in exercises via their stable `default-N` id; a custom exercise, or a built-in field the user has edited, is shown exactly as typed.
- `groupLabel(name)` translates a group only if it carries a `key`; renaming one drops the key, because the name is theirs now. Same trick for seeded timers (`timerLabel`, `key: "rest"`).
- **`data-*` attributes are lookup keys and must carry the stored English name**, never a label. Translating one silently breaks the click handler that resolves it.
- Dates go through `fmtDate`/`fmtShort`, which use `localeTag()` so they follow the app's language rather than the device's.

**`app.js` is a hand-rolled single-file SPA framework** — no React/Vue/build tooling. Key pieces, in the order they appear in the file:

- **`DEFAULT_LIBRARY`** — the seeded exercise library (name, muscle, kind, equipment, alternative, cue notes), ported verbatim from the spreadsheet's Exercise Library sheet.
- **Pure calculation helpers** (`bestSet`, `syncEntry`, `computeBadges`, `dashboardRows`, `weeklyTotals`, `volumeForWeek`, `deloadRadar`, `bodyTrend`, etc.) — these are the spreadsheet-formula ports; keep them side-effect-free.
- **`state`** (persisted) vs **`ui`** (transient, in-memory only) — two separate global objects. `state` holds workout log, library, muscle `groups`, presets, timers, goals, body measurements, `dayDrafts`, settings; it's loaded via `loadState()`/`migrate()` and written to `localStorage` under key `powerbuild-tracker:v1` via `persist()`/`writeNow()` (debounced autosave, flushed on visibility change / pagehide / beforeunload). `ui` holds open sheets, form drafts, filters, etc., and is never persisted directly — but in-progress drafts (open workout sheet, entry form, set form, body form) are snapshotted into `state.drafts` so a killed/reloaded tab restores exactly where the user left off (see `snapshotDrafts()` and the `restoreDrafts` IIFE at the bottom of the file).
- **Two unrelated things are called "drafts."** `state.drafts` is the crash/lock snapshot of whatever form is open right now. `state.dayDrafts` is deliberate: backing out of a half-built workout parks the whole day there (`closeWorksheet()`/`stashDayDraft()`), it renders above the history in the Log tab, and nothing in it counts toward sets, PRs, volume or the charts until the day is actually committed. **There is only ever one workout for today**, which is what `actions["log-exercise"]` (the Log exercise button in the exercise detail window) has to respect: it opens the sheet you already have open, else today's parked draft `draftId` and all, else a fresh day — it never starts a second one — and then drops straight into that exercise's entry form. It is a shortcut past New Workout → Add exercise → find it in the picker, not a second way to write to the log.
- **Set suggestions are built on last time, not your best ever** (`setSuggestion`, and the `SUG_*` constants above it). The card at the top of the entry window — above *Add set*, deliberately, because that window is where you decide what to do while the set editor is where you write down what you already decided — offers two ways past the previous session's best set: one more rep at the same weight, or the smallest real weight step (`weightStep`) at the same reps. Holding the reps on the heavier option is deliberate: dropping reps as weight goes up is normal training but would not raise the estimate, and the card only ever offers something that scores higher (every option is filtered through `metricFor`). **Neither option is recommended over the other** — they render identically, and `bySmallestStep` only ranks them by the one thing the app can compute exactly: which raises the estimate least, tagged `sug.smaller` (and tagged on neither when they tie). That lands on the extra rep in the 8-12 range and on the extra weight down on heavy triples, where one more rep is worth far more than a plate. This replaced an inferred double progression that was broken twice over — mechanically (the rep ceiling was a median of a window including last session, so "you're under your range" required your reps to have just *dropped*, which following the app could never cause, making the answer "add weight" forever) and in principle (**a rep range is an intention, and the log only records what you did** — crowning an option on a guess about someone's programming is the same mistake as a progress bar filling toward a goal they never set). If you reintroduce double progression, it has to run off a range the user actually set, not one read out of their history. The set editor shows the same two buttons, minus whichever the open set already *is*. **Both are tap-to-load, never auto-filled** — the log records what you did, never what the app hoped you would do.
- **Muscle groups are records, not a colour map.** `state.groups` is `[{name, key?, color}]`, seeded from `DEFAULT_GROUPS`; `colorFor()` reads it, so recolouring a group repaints every surface at once. **Its order is the order groups appear in everywhere**, and the user sets that by dragging in the group manager (see *Drag to reorder* below). Renaming a group in `actions["group-save"]` has to carry the library, log, presets, volume goals and the active filter with it; deleting one tips whatever is still in it into the bucket rather than refusing.
- **Drag to reorder is one gesture serving several lists.** `startRowDrag`/`moveRowDrag`/`endRowDrag` use pointer events rather than HTML5 drag-and-drop, which never fires on touch, and run entirely on inline transforms without a re-render (`render()` rebuilds `#app` wholesale and would drop the node mid-gesture), committing only on release. A row declares which list it is in with `data-dragrow="<kind>"` and carries a `[data-drag-handle]`; **`DRAG_COMMIT` maps that kind to the function that persists the new order** — `group` → `reorderGroups`, `preset` → `reorderPresets`, `pinned` → `reorderPinnedPresets`. Another reorderable list is a row attribute plus one line in that table, not another gesture.
- **Preset order is user-set, and the pinned strip is a slice of it.** `state.presets` order is the order presets appear in the Library, the picker and on Home. Both lists are rearranged in a *mode* (`ui.presetOrder` on Library → Presets, `ui.pinnedOrder` on Home) rather than by a permanent grip handle, because the cards themselves are what you tap to start a workout and a handle on them would be one mis-tap from starting the wrong day. Home shows `presets.filter(pinned)`, so `reorderPinnedPresets` rewrites **only the slots the pinned presets already occupy** and leaves unpinned ones exactly where they sit — arranging your home screen must not shuffle the library behind it.
- **Deloads are planned, never inferred.** `state.deloads` is `[{id, start, end}]` with inclusive ISO dates, set by tapping two days on the Weekly Volume calendar. `deloadStatus()` decides what the home banner says: nothing, a countdown once the start is within `DELOAD_HEADSUP` days, then a day-N-of-M badge while it runs. The old five-hard-weeks radar is gone — it was guessing at something only the lifter knows.
- **A week is seven days from your start date, or the last seven days — the user's call.** `settings.weekMode` is `"program"` (default, and what every existing save migrates to) or `"rolling"`, read through `rollingWeeks()`. Program mode is the spreadsheet's: `weekOf()` counts from `settings.startDate` and every seventh day turns the page. Rolling mode replaces that with a *window* — `windowEnding(day)` — for lifters whose split simply comes round in order and for whom a Sunday and a Monday session are the same session. In rolling mode: the Volume tab reads `ui.volAnchor` (the LAST of its seven days, set by tapping a calendar day, stepped a whole window at a time by the arrows) and sums with `volumeInRange` instead of `volumeForWeek`; the Progress tab's bar chart uses `rollingSetBlocks` (seven-day blocks counting back from today) instead of `weeklyTotals`; and **the program-week chips disappear** from the header, the history day cards and the workout sheet, because in that mode there is no program week to name. `volumeForWeek`/`weekOf` are deliberately kept for program mode rather than expressed as a date range — `weekOf` floors everything before the start date into week 1, and a range would silently drop those rows. **Deloads are untouched by the setting** and must stay that way: they are dates the user put in the calendar, not something derived from a week number.
- **A volume bar is a promise of a target.** In the Weekly Volume list a group only gets a progress bar when the user has set a target for it (`state.volumeGoals`). Without one there is no bar and no grading — the old behaviour filled the bar against the biggest group trained that period and flagged others "Low", which made a bar move for reasons that had nothing to do with the lifter, and called a rest day a failure. An untargeted group instead states the one fact available without a plan: how the period compares with the one before it (`vol.more`/`vol.fewer`/`vol.same`). Don't reintroduce a default target.
- **The Weekly Volume calendar** (`renderCalendar`) layers three independent things on each day cell: a tint for the program week whose numbers are shown below, a dashed gold band for a deload, and dots for the muscle groups trained. Calendar maths is all ISO strings (`isoOf`, `monthOf`, `addMonths`, `monthGrid`, `weekRange`) built from local date parts, so a daylight-saving shift can't move a day.
- **`UNCATEGORIZED` is a bucket, not a group.** It is never in `state.groups`, and exercises land in it two ways: their group got deleted, or they were quick-added mid-workout and the muscle question was skipped (`pick.skipMuscle` → `quick-add-muscle` with the bucket as its `data-g`). Two list functions keep the distinction: **`libraryGroups()`** is what the user can *choose* (filter chips, the muscle dropdown, quick-add chips, the group manager) and never contains it; **`allGroups()`** is what must be *shown* (library sections, the exercise picker) and appends it last when anything is in it. It has no target control in the Volume tab, its name is refused in the group editor, and it disappears on its own once every exercise has been re-filed. Adding an exercise *from the Library* still requires a group — Skip exists because you were mid-set, not as a way to leave the form blank.
- **Numbers accept a comma or a period.** Every numeric field is `${NUM}` (a text input with `data-num`, not `type="number"`, which discards the "wrong" separator). `handleBind()` strips non-numeric characters and stores the value period-separated via `decimalize()`; the field itself keeps whatever the user typed. Add new numeric fields with `${NUM}`, never `type="number"`.
- **`migrate(s)`** — schema migration for `state` loaded from localStorage. Bump/extend this whenever the persisted shape changes, rather than assuming a fresh shape.
- **`render()`** — rebuilds the `#app` innerHTML from `state`/`ui` on every change. Sub-renderers per tab/screen (`renderHome`, `renderLog`, `renderHistory`, `renderVolume`, `renderProgress`, `renderCalc`, `renderLibrary`, `renderBody`, `renderTimers`, `renderProfile`, etc.) return HTML strings that `render()` assembles. `patch(p)` is the standard way to mutate `state` (shallow-merges, then persists + re-renders).
- **Event delegation, not per-element listeners.** Clicks are handled by a single `document.addEventListener("click", ...)` that dispatches on the closest `[data-action]` ancestor to the `actions` object (a big lookup table of action-name → handler, defined right before the click listener). Typed input is handled by delegated `input`/`change` listeners keyed on `data-bind` attributes, routed through `handleBind()`. When adding new interactive elements, follow this pattern (`data-action="my-action"` + an `actions.my-action` entry, or `data-bind="path.to.field"` + a branch in `handleBind`) rather than attaching listeners directly to DOM nodes — nodes are thrown away and re-created on every `render()`.
- **`data-stopprop`** marks elements (sheet backdrops, nested editors) where an outer `data-action` must not fire when a click lands on an inner one — see the click listener for the containment check.
- **Sheets/overlays** (`sheet()`, `fullScreen()`) are modal-style panels layered via `ui` flags (e.g. `ui.showProfile`, `ui.showBody`, `ui.workoutSheet`, `ui.entryForm`, `ui.groupSheet`) rather than routing. Body measurements is one of these windows, opened from the ruler button next to the header gear — it is not a bottom-nav tab.
- **Timers** run on their own interval engine (`startTimerEngine`, `sweepTimers`, `fireTimer`) independent of `render()`, with Notification API integration (`askNotifyPermission`, `notifyDone`). One timer can be on screen several times at once — its card on the Timer tab, and its round dial (`pinnedTimerDial`) both on Home and at the bottom of the workout and entry windows, where `renderTimerList()` repeats the same up-to-3 `pinnedTimers()` — so `paintTimers()` addresses every copy by `[data-tmr-time]` / `[data-tmr-ring]`, never by a single element id. Every dial carries the same pause/reset pair the Timer tab's cards have, wherever it appears; an *idle* dial has nothing to pause, so it stays bare and the row doesn't jump when one of three timers starts. Because those dials sit inside overlays, the timer editor sheet sits at `z-index` 120, above all of them.
- **Alert sounds are synthesised, never files.** `SOUND_LIB` is a dozen alerts written as note lists (`[start, freq, length, waveform, gain, glideTo?]`) that `playSound(id, volume)` schedules on the Web Audio context — no mp3s to download, cache, miss offline or license. **Sound and volume are per timer** (`t.sound`, `t.volume`, defaults `DEFAULT_SOUND`/`DEFAULT_VOLUME`, which live in the storage section because `seedTimers()` runs before the audio code is reached), edited in `renderSoundPicker()` inside the timer sheet, and read through `soundOf()`/`volumeOf()` so a malformed or missing value can never silence a timer. Volume 0 is a real choice and schedules nothing.
- **Charts** (`drawBarChart`, `monotonePath`, `niceTicks`) are hand-drawn SVG, no charting library. The progress line chart (`drawLineChart` → `paintLineChart`) is the interactive one: pinch/wheel zoom, drag to pan, tap a dot to open the entry behind it, and a fullscreen copy (`renderChartFull`). Its view (`ui.chartView`) and selection (`ui.chartSel`) live in `ui` so a re-render never resets them, in-flight pointer state is module-level (`chartPointers`/`chartGesture`) because a gesture redraws the chart underneath itself, and **every `[data-linechart]` of the same scope is painted from the same state** — the card and the fullscreen window are one chart drawn twice. Selecting a point deliberately patches `[data-linedetail]` in place rather than calling `render()`.
- **The graph does not stop at your data.** `ui.chartView[scope]` is `{lo, hi, yLo?, yHi?}` in *index* space (x) and *value* space (y), and `chartWindow`/`setChartView` deliberately allow it past both ends of the series — out to `chartMaxSpan(n)` and far enough either side that the history is nearly, but never quite, off screen. The empty space in front of the last session is the feature: a graph that ends at your best set reads as a ceiling. `yLo`/`yHi` absent means the vertical axis is still auto-fitting to whatever is on screen (`niceTicks`), which is what makes a zoomed-in plateau readable; a pinch or a vertical drag freezes it and hands it over (`ticksWithin`, which fits ticks *inside* a given domain rather than rounding the domain outward). Vertical dragging is fullscreen-only — the card in the tab has `touch-action:pan-y` because the page under it has to stay scrollable — which the paint reads off `data-chartfull` on the wrap. `chart-reset` (or a double-click) is the one way back to auto.

**There are two of that chart, told apart by scope.** `"main"` is the Progress tab's; `"ex"` is the copy at the bottom of the exercise detail window (`exWindowProgress`, fed by `exerciseHistory`), which can sit on top of the Progress tab. The scope is the value of the `data-linechart` / `data-linedetail` / `data-charttoolbar` attribute and the `data-scope` on every chart button, and it keys the series (`chartState.line` / `.exLine`), the zoom (`ui.chartView[scope]`), the selection (`ui.chartSel[scope]`) and which one `ui.chartFull` has blown up. Anything new that touches the chart has to carry the scope with it, or the two graphs will start redrawing each other.
- **The 1RM calculator tab** (`renderCalc`) is stand-alone: nothing it does is logged. Its maths is `calcPct`/`calcReps` at the top of `app.js` — the same anchored Wathan curve the log runs on, read forwards and backwards — and its tables are built from the *unrounded* max so they round exactly once. The curve flattens onto an asymptote near 49.6% of the max, so `calcReps` returns `Infinity` below that and the percentage table prints `30+` rather than inventing a rep count.
- **Compound vs isolation is gone.** An exercise's `type` is no longer offered anywhere in the UI; the only thing it still decides is whether a lift is logged in minutes (`isCardioEx`), and that now follows the *Cardio muscle group* — `cardioType(muscle)` stamps it on save. Old records may still carry `"Compound"`/`"Isolation"`, which nothing reads.
- **Theming** is entirely CSS custom properties (`--bg`, `--text`, `--gold`, etc.) swapped via `data-theme="dark"|"light"` on `<html>`, set by `applyTheme()` and mirrored by the anti-flash inline script in `index.html` (reads the last saved theme before first paint to avoid a flicker).
- **Images** (exercise thumbnails, etc.) are downscaled and re-encoded client-side in `readImageScaled()` before being stored, to stay under the localStorage quota — don't store raw uploaded file data.

There are two placeholder slots called out in the top-of-file comment (`PLACEHOLDER_BODY_GRAPH_SLOT`, `PLACEHOLDER_RANKS_SLOT`) marking intentionally-deferred features (body measurement graphs; ranks and strength standards, which own the Progress tab's second segment) — grep for these tokens before assuming a feature is simply missing.
