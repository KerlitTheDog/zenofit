# Git workflow

This folder is a git repo connected to https://github.com/KerlitTheDog/zenofit (branch `main`). The backend is a separate deploy: a Cloudflare Worker in `api/`, with its own D1 database.

**"Push" means SHIP IT — all of it, with nothing to come back and ask about.** When the user says push (or ship, or deploy), that is the whole release: commit, apply any new D1 migrations to the REMOTE database, deploy the Worker, run the smoke suites against production, and `git push` the front end. Do not stop in the middle of that to confirm the next step, and do not hand back a list of commands for the user to run. They said push; the job is done when the thing is live and verified.

**THE ORDER IS NOT ARBITRARY, and getting it wrong ships a broken app:**

1. `git commit` — local, so a failure below leaves nothing published.
2. `cd api && npm run migrate` — `wrangler d1 migrations apply zenofit --remote`. **Before the Worker**, because a Worker deployed against a table that does not exist yet is a 500 on every request that touches it.
3. `npm run deploy` — the Worker.
4. `python3 test/*.py` — all seven suites, against the live API (that is their default target). They create throwaway accounts and profiles in production and leave a few rows behind, which is the accepted trade for testing the real thing; see `api/test/README.md`.
5. `git push` — **last**, because this is what publishes the front end to GitHub Pages, and the app it publishes calls the endpoints that steps 2 and 3 just put there. Pushing first leaves a window where the live app calls routes that do not exist. This happened once, with chat, and it is the whole reason the order is written down.

Bump `VERSION` in `sw.js` whenever a shell file changes, or the deploy reaches phones on their *second* launch instead of their first (see the update-banner comment in `index.html`).

**What still stops and asks**, because neither is routine shipping:

- Anything destructive to git history — force-push, `rebase`, `reset --hard` — and never force-push over a rejected push.
- A migration that **destroys** data: a `DROP`, a `DELETE`, or an `ALTER` that loses a column. An additive one (new table, new column, new index) goes up without asking, which is nearly all of them. The distinction is the same one the rest of this file is built on: this app does not quietly overwrite somebody's training.

**What the suites cannot prove, so say so rather than implying it is covered:** push notification DELIVERY. `VAPID_PRIVATE_KEY` is a Wrangler secret and is absent from `wrangler dev`, so neither a local run nor the smoke tests ever send a real push — they exercise the routes around it. A change to the push path (`api/src/push.js`, the `push` handler in `sw.js`, `enablePush` / `notifyEnable`) needs a real phone, installed to the home screen, with the app backgrounded. The Notifications window's own *Test a rest timer, 60 seconds* is that test, run from inside the installed app.

Note: this local folder is the source of truth. Editing files directly on the GitHub website risks those edits being overwritten by the next push from here.

# Project overview

Powerbuild Tracker (product name "Zenofit") is a mobile-first powerbuilding/progressive-overload tracker: workouts, planned sessions, weekly volume, PRs, and body measurements. It's a **faithful port of a spreadsheet** ("AbsoluteMain.xlsx"): the header comment in `app.js` maps each spreadsheet formula to its JS equivalent (week number, muscle-group lookup, est. 1RM, cardio score, "vs. Your Best" badges, dashboard rows, weekly volume, deload radar, body trend). When changing any of that logic, check the comment block at the top of `app.js` for the spreadsheet formula it's meant to reproduce.

The one deliberate departure from the spreadsheet is the **1RM estimate**. The sheet used Epley, which reads a single at 30 kg as a 31 kg max; the app now uses Wathan's equation divided by its own one-rep value, so one rep is exactly the weight lifted (`rmCurve`/`est1RM`, with the reasoning and the formula bake-off written up in the comment above them). Everything downstream (best set, PRs, goals, the progress graph, the calculator tab, the set suggestions) reads that one curve, so it is the only place to change it.

**The formula is a code detail, not a caption.** The bake-off, the comparison with Epley and the name "Wathan" belong in that comment and in exactly one place in the UI: the *Estimated 1RM* accordion in Home → How this works (`acc.rm.body`). Nowhere else in the interface says anything about it: not the calculator's result line or footer, not the entry form, not the set editor. There is no longer even an "exact at 1 rep" caption beside the number, because nobody logging a set of eight needs to be told what the curve does at one rep. Don't add a caption when adding a surface that shows an est. 1RM; the label and the number are the whole thing.

It's a installable PWA (see `manifest.webmanifest`): standalone display, portrait-locked, with home-screen install providing real orientation lock on Android and enabling timer notifications on iOS.

# Home → How this works

The accordion stack at the bottom of Home (`acc.*` in `i18n.js`, wired in `renderHome`) is a **reference, not a tour**. The test for whether something belongs there is: *does the app fail to answer this by being tapped?*

- **In:** rules that decide what happens to someone's data or what a number means: what counts toward PRs and volume and what is silently dropped, that a preset saves exercises and never numbers, that units live per-exercise and history is never rewritten, that a parked day counts for nothing until saved, that a plan counts for nothing until the day is actually logged and what a preset is instead, that there is no volume bar without a target, why the est. 1RM can hold still on a session that went well and where that improvement is shown instead, where the data physically lives and what can destroy it.
- **Out:** narration of the interface. Nobody needs to be told that ＋ adds an exercise, and the same sentence volunteered *mid-set* is noise. That is the standing complaint behind both this section and the removal of the 1RM caption.

Titles are questions a user would actually ask, so the collapsed list works as an index; a collapsed accordion costs one row, so being specific is cheaper than being comprehensive in fewer sections. Keep bodies tight, and when a feature changes, fix the copy here in the same commit, since this section going stale is how the app starts lying about itself.

# Running / testing

There is no build step, package manager, or test suite: this is plain HTML/CSS/JS loaded directly by the browser. To work on it, just open `index.html` (or serve the folder with any static file server) and reload after edits. There's no linter or formatter configured; match the existing style in the file you're editing.

# Architecture

The app itself lives in five files: `index.html` (shell + theme-flash-prevention inline script), `styles.css` (all styling, theme-driven via CSS custom properties), `i18n.js` (every string, in three languages), `standards.js` (pure data: the StrengthLevel strength-standards tables), and `app.js` (the entire application). Beside them, `zenofit-cloud.js` is the only code that talks to the network and `api/` is the Cloudflare Worker it talks to (accounts, sync, push, timers, chat) — both optional by design: the app runs unchanged with the API unreachable.

**Every dimension that answers to the device goes through the viewport engine, and nothing else measures the screen.** `applyViewport()` in `app.js` (the VIEWPORT ENGINE block above `render()`) is the only code that reads the device: it writes `--pb-scale` and `--pb-frame-w` onto `<html>`, and the matching block in `styles.css` derives everything else from them: the frame's height, the safe-area insets in the frame's own units (`--pb-sat` / `--pb-sab`), and the chrome measurements stacked on the bottom nav (`--pb-nav-h`, `--pb-header-pt`, `--pb-content-pb`, `--pb-fab-b`, `--pb-toast-b`). Three rules keep it honest:

- **Never write a raw pixel offset against the top or bottom of the screen again.** A top bar's first padding is `var(--pb-header-pt)`, not `14px`; anything sitting above the nav is `calc(<clearance> + var(--pb-sab))` or one of the `--pb-*-b` tokens. Those numbers are what the notch and the home indicator are subtracted from, and a hand-written `14px` is a control the user cannot reach on a notched iPhone, which is exactly the bug the engine was written for.
- **A phone renders at scale 1, by design.** The frame takes the full width it is given up to `--pb-fluid-max` (480pt) and only scales past that, so every handset draws the design at the size it was authored at; scaling exists for tablets and desktops, which are the only screens wider than that. If you change `VP_FLUID_MAX`, `VP_REF_H` or `VP_SCALE_MAX`, you are changing what happens on a tablet, and you should check a phone anyway.
- **A pinned footer's clearance is MEASURED, never written down** (`fitScrollFooters` / `FOOTER_CLEAR`, and the `data-footer-for` on the footers in `renderWorkoutSheet` and `renderEntryFields`). Both of those screens park their save button over a scrolling list and fade the list out under it with a gradient, and the clearance the list got underneath was a hand-written `120px` — the same species of raw offset as the rule above, just aimed at a piece of chrome instead of at the notch. It is right for a footer holding one button and wrong the moment it holds more: the workout sheet's grows by *Save as preset* and up to two lines saying what is still unlogged, copy that WRAPS, so the right number was never a number at all. Past 120px the bottom of the list came to rest under the *transparent* top of that gradient and the caption printed straight across the timer dials' labels. The footer now declares the list it sits over and its height is read off the element after `lucide` has drawn the icons — with `flashLogDay`, for the reason stated there: the glyphs settle the final heights. **This measures CONTENT, not the device**, which is why it is not in `applyViewport` and does not divide by `vpScale`: `offsetHeight` and the padding written back are both in the frame's own units, so the scale cancels, and the safe-area inset is already inside the height because the footer's own padding carries it. The `120px` still in the templates is what one pre-measure paint uses and nothing else; a third screen in this shape is an attribute, not another guess.
- **Pointer coordinates arrive in screen pixels; the frame is laid out in its own.** Anything doing arithmetic between an event's `clientX`/`clientY` and a laid-out size (`offsetHeight`, `clientWidth`, an SVG coordinate) has to divide the event side by `vpScale` first, see `moveRowDrag` and the chart gesture handlers. On a phone this divides by 1 and on a tablet it is the difference between a drag that tracks your finger and one that does not.

# Languages

English, Українська and Svenska. `i18n.js` holds `UI[lang]` (all interface copy, keyed by dotted name), `EX[lang]` (the 41 built-in exercises as `[name, equipment, alternatives, note]`, in the same order as `DEFAULT_LIBRARY`) and `STD_EX[lang]` (the 71 strength-standards lifts, keyed by **slug** rather than by position, because that list is data the app doesn't own and a row in it could move). English lives in `UI.en`, in `DEFAULT_LIBRARY` and in `STD_EXERCISES` itself. `T("key", vars)` looks a string up and falls back to English then to the key, so a partial translation is always safe; `TN("day", n)` picks plural forms (one/other for en+sv, one/few/many for uk). Long copy carries its own `*bold*` and `_italic_`.

Adding or removing a language means editing `LANGS`, `LOCALES` and the matching `UI`/`EX`/`STD_EX` blocks. `resolveLang()` coerces anything not in `LANGS` to English, so a saved setting for a language that has since been dropped degrades quietly, and `migrate()` rewrites it on load.

**The rule that keeps data safe: translations are display only.** Everything persisted stays in English, because those strings are identity: a log entry points at `"Bench Press (Barbell)"`, a goal is filed under it, an exercise sits in the group `"Chest"`. Switching language must never orphan a logged workout. So:

- `exLabelOf(ex)` / `exLabel(name)` / `exFieldOf(ex, field)` translate built-in exercises via their stable `default-N` id; a custom exercise, or a built-in field the user has edited, is shown exactly as typed. **That includes the name**: `exLabelOf` translates a built-in only while `ex.name` is still the shipped one, so a lift the user renamed reads back as theirs in every language. And because the edit form is prefilled with the LABEL, `actions["exwin-save"]` treats a name typed back exactly as it was shown as untouched, or a built-in opened in Svenska and saved for its colour would freeze into Svenska.
- **Renaming an exercise is a cascade, not a field edit, and the cascade is `renameExerciseIn`.** The name IS the identity, so a rename carries through `log`, `plans`, `dayDrafts`, `unlogged`, `presets` and `goals`, plus the open workout sheet, the open entry form and `ui.progressSelected`, exactly as `actions["group-save"]` does for a group. Writing it into the library alone left every one of those pointing at a lift that no longer existed: the session still rendered in the day, and opening it found nothing to edit. **The sweep lives in that one function and anything added later that stores an exercise name is added THERE, not at a call site** — it used to be inline in `exwin-save`, which was fine while there was one way to rename and became a second copy waiting to drift the moment `reparentUnder` needed the same move. It folds into a *patch object* rather than committing, so re-parenting a family can rename several rows in one write with each reading what the one before it left. A name already in the library is refused rather than merged, since two rows under one name is the same desync arrived at from the other end.
- `groupLabel(name)` translates a group while it still carries a `key` **and still wears the name we shipped it under** (`DEFAULT_GROUP_NAME`); rename it and it reads back as typed, in every language, exactly as a renamed built-in exercise does. **The key is identity and rides through a rename**, which is the whole point: it used to be dropped to stop "Pecs" coming back as "Chest", and that threw the group's identity away along with the claim about its name. Same trick for seeded timers (`timerLabel`, `key: "rest"`).
- **A group declares WHAT IT IS FOR, and the name is just a name** (`KIND` at the top of `app.js`, `groupKind` / `exKind` / `kindOf`). The Cardio group used to be identified by being called "Cardio", so calling it "Hell" broke the form. Four kinds now: **strength** (sets of reps × weight), **bodyweight** (sets of reps), **hold** (sets of seconds), **cardio** (minutes × effort). A kind earns a place in that table only by passing both halves of one test: **it changes what you write down, AND it has one axis on which more is unambiguously better.** The second half is the strict one — the PR badge, the graph, beat-last-time, the set verdicts and the suggestion card all need a direction to point in. Two shapes people ask for fail it and are deliberately absent: **rounds**, where "5 rounds for time" wants less time and "AMRAP 20" wants more rounds, and **distance**, where a longer run and a faster run are both better. Neither is hard to store; both would make the app decide what you meant. Don't add them without solving that first.
- **Everything that differs between the set-shaped kinds is three questions**, and every call site asks one of them rather than testing the kind: `setHasData` (is it filled in), `setScore` (what is it worth), `setLine` (how is it written). `sets: false` is the real fault line — cardio is the only kind not logged set by set, which is why so much of the app reads `kind === "cardio"` and stays correct, and why bodyweight and hold got the set list, dropset chains, ghost rows, last-time verdicts, PR badges, the graph and sets-per-week for free. `metricOf` is the converted, cross-session number and `setScore` the raw one you read back; `metricUnit` / `metricLabel` name it, since "est. 1RM" is a claim only the strength curve gets to make.
- **The kind lives at three levels, and only two of them store anything.** A group ALWAYS carries one. An exercise carries one only while it is an EXCEPTION to its group (`withKind` writes it, `exKind` reads it): **absent means "whatever my group is for"**, which is what makes filing a lift under a cardio group make it cardio and what carries a group's exercises along when the group is re-declared. v13 stamped a kind onto every row instead, which made the group setting inert — every exercise already had its own answer and never asked — and v14 undoes that, keeping a stamp only where it disagrees. Tapping the group's own option in the exercise editor CLEARS the exception rather than setting one. An entry, by contrast, has its kind frozen on it when logged: **re-declaring anything never reaches back into the log.** That is also why the seeded pull-ups and plank are still strength — flipping them would change the form under everyone who already has reps × weight on record for them.
- **A lift is READ in the kind it is logged in today, and only sessions in that kind are compared** (`readKind`, and the kind filter in `earlierOutings`). Change what an exercise is logged in and its old sessions do not change with it, which leaves two sets of numbers under one name; a rep count is not a kilo. So the graph, the best-ever, the PR flags (`computeBadges` keys on lift AND kind), the Progress row, the suggestion card, "last time" and the set verdicts all read one kind only. **The older sessions are still listed** in the exercise window, labelled with how they were logged and carrying no number or badge, with a line saying how many are off the graph: they happened, and a ledger that hides them is worse than one that labels them. Presets follow the same rule — `presetToEntries` takes the kind from the LIBRARY, never from the copy stored on the preset — and a plan hands over its target only while it still fits the lift's current shape (`planTargetUsable`).
- **Volume counts cardio in minutes and everything else in sets, and never adds the two together.** `volumeForWeek` / `volumeInRange` return `{sets, minutes}` per group. A group is free to hold both (declare it cardio and make one lift an exception, or the reverse), and summing them produced "32 sets" out of two sets and half an hour on a bike. The group's own kind picks which figure is THE number — the one a target grades and the one compared with last period — and the other is shown beside it when there is any of it. They also land under the entry's OWN group: filing every cardio entry under the literal key `"Cardio"` put a session done in "Hell" somewhere else entirely.
- **Search reads the label as well as the stored name** (`exMatches` / `exIsNamed`). Filtering on `ex.name` alone meant the library search and the exercise picker found nothing at all in Ukrainian or Svenska, and the picker, seeing no exact match either, then offered to add a lift you already had under its translated name as a second row keyed by a name nothing points at. Any new search over exercises has to try both. **`nameMatches(name, q)` is the same test where all that is to hand is a stored NAME** rather than a library row — a dashboard row, a log entry — and it is what the Progress tab's *Your lifts* search runs on. That search **filters the list and nothing else**: the selected lift is worked out from the whole list before the filter runs, so typing never moves the graph out from under you, and the dropdown above the graph still offers every lift, because narrowing a control that owns the selection would leave the lift on screen missing from the only thing that can change it. Tapping a result is what moves the graph, as tapping a row always has.
- **`data-*` attributes are lookup keys and must carry the stored English name**, never a label. Translating one silently breaks the click handler that resolves it.
- Dates go through `fmtDate`/`fmtShort`, which use `localeTag()` so they follow the app's language rather than the device's.

**`app.js` is a hand-rolled single-file SPA framework**, with no React/Vue/build tooling. Key pieces, in the order they appear in the file:

- **`DEFAULT_LIBRARY`**: the seeded exercise library (name, muscle, kind, equipment, alternative, cue notes), ported verbatim from the spreadsheet's Exercise Library sheet.
- **Pure calculation helpers** (`bestSet`, `syncEntry`, `computeBadges`, `dashboardRows`, `weeklyTotals`, `volumeForWeek`, `deloadRadar`, `bodyTrend`, etc.): these are the spreadsheet-formula ports; keep them side-effect-free.
- **`state`** (persisted) vs **`ui`** (transient, in-memory only): two separate global objects. `state` holds workout log, library, muscle `groups`, presets, timers, goals, body measurements, `dayDrafts`, settings; it's loaded via `loadState()`/`migrate()` and written to `localStorage` under key `powerbuild-tracker:v1` via `persist()`/`writeNow()` (debounced autosave, flushed on visibility change / pagehide / beforeunload). `ui` holds open sheets, form drafts, filters, etc., and is never persisted directly, but in-progress drafts (open workout sheet, entry form, set form, body form) are snapshotted into `state.drafts` so a killed/reloaded tab restores exactly where the user left off (see `snapshotDrafts()` and the `restoreDrafts` IIFE at the bottom of the file).
- **Three stores hold a day that is not (all) history, and they are not the same thing.** `state.drafts` is the crash/lock snapshot of whatever form is open right now. `state.unlogged` is what a SAVED day left unfilled (see the bullet below). `state.dayDrafts` is deliberate: backing out of a half-built workout parks the whole day there (`closeWorksheet()`/`stashDayDraft()`), it renders above the history in the Log tab, and nothing in it counts toward sets, PRs, volume or the charts until the day is actually committed. **There is only ever one workout for today**, which is what `actions["log-exercise"]` (the Log exercise button in the exercise detail window) has to respect: it opens the sheet you already have open, else today's parked draft `draftId` and all, else a fresh day (it never starts a second one) and then drops straight into that exercise's entry form. It is a shortcut past New Workout → Add exercise → find it in the picker, not a second way to write to the log. **A parked day is written by `stashDayDraft` and read by `sheetFromParked` / `sheetForDay`, and by nothing else.** Four buttons pick one back up — *Continue* in the log, *Log this day* on the calendar, *Start* on a plan, and *Log exercise* in a lift's window — and each used to spell the same object literal out by hand. They drifted, which is the one thing four copies reliably do: the fourth never carried `planIds`, so a day started from a plan and then picked up from an exercise window came back not knowing which plan it was answering, `prunePlans` had nothing to consume on save, and the plan went on reading as *unused* on its own day forever with no way left to clear it. So **a field added to a parked day is added in those two functions, not at a call site**, the same rule `renameExerciseIn` states for everything that stores an exercise name. Both COPY `planIds` rather than hand the array over, because `plan-start` pushes onto the open sheet's list and a shared array would edit the store through the back door.
- **Set suggestions are built on last time, not your best ever** (`setSuggestion`, and the `SUG_*` constants above it). The card at the top of the entry window, above *Add set*, deliberately, because that window is where you decide what to do while the set editor is where you write down what you already decided, offers two ways past the previous session's best set: one more rep at the same weight, or the smallest real weight step (`weightStep`) at the same reps. Holding the reps on the heavier option is deliberate: dropping reps as weight goes up is normal training but would not raise the estimate, and the card only ever offers something that scores higher (every option is filtered through `metricFor`). **Neither option is recommended over the other**: they render identically, and `bySmallestStep` only ranks them by the one thing the app can compute exactly: which raises the estimate least, tagged `sug.smaller` (and tagged on neither when they tie). That lands on the extra rep in the 8-12 range and on the extra weight down on heavy triples, where one more rep is worth far more than a plate. This replaced an inferred double progression that was broken twice over: mechanically (the rep ceiling was a median of a window including last session, so "you're under your range" required your reps to have just *dropped*, which following the app could never cause, making the answer "add weight" forever) and in principle (**a rep range is an intention, and the log only records what you did**, and crowning an option on a guess about someone's programming is the same mistake as a progress bar filling toward a goal they never set). If you reintroduce double progression, it has to run off a range the user actually set, not one read out of their history. The set editor shows the same two buttons, minus whichever the open set already *is*. **Under that card sits `renderLastTime`, the session it is arguing from, set by set** (`lastOuting`). The card names one set because that is the bar it offers two ways over, but four sets that fell apart and four that held share a best set and were not the same day’s work, and it is the second and third you are stood there trying to match. Read-only (everything else tappable in that window puts a number in the log) and in the unit each set was *logged* in, never converted; it renders under a plan target too, since a plan does not make last time less worth knowing. **Both are tap-to-load, never auto-filled**: the log records what you did, never what the app hoped you would do.
- **A new set opens on the set that stood in its place last time** (`openingSetFor`, read off the same `lastOuting` rows the panel above draws). Set three opens on last week's third SET — by chain coordinate, so never on the drop that happened to be third in the list — converted into the unit this entry is being logged in, and *Drop* says so on the way in (`asDrop`) so it is offered last week's drop rather than last week's set. It used to open on the set above it, which is right exactly once (the first set, where there is nothing above) and wrong from the second onward: somebody working up 60/80/90 was handed 60/60/60 and retyped two thirds of their own session. Past where last time ran out it falls back to the set above, which is that old behaviour and the only honest guess left, and with no history at all it opens blank. This is a starting point in an editor, not a number in the log (nothing is written until the set is saved) so it does not violate the tap-to-load rule above, which is about the app never *committing* a number a finger did not put there. The suggestion card still overrides it, because taking the card is a decision and the default is only a guess.
- **Unticking a set is an edit, not a refusal, and a not-done row stays in the log.** `entryOnRecord` says whether the entry in the window is already a record: a card in the open day sheet (`isDraft`) *or* a row in `state.log`, which is what the Log tab opens when you tap a history row. Anything on record may be emptied and saved again (the button relabels to `entry.saveNotDone`) because unticking is someone taking back a claim about their own training and the app has no business refusing to write that down. Nothing is turned away any more: a brand-new entry with nothing in it is a lift *lined up* for later (see the bullet below). Both routes into that window must stay covered; for a long time only the sheet one was, and the Log-tab route silently greyed out at exactly the moment it was needed. The row that comes back is blank but **keeps its `plan`**, so the lift reads as planned-and-not-done, the day chip drops to 0/n, and the ghost rows are still there to tick again later. That means **`state.log` can contain entries with no numbers on them**, which is a real invariant to hold: `earlierOutings` filters them out (a not-done row is not a session you had, and leaving it in let it become the "last day you trained this" and come back empty, hiding the real one behind it), and anything rendering a row has to guard `entrySummary` with `entryHasData`. Note `commitWorkout` still drops blanks when a whole *day* is saved, and there the same lift reverts to the plan via `prunePlans` instead, which reads the same way to the user and is why both are "planned, not done".
- **A lift can be lined up with nothing in it** (`lineUp` in `entryComputed`). The entry form used to refuse a brand-new entry carrying no numbers, on the grounds that a blank row is a row nobody asked for. That was wrong about who was asking: halfway through the hamstring curls you decide the calf raises are next and you want them on the day NOW, with the numbers to follow. Being made to type 1 rep at 1 kg to get past the button and correct it afterwards turns a note into a false record. **This is not a plan**: a plan is a dated intention that can sit in the calendar for weeks and is counted by nothing, while a lined-up lift is a card in the day you are training right now and becomes an ordinary logged lift the moment you fill it in. `commitWorkout` still drops whatever is blank when the DAY is saved, so a lift you lined up and never did leaves no empty row in your history, and the sheet's footer already says so before you save.
- **Supersets and dropsets are the same idea at two levels** (`isDrop`/`isSuper`, `linkMarks`, `dropMarks`, `superMarks`). A dropset is one exercise straight into a lighter set of itself; a superset is one exercise straight into a different one. Both are a single boolean on the item that CONTINUES the one above it: `set.drop` and `entry.superWith`. **Nothing stores a group id**, deliberately: an id is a second source of truth about an order the list already knows, and both lists are draggable, so the two would start disagreeing the first time somebody rearranged one. Runs are read upward from the order instead, a mark on the first item means nothing and is ignored, and deleting or reordering silently reshapes the runs into whatever the new order says. `commitWorkout` clears a link left stranded on what became the day's first entry, which is tidying the record rather than fixing a read. **Neither does any arithmetic**: no volume multiplier, no intensity adjustment, no fatigue discount. A drop is a set and counts as one set; a supersetted lift is a lift. est. 1RM, PRs, weekly volume, the graph and the last-time comparison all read exactly what they read before, because the app does not know what a dropset is worth and neither does anybody else. They say what you DID, which is the only claim the log is allowed to make. Drawn as an indented chain off the row above, with the label on the head of a run only, in the set list, the day sheet and **every surface that reads a session back**. That last part was a claim this file made and the code did not keep: `outingRows` dropped the flag on the way out, so the three sets you logged as a dropset came back a week later in *Last time* and in the exercise window's ledger as three ordinary sets, indistinguishable from three separate efforts. The flag now rides on the row (`drop`, read upward from the order so a set that opens an entry can never continue the last set of the entry before it) and `dropMarks` draws it in all four places. Where the reading is a row (`renderLastTime`) it is the same indent and arrow the editor uses; where it is a *chip* that wraps (the exercise window's ledger, the chart's point detail) the chip takes the chain's arrow in place of its number and the chain's colour, which is the same sentence in the space a chip has. **AND A DROP IS ONLY EVER MEASURED AGAINST A DROP** (`chainKeys` / `chainKeyAt`, read by `outingRows`, `lastTimeSets`, `entryLastResult`, `openingSetFor` and `lastSetMetric`). Everything that holds today against last time used to match by ROW NUMBER, which is right until one of the two rows is a dropset and is then wrong in the direction that flatters you: 8 x 80, 9 x 70, drop to 6 x 60 last week, and a third real set of 6 x 60 today reads as a MATCH — a full set graded against a burnout set taken with no rest. A set is addressed by where it sits in the order of EFFORTS instead: `chain` counts the real sets (a drop does not open one), `pos` counts how deep into a chain it is, and `chain.pos` is what the two sessions are matched on. A normal set is always `pos 0` and can only meet another normal set; the first drop off your second set is `1.1` and can only meet last week's first drop off its second set. No counterpart means UNJUDGED, which is the answer the app already gave a fourth set on a day that had three, and `extra` counts those as bonus sets. The key is computed from the order every time, never stored, so rearranging the list reshapes it — the same rule the marks live under — and `chainKeyAt` works out the key a set WOULD have so the two Add buttons can ask before the set exists.
- **A profile is a whole `state`, and there are several of them** (`loadProfiles` / `switchProfile`, Settings → Profiles). Trying a different block without giving up the one you are in, or logging for somebody whose phone is at home, needs a second everything: log, library, groups, presets, timers, goals, body, plans, settings. So a profile IS a state, the same object the backup file carries, and switching swaps it whole. **Storage is one small list per ACCOUNT plus one key per profile** (`powerbuild-tracker:roster:<userId>`, `powerbuild-tracker:state:<id>`) rather than all of them under one key, because every save rewrites its key and localStorage is a few megabytes with exercise photos already in it: writing four profiles because one gained a set would be four times the quota risk on every debounce. Export and Import act on the profile you are in, unchanged, since `state` is still `state`.
  - **A PROFILE LIST BELONGS TO AN ACCOUNT, NEVER TO A PHONE** (the PROFILES block: `readRoster` / `saveProfiles` / `signedInAs`, `profiles.userId`). There used to be one list per device, read by every account ever signed in on it, and that one fact produced every roster bug on record: another account's profile in your list, a sign-out that left a list for whoever came next, a sign-in that uploaded somebody else's training. Now logged in, `profiles` is that account's list and nothing else; **logged out it is EMPTY and the whole app is the login screen** (`renderGate` → `renderLoginGate`, early in `render()`); logged in to an account with no profiles, it is `renderNoProfiles` (name a first one, join a shared one, Storage check, log out). Log out of one account and in to another and you get the second account's list, never a merge; log back in to the first and its list is there instantly with no signal needed, and the roster brings it up to date. **Nothing is deleted from the disk by logging out** — the state keys and the account's list stay, reachable only through Storage check behind that account's password. `migrateDeviceList` moved the old device-wide `powerbuild-tracker:profiles` once: linked profiles to the account their record names, never-uploaded ones with content to whoever was signed in, the first-run blank deleted, and everything else (sync turned off, signed out) into no list at all, for Storage check.
  - **THE LIST ITSELF IS ACCOUNT DATA, NOT DEVICE DATA** (the ROSTER block in `app.js`: `rosterSync` / `rosterPushOrder` / `dropLocalProfile`, `profiles.position` and `profiles.name_updated_at` in migration `0005`, `GET /v1/profiles` and `POST /v1/profiles/order`). `profiles` on the server IS the roster, and every device builds the account's list from it and pushes its own changes back, which is the deal the items inside a profile have always had, one level up. Every pass ends with this device's list matching the account: what the account has is fetched, what was made here goes up, what left the account leaves the list. **Every await in `rosterSync` re-checks `stillMe()`**, because a pass that outlives a log-out would file one account's listing under the next account's list. **What stays local, deliberately: which profile you are LOOKING at** — that belongs to the person holding the phone, and syncing it would mean opening a laptop changed what the phone was showing mid-set.
  - **LOGGING IN ASKS BEFORE IT MAKES AN ACCOUNT** (`login-go` / `login-create`). One form, and it always tries to log in first; only a refused login whose name is really free (`/v1/auth/available`) offers to create it, as its own tap, because a typo in your own username ("testng1") used to become an empty new account on the spot, which looks exactly like every profile having vanished. **Logging out sends first** (`flushAccount` → `accountUnsynced`, counted the way a push would count: rows whose hash moved, marks whose row is gone, a profile not yet in the account, a queued removal, an unsent rename) and the confirm says how many changes could not go and that they stay on the phone. `enterAccount` / `leaveAccount` are the one place a change of account is handled; `restoreDrafts` is a named function because entering an account puts that account's half-typed forms back too.
  - **YOURS, OR SHARED WITH YOU, AND NOTHING ELSE** (`profileShared` / `profileShareLine` / `sharedLast`). The Profiles screen and the account sheet draw two groups: *Your profiles* and *Shared with you*, each shared row naming whose it is and the level (`ownerName` comes from the server's `LEFT JOIN`). The rows used to carry a line about where each profile physically was — on this phone only, backed up, synced but not to this account, get it — which described machinery and read as a list of faults; that is gone, and so is every cloud icon. Your own profiles are always ahead of shared ones in the stored order (`sharedLast`, applied by the roster and by `reorderProfiles`), so the list and the screen cannot disagree about where a row is. On a shared profile the red button is *Remove from my profiles* (leave), never *Delete*.
  - **Offline is untouched, which is the only reason this is safe.** Nothing in the roster is on the path of anything the app does: a profile is still a whole `state` under its own key, a set is still written to disk the moment it is typed, and every roster call fails soft and retries on the next pass. Train for three hours in a basement and the list reconciles itself when the signal returns, exactly as the log does.
  - **There are exactly two ways two devices can disagree, and both are settled without inventing anything.** A NAME carries the moment it was typed (`nameAt` locally, `name_updated_at` on the server) and the later one wins — not the last device to reconnect, which would let a phone coming back from a week in flight mode silently undo yesterday's rename on the laptop. A rename refused as stale comes back **200 with the name that won**, not an error, so the client takes that as the answer instead of retrying forever. The ORDER is whatever the server says and dragging pushes it (`reorderProfiles` → `rosterPushOrder`, one call for the whole list because a drag renumbers every row after the one that moved); positions the server never set sort **last**, so a list that predates all of this does not shuffle itself.
  - **Adoption is automatic and so is enrolment.** A profile in the account that this device does not hold becomes a local profile (a read grant arrives live, as joining one does); a profile in this account's list with no link yet — made here, often with no signal — goes up the next time there is a connection (the poll, coming back to the app, and the `online` event). Nothing outside the signed-in account's list is ever looked at, so there is no first-run-blank exception and no "signing in adds this phone's profiles" any more. When anything goes up the whole order is pushed (`rosterPushOrder`), because a new position can tie with an old one and the server and the phone break ties differently.
  - **Removal takes a profile out of the list and leaves the save on the disk** (`dropLocalProfile`). A profile deleted on one device leaves the account and therefore every device's list — that is what "the same everywhere" means — but its key stays, so Storage check still has it. An **empty** one is removed key and all, because a trail of blank keys is how that screen stops being worth reading. A removal only ever acts on a profile a listing has confirmed present before (`rec.seen`), so a listing that predates a join cannot delete what it has not heard of yet. **The list CAN end up empty** — it used to keep the last profile even after the account had lost it, which is precisely a profile in the list that is not in the account — and an empty account gets the no-profiles screen. Deleting your last profile by hand is allowed for the same reason.
  - **REMOVING A PROFILE IS A PROMISE, NOT A REQUEST** (`queueRemoval` / `runPendingRemovals` / `zenofit:pending`, and `DELETE /v1/profiles/:id/grants/me`). A removal is queued, survives being closed, is drained at the top of every roster pass, and only leaves the queue when the server agrees — or answers 404, which is the same thing said differently. **Each entry carries the account that made it (`acct`) and is only ever sent as that account** (`pendingMine`): a delete made offline, followed by logging in as somebody else, used to go out with the second account's token, get the 404 that "not yours" earns, and be dropped as done. Adoption skips anything queued, or the next pass would helpfully undo the delete.
  - **Two verbs, because "not in my account any more" is two different facts.** Yours is DELETED and tombstoned for everybody; somebody else's is LEFT, which revokes your own grant and touches their profile not at all. Sending the wrong one is what made this local-only: `deleteProfile` went out for anything not marked "read", so a WRITE grant got a delete the server rightly refused as not-yours into a `.catch` that said nothing, and a READ grant got no request at all. Either way the grant survived, the profile stayed in the listing, and the laptop kept its copy of something deleted on the phone hours earlier. `owned` is refreshed from the listing's `isOwner` on every pass and is the only thing that decides which verb goes.
  - **A profile you only READ wears its owner's name.** Renaming one locally was allowed and went nowhere — the server will not take a name for somebody else's profile — so one profile read "Em" on the phone, "Profile 1" on the laptop and "Profile 1" in both account sheets. Three names for one thing, on a screen whose whole claim is that the list is the same everywhere. A read grant now follows the owner's name, and `profile-form-save` refuses the rename rather than accepting one it knows it cannot keep.
- **A save that will not OPEN must never become a save that gets replaced** (`unreadable` / `allowOverwrite` beside `readProfileState`, checked in `writeNow`). This was the one way the app could destroy a training history entirely by itself, with no bug anywhere else: a stored state that would not parse — a write cut off by a dying battery, a browser truncating under quota — came back from `readProfileState` as `defaultState()`, the app came up blank and perfectly happy, and the very next autosave wrote that blank over the only copy. One bad read, permanent loss, no warning. Now a key that is THERE and will not parse poisons the WRITE instead: `unreadable` holds that profile's id, `writeNow` returns without touching its key (saying so once, the way the quota warning does), and the bytes stay exactly where they are for Storage check to hand back out — it lists one as DAMAGED and exports it raw. **A MISSING key is not this**: a first run and a new profile have no key and must not be flagged, or nothing could ever be saved. The app still runs rather than refusing to open, because a locked-out user cannot reach the screen that rescues them. The lock is deliberate, not absolute: `importBackup` and `reset-all` call `allowOverwrite()` because both are the user saying "replace what is there" out loud, behind a confirm. What is forbidden is the app deciding that quietly on their behalf — so anything added later that can write a whole profile belongs on that short list, and nothing else does.
- **An app whose only copy is one origin's localStorage owes its user a way to look at that** (`storageScan` / `adoptStorage` / `renderStorage`, Settings → Data → Storage check). When the app comes up empty, three very different things look identical from the inside: the data is gone, the data is fine but this is not the address it was saved at, or the data is fine and right here while no list names it. So the screen reads **every** Zenofit save, says how much training each holds and whose account it belongs to (`zenofit:owners`, written the moment a profile joins a list, plus every account's roster key), and prints the origin first. **It is a back pocket, isolated from the rest of the app**: nothing outside the screen reads what it finds (the account sheet used to list every save on the phone, and that is how one account's training kept surfacing in another's list), and nothing it finds goes anywhere unless somebody presses Recover there. **It is locked per account** (`storLocked` / `storAskPassword` / `renderStorUnlock`): Recover, Export and Share on a save belonging to another account ask for that account's password, checked by `POST /v1/auth/verify` (login's check without minting a token), and remembered only for that visit to the screen. Saves of the account you are in, and saves no account ever owned, open without asking. **The lock is a door, not a safe** — the bytes are plain JSON and developer tools can read them; the comment above `STATE_PREFIX` says so and describes the stronger version (encrypt on logout with a key derived from the password) and its catch. **Recover only ever ADDS, and always into the account logged in now**: a save no list names is put in this account's list; one still in another account's list, or the legacy key, is COPIED to a key of its own; recovering another account's save warns in as many words that it belongs to them. What lands has no link, so the roster puts it into the account as a new profile. **Every row also carries Export, and Share where the platform takes files** — damaged saves included — and `storageFileFor` reads and nothing else, because a full store is exactly when Recover cannot finish and the file matters most.
- **Switching is a bigger event than it looks.** `ui` is full of things belonging to the profile being left — an open workout, a half-typed set, a chart selection — so `closeEverything()` clears the screen back to Home rather than leaving it pointing at rows that no longer exist, and an open day is **parked first** (`closeWorksheet`, the same back-out its own arrow does) so it is waiting in the Log tab rather than living on invisibly inside the crash snapshot. Every profile operation flushes with `writeNow()` before it touches anything, because `state` is only written on a debounce. With no profile open (`profiles.active === null`: logged out, or an empty account) `writeNow` writes nothing, since the `state` the gate sits on belongs to nobody.
- **A variation is a library row of its own** (`variantOf` / `variantName`, `exWindowVariations`). A wide-grip pulldown and a close-grip one are the same movement and not the same lift: the weights differ, and averaging them into one history describes neither. So each gets its own row, its own log, its own best set, PRs and graph, and everything downstream keeps working because everything downstream only ever knew about library rows. What the link buys is the two things separate rows cannot do for themselves: they are **shown together** (nested under the parent in the library, listed in each other's window), and **the label is composed live** — `exLabelOf` builds "Pulldown · Wide grip" from the parent's current label, so renaming the parent re-labels every variation at once while not one stored name moves. Stored name is identity and must never shift under the log; the label is display, exactly as it is for a translated built-in. `exwin-save` composes the stored name from the parent so it stays unique — which is exactly why **`exDraftReady` is the one place that decides whether Save is live**, read by `renderExerciseWindow` to draw the button and by `handleBind` to flip it as you type. A variation's draft `name` is empty and STAYS empty until save composes it, so a second copy of the rule checking `name` greyed the button out for every variation there has ever been, however completely the form was filled in; the field that has to be filled is whichever one is on screen. A new field that gates saving goes in that helper, not beside it. A variation of a variation attaches to the ROOT, since nobody wants a tree of grips, and **deleting a parent never takes its variations with it** — they are separate lifts with their own history, so they simply stop being listed as a family.
  - **WHICH END OF A FAMILY IS THE BASE IS AN ACCIDENT, SO IT CAN BE MOVED** (`reparentUnder` / `shortUnder`, *File under another lift* on the variations panel). The base is whichever row existed before variations did, which is a fact about the order somebody started logging in and not about the movement: log the one-arm machine for a year and every ordinary pulldown afterwards has to hang off *it*, with the machine — the variation — sitting where the movement should be. There was no way out of that but deleting a lift and its history. So an existing row can be filed under another after the fact, and **its own variations come with it**, re-attached to the new base beside it rather than left pointing at a row that is no longer one. Each moved row's stored name is recomposed from the new parent's, which makes this a RENAME and sends it through `renameExerciseIn` — unless that name is taken, where the row keeps the one it already answers to, because a unique name it answers to is worth more than a tidy one. The short part is guessed by stripping the parent's name off the front ("Lat Pulldown (OA machine)" under "Lat Pulldown" is an *OA machine*) and then **shown in a field before anything is written**, since it is arithmetic on a string and the person reading it knows what the lift is. Only BASES are offered as a parent, so a cycle cannot be built; picking a variation resolves to its root. The inverse (*Make it a lift of its own again*) is deliberately there and needs no confirm — it is what deleting a parent has always done to what it leaves behind, nothing is lost, and a move you cannot undo is a move most people will not make. `reparentUnder` hands back a patch instead of committing one, because `patch()` renders and the window that called it is still looking at the row by its old name.
- **Sync is a copy, never the store** (the SYNC block above `backupText`: `SYNC_COLLECTIONS` / `syncLocalItems` / `syncApply` / `syncPull` / `syncPush` / `syncNow`, with the sheets in `renderSyncSheet` / `renderJoinSheet`). Everything local-first stays exactly as it was: nothing waits on a network to be counted and the app works the same in a basement. It is **always on, for every profile in the account, and there is no switch and no word for it in the interface**: it used to be off until turned on per profile, which is exactly what made "the same profiles on every device" impossible to promise. The only per-profile decision left is SHARING it with another account (`renderSyncSheet`, titled *Sharing*: codes, the people list, and for a shared profile, leaving it). What is done offline is kept on the phone and goes up when there is a connection, the way an online document editor behaves. Locally a profile is a whole `state` under its own key; on the server it is a row plus items of `{collection, itemId, json}`, and the bridge is a `remoteId` in **`zenofit:profiles`, outside `state`** for the same reason `zenofit:device` is: `backupText` serialises `state`, a backup is a file people share, and restoring one onto a second phone must not hand it the keys to the original. **What travels is `SYNC_COLLECTIONS` and nothing else**, and the server enforces the same list and refuses an unknown collection *by name* rather than dropping it, so the two disagreeing is loud. Deliberately absent: `drafts` (a photograph of a half-typed set editor) and `timers` (they carry a `cloudId` naming a push alarm booked for ONE device). Of `settings` only the training half goes — `units`, `startDate`, `weekMode`, `sex`, `name` — because theme and language are properties of a phone, not of a person's training. **Change detection is a hash per item** (`marks`, in the sync record), because nothing in this app stamps an edit — a log entry has `createdAt` and has never had an `updatedAt`, and adding one would mean touching every one of the hundreds of places that write. A push is whatever no longer matches its mark, plus a tombstone for any mark that outlived its item; that cannot miss an edit made by code that has never heard of sync, and a second push with nothing changed sends zero. The `clientUpdatedAt` beside it is stamped when the change is **detected**, which is honest for the one thing the server uses it for (refusing to go backwards) and is **not a merge policy**: two people editing the same set between two syncs is not a case this resolves, and dressing it up as one would be worse than saying so. `syncNow` **pulls before it pushes**, since writing over the server before reading it is how an edit made elsewhere disappears unseen. **`syncApply(items, into)` and `syncPull` can target a profile that is NOT on screen**, which is what makes a freshly signed-in device arrive holding real profiles rather than a list of empty names: an off-screen profile is read off its own key, filled, and written back with `writeProfileState` (same two guards as `writeNow` — a save that will not parse is not written over, a full store is reported); `state` is never touched for one, and a LIVE profile is never pulled this way at all, since the whole point of one is that nothing of it is on this phone. The three lists whose order the user set and can see (`groups`, `presets`, `library`) carry their index as `__i` and are sorted back into it on the way in, because an item store has no order; `__i` is stripped before the row reaches `state`. **A PAGE IS NOT THE WHOLE LIST, and a row it does not mention keeps the place it already has**: falling back to "sorts last" is correct only when the page IS the collection, and it almost never is — renaming one exercise on the other phone pushes exactly one library row, which then sorted itself to the top of the library while everything else fell in behind it, and the shuffled order went back up as if somebody had meant it. A move really made elsewhere still lands whole, because moving one row renumbers every row after it and pushes all of them, so the page carries the part of the list that actually changed.
  - **PHOTOS HAVE A STORE OF THEIR OWN, AND A ROW NEVER CARRIES ONE** (the PHOTOS block beside sync: `photoPass` / `photoUpload` / `photoLoad` / `photoSlot`, `libraryWire`, `api/src/photos.js`, the `photos` table in migration `0007`). A photo used to ride inside its library row, so a row over the item limit went up *without* it and the other phone got the lift and a placeholder, and every pull re-sent every photo on its page. Now each photo has an **id — the SHA-256 of its data URL** (`ex.photoId`) — goes up to the photo store once (`PUT /v1/photos/:id`, which checks the bytes hash to the id, so nobody can store a different picture under an id somebody's library names), and the row travels with the id and without the picture. **Locally nothing changed**: `ex.image` is still the data URL, every screen draws from it, a backup still carries it, the app still works in a basement. One pass does three jobs for the profile on screen — *identify* (a picture with no id gets one: new photos, and every photo saved before this existed), *upload* (asking `POST /v1/photos/have` first, and remembering confirmed ids per device in `zenofit:photos-up`), *download* (an id with no picture is fetched and written into the row) — after every sync, on switching profile, after a live profile's fetch, and straight after a photo is saved, so the id exists before the push's own debounce fires. `syncPush` uploads before it sends any row naming a photo, so the other phone is never handed an id it cannot fetch yet; a photo that fails to upload never holds the row back. Four rules keep it honest, and all of them are load-bearing. **The wire row is built in `syncLocalItems`, before `__i`**, with the image taken out wherever it sat and `imageMissing: true` put back on the end, so the change hash is identical on the phone that sent it and the phone that later filled the picture in — two devices disagreeing about that hash is a row that pushes itself back and forth for ever. **`imageMissing` still rides on every photo row** for the builds that came before the store: to one of those the flag means "keep yours", so an old phone that holds the picture keeps it instead of deleting it on the strength of a row it half understands. **`syncApply` keeps the picture it holds when the incoming row names the SAME photo** (same id, or, from an old build, the bare flag) — the server does not filter a pull by who wrote it, so without this the phone that took a photo deletes it the moment it syncs; a *different* id is a photo changed elsewhere and the local one makes way; a row with neither is a photo removed. **A row with no photo at all goes up exactly as it always did** (`libraryWire` returns it untouched), so shipping this re-sent nothing that never had a picture. Fetched pictures also live in Cache Storage under `zenofit-photos` (sw.js keeps that cache across deploys; the id is the content, so nothing in it can go stale), which is what lets a live profile and a chat show a picture twice without fetching it twice; signing out clears it with the chat cache. `photoAway` / `photoComing` tell the two placeholders apart: an id with no picture is *on its way* and draws a slot that fills itself in place (`photoPaint`, never a render); `imageMissing` with no id is a photo still on a device running an old build. Readable by anybody signed in who holds the id — 256 bits nobody can guess, travelling only inside a profile or a message — with a per-account cap (`MAX_ACCOUNT_PHOTO_CHARS`) and an upload rate limit. **D1 is the store today** (bound to the Worker already, no new infrastructure, 2 MB per row).
    - **R2 IS THE FUTURE OPTION FOR PHOTOS — KEEP IT IN MIND, DO NOT DO IT UNPROMPTED.** Cloudflare R2 is object storage made for exactly this, and it is where photos should move once D1 stops being comfortable. Signs it is time: the `photos` table is a large share of the database (D1's per-database cap on the free plan is a few hundred MB — check the current limits rather than trusting this line), uploads start failing on size, or the per-account cap (`MAX_ACCOUNT_PHOTO_CHARS`) is being hit by ordinary use. It is a small change because the design was built for it: the id scheme (SHA-256 of the data URL for a library photo, hash of thread + picture for a chat photo), the routes, the `have` check, the per-account cap and the client are all unchanged, and only `api/src/photos.js` (`storePhoto` and the GET) plus the unsend branch in `chat.js` would move from SQL rows to `env.PHOTOS.put/get/delete`. Keep a small `photos` table in D1 for the metadata (id, size, owner, thread) so the cap and the thread check stay queries. It needs things only the user can do: **R2 has to be enabled on their Cloudflare account** (it asks for a payment method even inside the free tier), a bucket made (`wrangler r2 bucket create`) and bound in `wrangler.toml`. So raise it with the user when the signs appear and let them decide; moving the existing rows across is a one-off copy script, and nothing on a phone has to change.
  - **One row the server would refuse must not stop the other four hundred** (`SYNC_MAX_ITEM`, `SYNC_MAX_ID`, the `tooBig` list in `syncPush`). With the photos handled above, two things can still make a row unsendable: its SIZE, which now means a genuinely enormous row rather than a picture, and its ITEMID, which for a goal or a volume target is an exercise or a group NAME and is capped at 200 characters by the server — a longer one failed **every** push, for ever, silently. Either is left behind and **named** instead: everything else syncs, the sheet counts the two cases separately (a photo left behind is a shrug, a row left behind is a job), and neither is marked as sent, so fixing the row sends it next time with no extra bookkeeping.
  - **The server's message is the useful half, and it used to be thrown away** (`syncErrText`). Errors were reported as `e.code` alone, so `bad_item` appeared on screen while the message beside it read "library/default-0 is 700 KB, over the 512 KB limit" — the app knew exactly which row was the problem and said none of it. The code is now only substituted where the raw word actively misleads: **`not_found` on a profile you are linked to does not mean it is gone**, it means THIS device cannot see it, which is what happens when a share is withdrawn or the phone is signed in as somebody else; same for `read_only`. Everything else keeps the server's own sentence.
  - **A profile's name on the server is set once and has to be kept up** (`renameProfile` from `profile-form-save`). Renaming locally never reached it, so the account sheet listed profiles under names that existed nowhere on the phone. It is fire and forget — the name is display only, nothing is filed under it — and the account list **prefers the name this phone knows a profile by** wherever it is on this phone at all, so a rename that has not reached the server yet cannot make that list disagree with the Profiles screen two taps away.
- **Sync runs itself** (`syncTouch` / `syncQuiet` / `syncPollStart`, hooked into `persist()` and `visibilitychange`). There is no button for it any more; Refresh in the header is the one way to ask for a pass now. **Pushing is debounced**, not immediate: saving one workout writes state a dozen times in a minute and a push per write would be a dozen requests for one session, so `SYNC_PUSH_AFTER` waits for the typing to stop — and a push that finds nothing changed sends zero rows anyway, so being slightly eager costs one cheap request while being late costs an upload the phone may close before making, hence the `pagehide` flush. **The debounce belongs to the profile that armed it** (`syncFlush`, called by `switchProfile` before `profiles.active` moves): the timer names no profile and pushes whichever one is active when it fires, so leaving one inside the window armed a push for the profile you arrived at and dropped the one you left, whose last few sets then sat on the phone until something happened to touch that profile again — which, for one you switched away from, can be weeks. Anything else that changes which profile is active belongs in front of that same flush. **Pulling is polled** (`SYNC_POLL_EVERY`, only while the app is on screen, plus straight away on coming back, throttled by `SYNC_PULL_GAP`), because nothing pushes us: a rest timer gets a real web push, a set logged on the other phone does not. The one hook is `persist()`, which every mutation already goes through, so automatic sync sees every change without a single call site knowing it exists — and `syncApplying` stops a pull's own `writeNow` from scheduling a push straight back. **Nothing here re-renders unless something landed, and not even then while a field has the caret in it** (`syncTyping`): `render()` rebuilds `#app` wholesale, and a sync that repainted mid-word would throw away the input somebody was typing in, from a timer they cannot see. It is silent by design — an unattended failure that raises an alert is a phone interrupting a set to say the wifi is bad — so errors are recorded for the sync sheet and nothing else.
- **A live profile is not on this phone at all** (`syncLive` / `liveEnter` / `liveAdopt`, with the `writeNow` guard). This is the one deliberate exception to local-first, and it exists for a real person: a phone too full to save anything and a training log she still wants to look at. `state` is filled from the server into memory on switching in, `writeNow` refuses to write its key, and closing the app forgets it entirely — there is no clever eviction, just a profile the save path declines to save. **Only ever a READ grant**, never a profile you own: the trade is that no signal means no profile, and losing your own log to a dead connection is not a trade anybody would take, while somebody else's log is still whole on the phone that owns it. Read-only is what makes it safe — with nothing of yours in there, a failed fetch can lose nothing. It starts from a **blank state and no cursor**, so what you end up looking at is exactly what the server holds, tombstones and all, rather than a merge with leftovers; and a failed fetch **puts back whatever was on screen** rather than leaving somebody staring at an empty log and drawing the obvious wrong conclusion, with the strip at the top saying so and offering Retry. `liveAdopt` moves an existing read-only copy over on first launch **without deleting its key** — `liveEnter` drops that only once a fetch has proved the server hands the same thing back, so a phone with no signal on the day this ships still opens the copy it already had. It is also reached mid-session now: a pull that reports the grant has dropped to read hands `syncDemoted` the profile, which adopts it and re-enters it, and a pull that reports the opposite clears `live` so the save path starts keeping it again.
- **An account is a device that got claimed** (`api/src/auth.js`, migration `0004_accounts.sql`, `register`/`signIn` in `zenofit-cloud.js`, `renderAccountSheet` in `app.js`). Identity started as one row per browser install: a token in `zenofit:device`, no way back in once it was gone, and a synced profile stranded on the server the moment a phone died. A username and a password are that **same user row**, claimed — nothing is moved and there is no second users table, so `profiles.owner_id` keeps pointing at what it always pointed at and somebody who registers today keeps what they synced yesterday. Registering *with* a device token claims it; registering without one makes a fresh account, which is what a second person on a shared phone wants. **The password never reaches the server.** A Worker on the free plan gets 10ms of CPU per request, which is less than any honest password hash needs, so the browser runs PBKDF2-SHA256 at 210,000 iterations and sends 256 bits of derived key; the server salts and SHA-256s that once, which is cheap and sound because the thing it hashes is no longer guessable. **The client's salt is the lower-cased username**, not a random value, so a login needs one request instead of two and there is no endpoint that answers "does this account exist" before a password is offered — the cost is that two identical passwords under different names share nothing, which is fine, and usernames are unique so no two people share a salt. If `PBKDF2_ITERS` ever changes on one side, `test/smoke_auth.py` must change with it or every login fails while every test passes. **Tokens moved to their own table** in the same migration: `users.token_hash` held exactly one, which was right while a user WAS a device and wrong the moment you can sign in somewhere else — the second phone's login would have silently signed the first one out. The migration back-fills every existing device's token into a row of its own, so deploying it signs nobody out. `username_lc` carries the UNIQUE index because nobody remembers the case they typed. **There is no password reset** — there is no email to send one to, and the sheet says so before you pick one.
- **An account is what holds the profiles, so there is no app without one.** Every profile belongs to exactly one account's list (`profiles.userId`), and the account's list is the same on every device it logs in on. Sharing is the one way a profile reaches a SECOND account, and it arrives there under *Shared with you*, never mixed in with that account's own.
  - **The account sheet is who you are, the account's profiles, and Log out** (`renderAccountSheet`, only ever drawn logged in). It used to list every profile on the PHONE with a status word each (*back up*, *get it*, *on this phone*, *synced but not to this account*) and a button for whichever needed doing; that was the app's bookkeeping on display, and it is gone along with `acct-backup`, `acct-pull` and `refreshCloudProfiles`.
- **One control means "show me what is actually there now"** (`refreshNow` / `swRefreshShell` / `refreshBtn`, the circular arrow in both headers, and the `refresh-shell` message in `sw.js`). Two different things go stale in here and both used to be fixed the same way — close the app, open it again, and if that did not do it, once more. **The training**: a live profile is fetched on the way in and then polled every few minutes, which is right for a phone in a pocket and no use to somebody stood there having just been told a set was logged on the other phone. **The app itself**: `sw.js` answers from cache first and re-fetches behind you, which is what makes it open instantly and work with no signal, and it also means a deploy appears on the SECOND launch — nothing on screen ever said so, so what it taught was exactly that habit. From the user's side those are one request, so they are one button: a waiting worker is taken (which reloads), otherwise the shell is re-fetched past both caches and the page reloads **only if something really came back different** (ETag first, an exact body comparison where there is none), and otherwise it pulls the profile in front of them. It is read-only in every sense — it is on `READ_OK`, and the debounce is flushed before a reload can happen — and it holds its spin for 450ms even when the answer is instant, because a spinner that flashes for 40ms is the same thing to a finger as a button that did nothing.
- **A join code types itself** (the `joinCode` branch of `handleBind`). Ten characters from a 32-letter alphabet, printed `XXXX-XXXX-XX`, and usually copied off another phone a character at a time while somebody reads it out. So the field upper-cases, inserts the dashes after the fourth and eighth, and refuses an eleventh. None of it is *required* — `normalizeSeed` on the server already forgives lower case, missing dashes and the excluded letters — it is there so the thing being typed looks like the thing being read. **The caret is placed by hand**, because rewriting `value` sends it to the end, which on a phone means the cursor jumping past a dash the field just inserted and the next backspace eating the wrong character.
- **A read grant is a constraint, not a label** (`syncReadOnly` / `READ_OK` / `toastReadOnly`, checked in the one click dispatcher). Enforcement is an **allowlist** rather than a list of things to block, so it fails the safe way: an action added next year is refused until somebody decides it is safe, instead of quietly becoming a hole. On the list is navigation and looking — tabs, sheets, filters, the chart, the calculator, the accordion, Storage check, export — plus the sync sheet itself, because *Leave* has to stay reachable from inside a profile you cannot write to, and the timers, which belong to the phone rather than to the training. A strip at the top of every tab says whose profile it is, on Home too, where there is no header to hang it under. The server refuses the write as well; this side is the courtesy that stops somebody logging a session into a profile that will throw it away on the next pull. **Joining always makes a NEW local profile, and a BLANK one** (`join-go` / `acct-pull` / the roster's adoption → `addProfile(name, {forRemote: true})`), never a merge into one that already has your training in it: that is the one outcome here nobody could undo. `forRemote` empties the seeded `library` and `groups`, and it is not tidiness — the seeds used to survive the pull as unmatched, unmarked rows and then get pushed up as the joining device's own, so five built-ins the owner had deleted years ago **reappeared in the owner's library** with nobody having asked for them. A profile that is a copy of another one starts from nothing or it is not a copy, it is a merge; live profiles have always done exactly this (`liveEnter`), and this is the same rule applied to the copies kept on disk. The timers stay seeded, because they never sync and belong to the phone.

    Your own code typed on the phone that made it is refused outright (`alreadyMine` → `sync.joinOwn`) rather than becoming a second, read-only, live copy of a profile already in the list.
  - **THE LEVEL IS DECIDED BY THE CODE SOMEBODY CAME IN ON, IN BOTH DIRECTIONS** (`/v1/join`). This is the bug that made read-only look like a lie. `ON CONFLICT` used to keep the better of the two levels — a write grant survived a later join on a read code — on the reasoning that only revoking should take access away. But it is the OWNER who mints a code, so handing somebody a read code IS the owner taking write access away, and nobody can promote themselves with a code they were never given. Getting it backwards meant sharing read-only to somebody who had *ever* been given write changed nothing at all: her app said "read only" because that is what the code said, the server kept taking her pushes because the grant still said write, and her sets landed in his log. `PUT /v1/profiles/:id/grants/:userId` is the direct version of the same decision, owner only, wired to *Move to read only* / *Let them edit* in the people list, because "I'd rather she just looked at it now" should not cost her the profile and a new code.
  - **Making a code RETIRES the old ones** (`sync-make-code` → `rotateSeeds`, not `createSeed`). The line under those two buttons always said so and the code never did: every profile is minted with a write seed it never shows anybody (`POST /v1/profiles`), a read code made afterwards left that one live, and nothing in the app had ever revoked a seed. So a profile "shared read-only" still had a working write code hanging off it. Nobody already in is touched — a grant is a person, a seed is only the doorway, which is the difference between this and *Remove*.
  - **A change of level is learned on the next pull, and acted on** (`syncPull`'s `demoted` / `syncDemoted`, and the `live` half of the same patch). Dropping to read turns the local copy into a live profile there and then: the screen locks on the next frame, the copy leaves the phone, and it is re-fetched from the server. Rising above read does the reverse and **clears `live`**, or the profile would be one `writeNow` refuses to save, and a week of her sessions would exist only on the server.
  - **A DRAG IS NOT A CLICK, AND THE ALLOWLIST ONLY GUARDS CLICKS** (`DRAG_READ_OK`, checked in the `pointerdown` handler). Reordering arrives as `pointerdown`, so on a profile whose every button said no, dragging the library, the groups or the presets into a different order went straight through and the next pull silently put it back. Only `profile` and `pinnedTimer` are allowed, which is the same line `READ_OK` draws: the profile index and the timers belong to the phone. It is refused *before* the gesture starts, because a row that picks up, follows your finger and springs back reads as a bug rather than as a rule.
- **A backup is `state`, not a list of things to back up** (`backupText` / `importBackup`, Settings → Data). Everything the user has is one object under one localStorage key, so the export is that object serialised and nothing is enumerated, which is the point: a hand-listed backup silently stops covering whatever is added next, and the first anyone hears of it is a restore missing their custom exercises. **Adding a field to `defaultState()` is all it takes to be included.** The one exclusion is `drafts`, the crash snapshot of whichever form was open at the moment of export: it is a picture of the UI, not of anyone's training, and restoring it drops the person on the other end into a half-typed set editor from a session they were never in. `dayDrafts` is not that and travels. Import goes through the same `hydrate()` the first load uses, so a file written by an older version comes up exactly as that data would if it had been sitting in localStorage, since a restore must never be a downgrade. It accepts a bare state object as well as the envelope, refuses anything without a `log` array and a `settings` object, and asks before it writes, because overwriting a training history with a file that merely parsed is the one failure here that cannot be undone.
  - **The same file goes out two ways, and there is only one file** (`backupName` / `backupText` feed both `exportBackup` and `shareBackup`). Download is the wrong shape for what people do with a backup on a phone — send it to somebody — so the bytes also go to the system share sheet (Web Share Level 2), where a chat or a mail is one tap instead of Downloads plus a file picker. **Never add a second export format for it**: the share and the download must stay the same file or a restore starts depending on which button was pressed. Whether the sheet takes files is *asked*, never assumed: `shareFileType()` probes `navigator.canShare({files})` with a real `File` (it needs a secure context, and some platforms take a `.json` only as `text/plain`, so it tries both and the winner is what the file is built with), memoises the answer, and the button is not drawn when the answer is null — a share button that cannot share is worse than none. `navigator.share` is called with nothing awaited before it, or the browser drops the tap's activation and refuses. A dismissed sheet is `AbortError` and says nothing, since that is an answer; any other failure says so once and falls back to the download, because the sheet is a convenience on top of the file and the file still has to arrive.
- **Muscle groups are records, not a colour map.** `state.groups` is `[{name, key?, color, kind}]`, seeded from `DEFAULT_GROUPS`; `colorFor()` reads it, so recolouring a group repaints every surface at once. **Its order is the order groups appear in everywhere**, and the user sets that by dragging in the group manager (see *Drag to reorder* below). Renaming a group in `actions["group-save"]` has to carry the library, log, **plans, day drafts**, presets, volume goals and the active filter with it, the same sweep the exercise rename does and with the same standing rule: **a new place that files something under a group name belongs in that list.** The log's `muscle` is only a fallback (`muscleOf` reads the library row first), which is why a miss there stayed invisible for so long and exactly why it is worth keeping true, since the fallback is what answers for an exercise no longer in the library at all. There is no sweep of the open workout sheet or entry form as there is for a rename of an exercise, because the group manager opens from the Library tab only and nothing of the sort can be on screen. **Note what a rename does NOT carry: `isCardioEx`/`cardioType` still test the literal name "Cardio"**, so renaming that one group stops new exercises in it being logged in minutes (the built-ins keep their `type` and are unaffected). Fixing that means deciding where a lift's cardio-ness really lives, which is a design question, not a missing line here; deleting a group never takes exercises down with it, and tips whatever is still in it into the bucket rather than refusing, over that same list and unconditionally, since `groupUseCount` counts library rows only while a logged entry can still name a group after its exercise has gone. **`group-delete` rebuilds the survivors from their RECORDS, never from a list of names**: mapping names back into fresh `{name, color}` objects dropped every remaining group's `key`, so deleting one group you invented un-translated all seven shipped ones and lost track of which was cardio. Migration v12 repairs that damage with the same back-fill v5 used.
- **Drag to reorder is one gesture serving several lists.** `startRowDrag`/`moveRowDrag`/`endRowDrag` use pointer events rather than HTML5 drag-and-drop, which never fires on touch, and run entirely on inline transforms without a re-render (`render()` rebuilds `#app` wholesale and would drop the node mid-gesture), committing only on release. A row declares which list it is in with `data-dragrow="<kind>"` and carries a `[data-drag-handle]`; **`DRAG_COMMIT` maps that kind to the function that persists the new order**: `group` → `reorderGroups`, `preset` → `reorderPresets`, `pinnedPreset` → `reorderPinnedPresets`, `pinnedTimer` → `reorderPinnedTimers`, `entry` → `reorderDraftEntries` (the lifts inside the open day), `libExercise` → `reorderLibraryExercises` (one group's lifts inside the flat library, via the same `reorderPinnedIn` move, keyed off the row's `data-group`), `set` → `reorderSets` (the sets inside the open entry, the one list whose order is read as data rather than shown as a choice), `variation` → `reorderVariations` (one lift's family, ranked from the *Ways you do this* panel, keyed off the row's `data-root`). Another reorderable list is a row attribute plus one line in that table, not another gesture. The two pinned strips share `reorderPinnedIn`, since "rearrange a filtered view of one master list without disturbing what it filtered out" is the same move either time. **`DRAG_READ_OK` is `READ_OK`'s other half**: the click dispatcher's allowlist never sees a drag, so a new reorderable list has to be decided about in both places, and the default in both is no. **Ranking variations moves them in `state.library` and nowhere else**, which is what keeps one drag honest in all three places a family is listed — the panel, the nested library list and the picker you add a lift from — with no ordinal field that could drift from the list it claims to describe; only the slots that family already occupies are rewritten (the `reorderPinnedIn` move again), so a variation filed under the family long after the fact, sitting forty rows away, still ranks without shifting a single row around it. The **base is not in the list**: every surface draws it first by construction, so a handle on it would promise a move nothing would carry out, and it sits above the draggable rows saying `ex.baseStays`. Each row carries how many DAYS you have trained it, because that is the thing anybody ranking these is ranking them by and it is sitting in the log unasked.
- **A dial is a control, so reordering is a mode.** The pinned strips (presets on Home, timer dials on Home *and* at the foot of the workout and exercise windows) swap their cards/dials for compact drag rows while `ui.presetOrder` / `ui.pinnedOrder` / `ui.timerOrder` is on, rather than wearing a permanent grip handle. You tap a preset card to start a workout and a timer dial to start a rest; a handle living on either is one mis-tap from doing the wrong thing mid-set. `orderToggle()` draws the Reorder/Done control into a `sectionTitle`'s right slot. Note the timer list renders **twice at once** when the entry form sits on top of the workout sheet: two independent containers of the same three rows, which is fine because a drag only ever walks `row.parentElement`.
- **Preset order is user-set, and the pinned strip is a slice of it.** `state.presets` order is the order presets appear in the Library, the picker and on Home. Both lists are rearranged in a *mode* (`ui.presetOrder` on Library → Presets, `ui.pinnedOrder` on Home) rather than by a permanent grip handle, because the cards themselves are what you tap to start a workout and a handle on them would be one mis-tap from starting the wrong day. Home shows `presets.filter(pinned)`, so `reorderPinnedPresets` rewrites **only the slots the pinned presets already occupy** and leaves unpinned ones exactly where they sit, since arranging your home screen must not shuffle the library behind it.
- **Planning is a second ledger that nothing counts.** `state.plans` is `[{id, date, name, entries, createdAt}]`, one dated session you have decided on and not done. Its `entries` are **ordinary entry objects**, the same shape the log uses, which is why the plan builder is not a screen: `renderWorkoutSheet` takes a `draft.planning` flag and the same picker, presets, set list, set editor and "beat last time" card write a plan instead of a day (`commitPlan` vs `commitWorkout`). Two rules make it a plan rather than a log row with a future date, and both matter: **nothing in `state.plans` is ever counted** (not sets, PRs, volume, weeks or charts, and that is the whole point, since a future-dated *log* entry is believed by every calculation downstream), and **a plan may keep entries with no numbers on them** ("Wednesday: these six lifts, weights on the day"), where `commitWorkout` drops blanks. Backing out of a planning sheet saves it; emptying one deletes it, exactly as for a parked day. One plan per date, kept true in `handleBind`'s `draft.date` branch rather than argued about on save.
- **A plan is consumed lift by lift, not by the day.** `plan-start` turns each planned entry into a *blank* entry carrying `e.plan`, a frozen target snapshot (`planTargetOf`: `{sets:[{reps,weight}], unit}`, or `{minutes,intensity}` for cardio), and stamps `draft.planIds` plus, on each entry, a transient `planFrom`/`planIx` back-link that `stripPlanLink` takes off again on the way into the log. The targets ride into the log inside the entries, so "did I do what I said I would" is answerable from `state.log` alone, forever, with no second source of truth about whether a day happened. **Saving a day is not a declaration that the session is over**: people save after the first lift and carry on, so `prunePlans` leaves whatever is still blank *and still in the sheet* on the plan, stamped `startedOn`, and `edit-day` hydrates those back in when the day is reopened; a lift you deleted from the sheet leaves both, because taking it out is the decision not to do it. The plan only disappears once nothing is left of it, and `renderPlanResult` waits for that same moment rather than scoring a session its user is still in the middle of. The back-link is what makes any of this possible: `e.plan` alone cannot tell a planned lift from an ordinary blank, because a plan that named the exercise and left the weights for the day hands over no target at all. `stashDayDraft` carries `planIds`/`planName`, and the back-links ride along on the cloned entries, so parking a session mid-way does not lose the link either. **Planned numbers are never copied into the log**: they appear as *ghost rows* at the end of the set list (`ghostSetRow`), where ✓ (`plan-tick`) logs one exactly as planned and the row itself (`plan-load-set`) opens the set editor with the target loaded. That is the same tap-to-load rule the suggestion card lives under, and it is what buys the smoothness (a session that went to plan is one tap per set) without ever writing a number into the log that a finger did not put there.
- **A saved day keeps what you did not log, and scrapping one is a separate decision** (`state.unlogged`, `unloggedOn` / `unloggedWith` above `commitWorkout`, `actions["scrap-draft-entry"]`). Blank entries used to be dropped on save, which read one gesture as two decisions: *I skipped that lift* and *I forgot to write it down* produced the same result and only the app knew which had happened — and the one you actually did was the one you lost. So `commitWorkout` now files them under `state.unlogged` as `[{date, entries, savedAt}]`, one row per date, and `edit-day` hydrates them back into the sheet after the logged rows and the plan ghosts. **It is not the log and it is not history**: nothing in it is a set, nothing is counted toward volume, PRs, weeks or a chart, and the Log tab does not draw it — the same promise `plans` and `dayDrafts` make. The other half is the bin on a waiting card: no confirm (a blank holds no numbers) and nothing is written until the day is saved, so backing out of an edit undoes it, and on a plan-linked blank it gives up the plan's claim exactly as deleting one from the sheet always has. **Plan-linked blanks are deliberately absent from it** — `prunePlans` already leaves those on the plan and `edit-day` reads them from there, so storing both would deal the same lift into the sheet twice. **Nothing waits on a lift the day already has a row for** (`stillOutstanding` / `loggedNamesOn`). *Waiting* means still outstanding, and a blank Hack Squat beside the Hack Squat you logged is not outstanding, it is the same lift twice — `edit-day` deals the logged row in regardless, so the twin can only ever arrive as a duplicate card under a lift the day says you did. Deleting the twin and backing out **without** saving used to leave it exactly where it was, which is the right rule about unsaved edits and the wrong one here, because there was nothing left for it to be waiting on. So the rule does not turn on who pressed save: `unloggedOn` drops it on the way OUT of the store as well as `commitWorkout` dropping it on the way in, which is what makes a day saved before the rule existed open clean and the next save of that day write the shorter list. Note the two ends read different sources on purpose — the read filters against `state.log`, the write against the sheet's own filled rows, which are not in the log yet. A lift the day has no row for is untouched by any of this and still comes back when an edit is abandoned. Two paths unmake a day and both must clear its row or it is orphaned where nothing can reopen it: `delete-day`, and `commitWorkout` when the save leaves the day with no filled rows at all. Being a plain `defaultState()` array it travels in a backup and defaults to `[]` on an older save with no migration, and because it files things under an exercise name *and* a group name it is in all three rename/delete sweeps (`exwin-save`, `group-save`, the group delete).
- **A day has a note of its own, and it is read back in six places** (`state.dayNotes`, `dayNoteOn` / `noteBlock` / `dayNoteBlock`, written in the *Session note* field at the foot of `renderWorkoutSheet`). An entry's `notes` is about one lift; this is about the session — how you slept, what the gym was like, why the numbers are what they are — so they are two fields answering two questions and neither is a place to write the other. It is a **map keyed by DATE**, like `goals` is keyed by a lift's name, because there is no day record to hang it on: the log is a flat list of entries carrying a date, and a day's rows come and go while the date does not. **It counts for nothing** (no PR, no volume, no week, no graph — the app never reads it) and it is **dropped with the day it belongs to**: `delete-day`, and a day emptied out and saved as not done, since a note with no session under it is a sentence about nothing. On a day MOVED to another date it goes with the day; the one thing an empty note never does is wipe a note already sitting on the destination, which the sheet was never handed and so cannot be what decides is gone — the same reasoning `unloggedWith`'s `alsoDrop` follows. It is written in **one** place and read back in six, which is the point of it: the day in the Log tab (where the note itself is a second way into `edit-day`), the day on the Calendar, a parked day above the history (where it rides on the `dayDrafts` row as `dayNote` and reaches `state.dayNotes` only when the day is committed, exactly as the entries do), the point you tap on a lift's graph, every session in a lift's history, and **`Last time` in the next workout**, which is the surface that pays for the feature: “shoulder was cold, went light” is not a fact about one lift and could never have been written on one, and it is exactly what you want in front of you stood over the bar a week later. A day holding **nothing but a note** is still parked rather than binned (`stashDayDraft`), and clearing both is what deletes a parked day; it can never be *saved* on a note alone, because a note is not a workout.
- **Planned vs done is three verdicts and no cleverness.** `setVerdict` says **beat** (more on one axis, short on neither), **hit** (matched) or **under**, matching planned set *i* to logged set *i* by position, with anything past the end of the plan a bonus set. It deliberately does **not** judge on estimated 1RM: a heavy triple outscores the eight you planned, and calling that "target hit" would be the app deciding what you meant. **That rule is for plans only** (see the next bullet: measured against last time, the same trade reads as the improvement it is). `entryPlanResult`/`dayPlanResult` aggregate it for the set list, the entry card, the history row, the day chip and the result sheet (`renderPlanResult`), which is shown once on saving a planned day and never volunteered again. Under is never scolded anywhere it appears.
- **The verdict, pointed at last time** (`setProgress` / `lastTimeSets` / `entryLastResult`, drawn in `renderSetList`). Est. 1RM speaks for an *exercise* through its BEST set, which is the right answer to "what could I lift for a single" and the wrong answer to "did today go better than last time": match your top set, add a rep to your second, and the headline estimate does not move even though the session was strictly better. So with no plan to answer to, each set is compared with **the set that stood in its place last session** — by chain coordinate, not by row number, so a drop only ever answers to a drop (see the dropset bullet above). It is graded by `setProgress`, **not** by the plan's `setVerdict`, and that distinction is the whole point: the two-axis rule calls a set under the moment it is short on either axis, so 14 × 60 kg followed a week later by 11 × 65 kg read **under** on the strength of the reps alone — while that set is 88.5 kg of estimated max against 87.4, and the est. 1RM card open on it said "1.1 higher than set 2" in gold at the same moment. Trading reps for plates and coming out ahead is the shape of getting stronger, not a step backwards, and the app was contradicting itself on one screen to say otherwise. `setProgress` asks the per-set score instead, **rounded, so the verdict is checkable against the two numbers actually printed**, and the one-axis kinds are unaffected because for reps and for seconds the score IS the axis. **Against a plan the two-axis rule stays**: a plan is a sentence you wrote down and 11 reps is not the 14 you said, which is a different question with a different right answer. Sets past where last time ran out are simply **unjudged**: no verdict, no penalty, so a session can never score worse for containing more work, which is the trap any average over sets falls into (adding a real back-off set drops a mean by several kg and quietly teaches people not to log it). A plan outranks last time where both exist, cardio and first outings return null, and last time's weights are brought into the unit being typed in by **`weightAs`, which rounds to TWO decimals**, so a kg set and the same set logged in lbs cannot disagree by a float hair. That rounding used to be one decimal, and it invented verdicts of its own: 26.25 kg came back as 26.3, so a set that repeated last session exactly was logged as less than the number it was being measured against and read **under**, with the card above it simultaneously reporting a *higher* estimate off the same rounding. Two decimals hold every step a plate tree can make (1.25 kg, 2.5 lb), which is all the precision a weight off the log ever claims; `weightAs` is now the one road every past weight travels to sit beside a present one (`lastTimeSets`, `openingSetFor`, `setSuggestion`), so they cannot round differently from each other again, and the row's own "last time 7 × 26.25" prints at that same precision. **Under is never counted up at you**: the tally above the list names only what was beaten or matched. Nothing here touches the exercise's est. 1RM, the PR badge or the graph.
- **The entry card names two numbers, and no longer offers an opinion** (`entryComputed` → `entryRefCols`, kept live by `updateEntryPreview`). Beside the exercise's est. 1RM sit **LAST TIME** and **BEST EVER**, in that order because that is the order they are useful in: last week's number is the one you can do something about tonight, and putting the all-time ceiling first would make every ordinary session read as a failure. Each wears the set list's own `VERDICT_COLOR` against its own bar — gold once today's figure is past it, green when level, muted until then — so *did I beat it* is answered by the colour and *by how much* by the two numbers, with no sentence in between. This replaced a single word out of `BADGE_TEXT` ("Beat your best 💪", "Below best, normal, keep going"), which is gone along with those strings: **encouragement is not information.** It never said what the best actually WAS, so the one question it provoked was the one it could not answer, and the only bar it implied was an all-time one that most sessions are nowhere near. A bar that does not exist yet prints an em dash rather than vanishing, so the row keeps its shape the moment history arrives, and no unit is repeated on either — they are the same quantity as the figure beside them, whose label already carries it. **The window is filtered by KIND as well as by name**, which the word never was: that mattered less when the output was a sentence and matters completely now that it is a number, since `metricOf` answers in kilos for a strength session and in reps for a bodyweight one, and pooling them put a rep count in a kilo column. It is otherwise deliberately wider than `earlierOutings` — it includes the entries in the open day sheet, which are not in `state.log` yet — so a lift logged twice in one session is measured against its own earlier card. `BADGE_SHORT` is untouched and still labels the rows in your history, which is a label on a list rather than a verdict delivered mid-set.
- **The est. 1RM in the set editor is measured against the set in the same position, with the all-time best beside it** (`lastSetMetric` / `bestEverMetric` / `vsLastLine` / `bestEverBlock`, kept live by `updateSetPreview`). On its own that figure answers nothing, because nobody carries last week's estimate around in their head, and the whole point of typing your own numbers is that you did not want either option the suggestion card offered. Two references, because they answer two different questions and conflating them was the bug. **The main one is positional**: set two is measured against last session's *set two*, on the same per-set score `setProgress` grades the row behind the sheet with and on the same chain coordinate it matches on (`lastSetMetric` takes the open set so it knows whether it is a drop), so the number and the beat/under badge on the row can never disagree. It used to be measured against last session's **best** set, which made the card say "1.2 lower than last time" on a back-off set that had just beaten the back-off set it was actually repeating: true statement, wrong question. It therefore names the position as well as the number ("set 2 last time 29.1 · 23 Aug"), or the figure reads as the session's, which is exactly what it stopped being. Sets past where last session ran out are **unjudged**, the same rule `entryLastResult` follows, and the card says so in a faint line rather than going blank, because a card that silently drops its comparison reads like a bug. **The side one is all-time**, small and muted: the best this lift has ever been worth, over the same strictly-earlier window the PR badge reads (`earlierOutings`), so the two can never disagree about what "best" was. It is the ceiling and not a target, which is why it is second and quiet, and it goes gold and says *new best* the moment the set in the boxes clears it, which is the same claim the badge will make when the entry is saved. Both are read in the unit being typed in (the positional one through `lastTimeSets`, the all-time one through `weightAs`), because a kg estimate held against an lbs one is not a comparison. Both are computed **once per render** and parked in the module-level `setRefs`: neither can move while the sheet is open (typing does not write to the log, and the unit select does a full render), and each otherwise costs a sort of the whole log per keystroke. It wears the set list's own `VERDICT_COLOR` (beat/hit/under), stays put under a plan because it states a fact about a number rather than proposing one, and is text and colour only, no icon, because it is rewritten in place while you type and a freshly injected lucide placeholder has nothing to turn it into a glyph.
- **Set order is data, which is why the set list is draggable** (`reorderSets`, `data-dragrow="set"`). Everywhere else an order is presentation; here `entryLastResult` reads it, so a session worked up and logged bottom-first comes back as a row of "under" verdicts describing nothing but the order it was typed in. Dragging it into the order the sets actually happened is what makes those verdicts mean anything. Reordering is a **mode** for the same reason it is one everywhere else (a set row is what you tap to correct a number), and `ui.setOrder` holds the ENTRY'S ID rather than a boolean, so opening a different lift stops matching instead of leaving a mode for twenty call sites to remember to clear. Nothing derived moves with it: `bestSet()` takes the highest estimate wherever it sits.
- **A plan is not a preset, and the difference is load-bearing.** A preset is a bundle of exercises with **no date and no numbers**: the shape of a session you repeat, and what the pinned strip on Home is for. A plan is **one dated session with the weights you are going for**, which is why today's plan gets its own card above the pinned strip and is gone again tomorrow. They compose, and *Add exercise → Presets* inside a planning sheet is the normal way to start one. Don't let either grow into the other.
- **The Calendar tab is where a plan is born and started** (`renderCalendarTab` = month grid → day card → plans list → deload planner → `renderVolume`). Tapping a day now means two things at once: it still picks the period the volume numbers are read over, and it selects `ui.calDay` for **the day card** (`renderDayCard`), the one surface that answers "what is on this day" in the same shape past or future: what you trained, what you planned, the parked draft if there is one, and the one or two things worth doing about it. Which button is the big one follows the calendar, not the feature: *Start* on today or earlier, *Edit plan* on a day you cannot train yet. On the month grid a **solid dot is a group you trained and a hollow one a group you have planned**, with anything already trained dropped from the planned row.
- **Deloads are planned, never inferred.** `state.deloads` is `[{id, start, end}]` with inclusive ISO dates, set by tapping two days on the Calendar tab. `deloadStatus()` decides what the home banner says: nothing, a countdown once the start is within `DELOAD_HEADSUP` days, then a day-N-of-M badge while it runs. The old five-hard-weeks radar is gone, since it was guessing at something only the lifter knows.
- **A week is seven days from your start date, or the last seven days, the user's call.** `settings.weekMode` is `"program"` (default, and what every existing save migrates to) or `"rolling"`, read through `rollingWeeks()`. Program mode is the spreadsheet's: `weekOf()` counts from `settings.startDate` and every seventh day turns the page. Rolling mode replaces that with a *window*, `windowEnding(day)`, for lifters whose split simply comes round in order and for whom a Sunday and a Monday session are the same session. In rolling mode: the Calendar tab reads `ui.volAnchor` (the LAST of its seven days, set by tapping a calendar day, stepped a whole window at a time by the arrows) and sums with `volumeInRange` instead of `volumeForWeek`; the Progress tab's bar chart uses `rollingSetBlocks` (seven-day blocks counting back from today) instead of `weeklyTotals`; and **the program-week chips disappear** from the header, the history day cards and the workout sheet, because in that mode there is no program week to name. `volumeForWeek`/`weekOf` are deliberately kept for program mode rather than expressed as a date range: `weekOf` floors everything before the start date into week 1, and a range would silently drop those rows. **Deloads are untouched by the setting** and must stay that way: they are dates the user put in the calendar, not something derived from a week number.
- **A volume bar is a promise of a target.** In the Calendar tab's volume list a group only gets a progress bar when the user has set a target for it (`state.volumeGoals`). Without one there is no bar and no grading. The old behaviour filled the bar against the biggest group trained that period and flagged others "Low", which made a bar move for reasons that had nothing to do with the lifter, and called a rest day a failure. An untargeted group instead states the one fact available without a plan: how the period compares with the one before it (`vol.more`/`vol.fewer`/`vol.same`). Don't reintroduce a default target.
- **The Calendar tab's month grid** (`renderCalendar`) layers four independent things on each day cell: a tint for the program week whose numbers are shown below (or a `--raise` tint plus a border for the selected `ui.calDay`), a dashed gold band for a deload, solid dots for the muscle groups trained, and hollow dots for the ones a plan has lined up. Calendar maths is all ISO strings (`isoOf`, `monthOf`, `addMonths`, `monthGrid`, `weekRange`) built from local date parts, so a daylight-saving shift can't move a day.
- **`UNCATEGORIZED` is a bucket, not a group.** It is never in `state.groups`, and exercises land in it two ways: their group got deleted, or they were quick-added mid-workout and the muscle question was skipped (`pick.skipMuscle` → `quick-add-muscle` with the bucket as its `data-g`). Two list functions keep the distinction: **`libraryGroups()`** is what the user can *choose* (filter chips, the muscle dropdown, quick-add chips, the group manager) and never contains it; **`allGroups()`** is what must be *shown* (library sections, the exercise picker) and appends it last when anything is in it. It has no target control in the volume list, its name is refused in the group editor, and it disappears on its own once every exercise has been re-filed. Adding an exercise *from the Library* still requires a group, and Skip exists because you were mid-set, not as a way to leave the form blank.
- **Numbers accept a comma or a period.** Every numeric field is `${NUM}` (a text input with `data-num`, not `type="number"`, which discards the "wrong" separator). `handleBind()` strips non-numeric characters and stores the value period-separated via `decimalize()`; the field itself keeps whatever the user typed. Add new numeric fields with `${NUM}`, never `type="number"`.
- **`migrate(s)`**: schema migration for `state` loaded from localStorage. Bump/extend this whenever the persisted shape changes, rather than assuming a fresh shape.
- **`render()`**: rebuilds the `#app` innerHTML from `state`/`ui` on every change. Sub-renderers per tab/screen (`renderHome`, `renderLog`, `renderHistory`, `renderCalendarTab`, `renderProgress`, `renderCalc`, `renderLibrary`, `renderBody`, `renderTimers`, `renderProfile`, etc.) return HTML strings that `render()` assembles. `patch(p)` is the standard way to mutate `state` (shallow-merges, then persists + re-renders).
- **Event delegation, not per-element listeners.** Clicks are handled by a single `document.addEventListener("click", ...)` that dispatches on the closest `[data-action]` ancestor to the `actions` object (a big lookup table of action-name → handler, defined right before the click listener). Typed input is handled by delegated `input`/`change` listeners keyed on `data-bind` attributes, routed through `handleBind()`. When adding new interactive elements, follow this pattern (`data-action="my-action"` + an `actions.my-action` entry, or `data-bind="path.to.field"` + a branch in `handleBind`) rather than attaching listeners directly to DOM nodes, since nodes are thrown away and re-created on every `render()`.
- **`data-stopprop`** marks elements (sheet backdrops, nested editors) where an outer `data-action` must not fire when a click lands on an inner one, see the click listener for the containment check.
- **Sheets/overlays** (`sheet()`, `fullScreen()`) are modal-style panels layered via `ui` flags (e.g. `ui.showProfile`, `ui.showBody`, `ui.workoutSheet`, `ui.entryForm`, `ui.groupSheet`) rather than routing. Body measurements is one of these windows, opened from the ruler button next to the header gear, and it is not a bottom-nav tab.
- **Timers** run on their own interval engine (`startTimerEngine`, `sweepTimers`, `fireTimer`) independent of `render()`, with notifications through the one switch (`notifyFirstAsk`, `notifyDone`, see *ONE SWITCH* under chat). `notifyDone` shows through the service worker's `showNotification` — Chrome on Android refuses `new Notification()` from a page outright — and only when nobody is looking: on screen, the chime, the buzz and the banner have already said it. One timer can be on screen several times at once: its card on the Timer tab, and its round dial (`pinnedTimerDial`) both on Home and at the bottom of the workout and entry windows, where `renderTimerList()` repeats the same up-to-3 `pinnedTimers()`, so `paintTimers()` addresses every copy by `[data-tmr-time]` / `[data-tmr-ring]`, never by a single element id. Every dial carries the same pause/reset pair the Timer tab's cards have, wherever it appears; an *idle* dial has nothing to pause, so it stays bare and the row doesn't jump when one of three timers starts. Because those dials sit inside overlays, the timer editor sheet sits at `z-index` 120, above all of them.
- **The stopwatch counts the other way, and is the Timer tab's second half** (the STOPWATCH block: `newStopwatch` / `swElapsed` / `paintStopwatch` / `renderStopwatch`, behind the `ui.timerSeg` segment control in `renderTimers`, with the countdowns moved into `timersBody`). Every timer in the app counts DOWN to something; nothing counted up, which is what you want for how long a circuit took or how long the whole session ran. It is `{startedAt, acc, laps}` and the clock is **arithmetic, never a ticking number** — `acc` is what the last pause banked, `startedAt` is when the current run began — which is the same trick `endsAt` plays for the countdowns, pointed the other way, and is what makes the reading survive a re-render, a backgrounded tab and the app being closed and reopened. **Nothing is written while it runs**: only start, stop, lap and reset write, because the paint can work the number out for itself. It has **its own rAF loop** rather than riding the 250ms timer engine (at four frames a second the hundredths column would flicker through values it never showed), it paints in place like `paintTimers` for the same reason, and the loop ends the moment the digits leave the screen, so one left running in the background costs nothing. `laps` holds the **cumulative** reading at each lap, so a split is the difference with the one before and no lap can disagree with the total above it; fastest and slowest are marked once there are three, because with two the marks say nothing the two numbers do not. It lives in `state` (so it is per profile, exactly as the timers are) and **writes nothing to the log**, deliberately: a time worth keeping is one somebody types into a set themselves, the same rule the 1RM calculator lives under. It is on `READ_OK` for the same reason the timers are, and it feeds the nav's own running dot beside them — the countdowns and the clock that counts up are the same question asked in opposite directions and belong behind one icon, which is why it is **not** a third mini tab on the workout log, where it was first built and did not belong.
- **A rest timer is two alarms, and the local one wins wherever it can** (`cloudTimerStart` / `cloudTimerCancel` beside `startTimer`). `startTimerEngine` ticks every 250ms and `fireTimer` does the chime, the buzz and the notification, all of which need a living tab — so locking the phone mid-rest, which is exactly what people do, throttles that tab and then discards it, and the alert the timer existed for never happens. So every start also books the same deadline with the server (`ZenofitCloud.scheduleTimer`), which pushes a notification whether this app is alive or not. Three rules keep the pair from both going off in your ear: **the local one is scheduled to win** — the server's copy is booked `PUSH_GRACE_MS` (2s) late and `fireTimer` cancels it on the way past, so the push only ever speaks when the page was not there to; the gap is already in our favour, since the server starts counting when the request lands and we started when we sent it, but leaning on network latency for correctness is not a plan. **It is a second chance, never a prerequisite**: nothing is awaited, every failure is silent, and every degraded path (no `ZenofitCloud` at all, push blocked, push not enabled, the call throwing, a timer longer than the API's one-day ceiling) leaves the local timer running exactly as before — a rest timer starts the instant it is tapped, in a basement gym with no signal. **The deadline goes as a duration, never a wall-clock moment** (`inMs`, which the client puts on the wire as `durationMs`): a real phone tested here was 2.8 seconds off the server, and `inMs` means the phone's idea of the time never enters the arithmetic. Every transition that stops a countdown hands the server's copy back — pause, reset/stop, `fireTimer`, editing a running timer's length (`timer-save` restarts it, so the old deadline is stale), and `timer-delete` before the row leaves state. The handle is `t.cloudId`, which **persists in state on purpose**: start a rest, let the app die, reopen, tap Stop, and that is the only way the stray push can still be called off. Because it persists, `backupText` strips it next to `drafts` — it names an alarm booked for THIS device, on a server that will only cancel it for the device that booked it, and a backup is a file people share.
- **Alert sounds are synthesised, never files.** `SOUND_LIB` is a dozen alerts written as note lists (`[start, freq, length, waveform, gain, glideTo?]`) that `playSound(id, volume)` schedules on the Web Audio context, with no mp3s to download, cache, miss offline or license. **Sound and volume are per timer** (`t.sound`, `t.volume`, defaults `DEFAULT_SOUND`/`DEFAULT_VOLUME`, which live in the storage section because `seedTimers()` runs before the audio code is reached), edited in `renderSoundPicker()` inside the timer sheet, and read through `soundOf()`/`volumeOf()` so a malformed or missing value can never silence a timer. Volume 0 is a real choice and schedules nothing.
- **Charts** (`drawBarChart`, `monotonePath`, `niceTicks`) are hand-drawn SVG, no charting library. The progress line chart (`drawLineChart` → `paintLineChart`) is the interactive one: pinch/wheel zoom, drag to pan, tap a dot to open the entry behind it, and a fullscreen copy (`renderChartFull`). Its view (`ui.chartView`) and selection (`ui.chartSel`) live in `ui` so a re-render never resets them, in-flight pointer state is module-level (`chartPointers`/`chartGesture`) because a gesture redraws the chart underneath itself, and **every `[data-linechart]` of the same scope is painted from the same state**: the card and the fullscreen window are one chart drawn twice. Selecting a point deliberately patches `[data-linedetail]` in place rather than calling `render()`.
- **The graph does not stop at your data.** `ui.chartView[scope]` is `{lo, hi, yLo?, yHi?}` in *index* space (x) and *value* space (y), and `chartWindow`/`setChartView` deliberately allow it past both ends of the series, out to `chartMaxSpan(n)` and far enough either side that the history is nearly, but never quite, off screen. The empty space in front of the last session is the feature: a graph that ends at your best set reads as a ceiling. `yLo`/`yHi` absent means the vertical axis is still auto-fitting to whatever is on screen (`niceTicks`), which is what makes a zoomed-in plateau readable; a pinch or a vertical drag freezes it and hands it over (`ticksWithin`, which fits ticks *inside* a given domain rather than rounding the domain outward). Vertical dragging is fullscreen-only (the card in the tab has `touch-action:pan-y` because the page under it has to stay scrollable), which the paint reads off `data-chartfull` on the wrap. `chart-reset` (or a double-click) is the one way back to auto.

**There are two of that chart, told apart by scope.** `"main"` is the Progress tab's; `"ex"` is the copy at the bottom of the exercise detail window (`exWindowProgress`, fed by `exerciseHistory`), which can sit on top of the Progress tab. The scope is the value of the `data-linechart` / `data-linedetail` / `data-charttoolbar` attribute and the `data-scope` on every chart button, and it keys the series (`chartState.line` / `.exLine`), the zoom (`ui.chartView[scope]`), the selection (`ui.chartSel[scope]`) and which one `ui.chartFull` has blown up. Anything new that touches the chart has to carry the scope with it, or the two graphs will start redrawing each other.
- **Under that graph is the ledger it was drawn from** (`exerciseHistory().sessions` → `exWindowHistory`). The graph says where a lift has got to; the list says what you actually did, newest first, every set written out in the unit it was logged in. **A row is a DAY, not an entry**: two entries of the same lift on one day are one session's work and nobody remembers them as two, so they are merged, and the session's headline number and its PR flag are taken from the FIRST of its points to reach the day's best (taking the last would call a day that opened with a PR and then backed off a "match" of itself). Both readings come out of the one `exerciseHistory` call for the same reason the two graphs share a scope: a list and a graph answering different questions about one set of facts must never answer them from different facts. Rows past `EX_HISTORY_PAGE` are folded away behind one tap (`ui.exHistAll`), because somebody who has benched for two years has a hundred of them and a hundred cards would make the graph the thing you scroll past. The sets themselves come from **`outingRows`, shared with `renderLastTime`**, which is the same question ("what was that session") asked from two places.
- **Tapping a session goes to that day in the log** (`open-log-day` → `ui.logJump` → `flashLogDay`), because a date is a session you trained and the rest of what you did that day is most of what you came back for. Sending someone to a date is not the same as showing it to them, so the Log tab's history card carries `data-day` and the arriving frame scrolls to it and lights it for a moment; the marker is spent on that frame and the class goes on the node rather than into the HTML, or `render()` would replay the flash on every keystroke afterwards. A workout window in the way is closed the way its own back arrow closes it, parking the day, which is why the hint under the list says so *before* it is tapped and why the destination is set after that back-out rather than before (a plan saved on the way out lands on the calendar and would otherwise overrule the jump).
- **The 1RM calculator tab** (`renderCalc`) is stand-alone: nothing it does is logged. Its maths is `calcPct`/`calcReps` at the top of `app.js`, the same anchored Wathan curve the log runs on, read forwards and backwards, and its tables are built from the *unrounded* max so they round exactly once. The curve flattens onto an asymptote near 49.6% of the max, so `calcReps` returns `Infinity` below that and the percentage table prints `30+` rather than inventing a rep count.
- **Strength standards are a lookup, not a feed** (`renderProgStandards` and the STRENGTH STANDARDS block in `app.js`, data in `standards.js`). The Progress tab's second segment, the old `PLACEHOLDER_RANKS_SLOT`, answers one question about one lift: pick it, say what you weigh and what you lifted, tap. Seventy-one lifts × two sexes × nineteen bodyweights is 12,780 numbers, and **any amount of it on screen at once is a wall nobody reads**, which is why there is no ambient rank anywhere in the app and why anything new that shows one still has to go through `stdCheck()`. Nothing here is logged and nothing here writes to history, exactly like the calculator tab.
  - **The lift field takes a max OR a set, and they are the same answer** (`f.mode`, `stdMode` / `stdSetMax` / `stdLiftValue`). The tables are written in one-rep maxes and nobody trains in them, so *What you lifted* switches the field between a 1RM and reps × weight, and a set is folded into a max by `est1RM` — the log's own anchored Wathan curve, reps rounded exactly as `calc-run` rounds them. **That identity is the point**: the rank from 5 × 135 is the rank you would have got by working the max out on the 1RM tab and typing it back in, which is the trip the switch exists to save, and a second curve here would be a second answer. The running est. 1RM beside the two boxes is patched in place while typing like the hints are, and is label-plus-number only — no caption about the formula, per the rule above. The two routes keep their own fields, so flipping the switch overwrites nothing and only throws the last verdict away, and `stdCheck` records the set on `res.set` so the card can name it (`std.fromSet`): a rank quoting a number nobody typed cannot be checked by hand. A rep-count standard has no max to estimate and never sees the switch.
  - **The five levels are renamed in the labels only.** The source's beginner/novice/intermediate/advanced/elite are `STD_LEVELS` = wood/gold/diamond/titanium/vibranium, drawn in `--tier-*` (per theme, in the THEMES block of `styles.css`, because a tier name has to read on a near-white card too). Nothing about a tier is persisted, so the words can change freely.
  - **It refuses to guess two things.** `settings.sex` starts `""` and the check stays disabled until it is answered, because the tables are split and a default is not a preference, it is the wrong table. It is asked in the one place it is used and is deliberately *not* in Profile. And the lift number is only ever pre-filled from the log, never for a rep-count standard on a lift logged in reps × weight: "your best set of pull-ups at bodyweight" is not in there to be read. The pre-fill is an est. 1RM, so it fills the 1RM route only; the set route starts blank, because it is for the set in front of you rather than one already on record.
  - **WHICH standard a lift of yours answers to can be said by hand** (`stdSlugFor`, `ex.std`, the *Strength standard* row in `exWindowStandard`, and the picker's `{ex}` mode). `STD_MATCH` is keyed by the shipped `default-N` ids and can never reach further than the built-ins, so a custom exercise, a variation and a built-in somebody rebuilt by hand were all invisible to the standards tab — which is most of the library for anybody who has been using the app a while. The manual answer wins and is stored **on the library row**, which is what makes it per PROFILE without a line of code saying so: a library belongs to one profile, the same movement is not even named the same in two of them, so a link made in one is meaningless in another and never travels to one. It rides along in sync and in a backup because it is part of the row, and needs no collection of its own on the wire — which also means no change to the server's `COLLECTIONS`, and an old build simply carries the field without reading it. **`""` is a real answer** and means *not this one*, so a built-in tied to a lift you do not do it as can be untied and stays untied; deleting the field instead would hand the row straight back to `STD_MATCH`.
  - **ONE PRESS, FROM A LIFT TO A RANK** (*Check how strong you are* → `ex-std-check`, drawn by `exWindowStandard`). Getting an answer out of the standards tab used to be five steps, four of which the app could do itself while you were stood on the lift's own page: it knows the lift, it knows your best set, it knows your bodyweight and it knows your sex. So the button fills the form in and **runs the check**, lands on Progress → Standards and scrolls the rank card into view (`ui.stdJump` / `flashStdResult`, the same one-shot shape as `ui.logJump` / `flashLogDay`). The set goes in by the **set route**, never as a pre-computed max, so the card names the set it came from and the verdict can be checked by hand. `stdBestSetFor` picks THIS row's best set — not the best of everything tied to the same standard — by the highest est. 1RM, which is both the measure the graph ranks by and the number the tables are written in, so there is no second opinion to have; a rep-count standard is ranked on reps and reads only a bodyweight-kind exercise. The button is **disabled, not hidden**, with no link or no sets logged, and the line under it says which of the two is missing: a control that is not there teaches nothing. This does not make a rank ambient — it still goes through `stdCheck`, which remains the only way one is ever produced.
  - **The form remembers itself, per profile, and the bodyweight is whichever is newer** (`settings.std`, `stdForm`, `stdLatestBw`). `ui.std` **is** `settings.std` rather than a copy of it, so every keystroke is already in `state` and the next save writes it, with nowhere for the two to drift apart; it is per profile because `settings` is, and it is deliberately not one of the settings keys that sync, being the state of a question box rather than part of anybody's training. Two places in the app know what you weigh, so the rule is simply the later of the two: a value that CAME from a check-in follows the newest check-in, so logging one is enough to make every rank current, while a value TYPED here is a what-if that holds against check-ins already on record and gives way to one logged on a later day. `bwOn` is the day the figure in the box is true for, which is what makes those two cases one comparison instead of a special case each.
  - **A pre-fill hint is a claim about provenance.** "Your best from the log" / "your check-in on 12 Aug" stop being true the moment the field is typed over, and typing never causes a render, so `handleBind` retires both hints in place (`stdLiftHint` / `stdBwHint`). Bodyweight is read from the latest Body check-in and never written back; typing over it is a what-if.
  - **Thresholds are converted and rounded once, on the way out** (`stdThresholds`), so the ladder and the verdict can never disagree. Bodyweights between two 5 kg rows are interpolated; past either end of the grid the end row is used, because there is no data out there to extrapolate from.
- **First-set-best-set is gone, shape and all** (migration v15). v5 took the SETTING away and left the SHAPE: an entry logged in that mode was a total-set count plus the numbers of one top set, with no `setList`, and every screen that could meet one carried a second branch for it — a second set of form fields, a *Convert* button, a "top set of 4" caption, its own word in the summary line. Ten code paths and eight strings kept alive for a prototype that was never chosen and that nothing had written to since v5. v15 brings the rows across instead of leaving them behind: the recorded top set becomes set 1 and the entry is re-derived from it, in the log, the plans, the parked days, the unlogged rows and the crash snapshot. **The sets that were never written down are NOT invented** — four sets of which one was recorded come back as the one that was recorded, which is the same claim the old row made in words said as data instead; repeating the top set four times would put three sets in somebody's history that nobody logged. Weekly volume for those weeks therefore counts what was recorded rather than what was claimed, and nothing else moves, because est. 1RM, the PR badges and the graph all read the best set and the best set is the set that came across. `isDetailed` survives, and the question it now asks is about **cardio**: a cardio session is minutes × effort and is the one kind that legitimately has no set list.
- **A MIGRATION IS THE ONE PLACE WITH NOBODY WATCHING, AND IT MUST NOT THROW** (`readProfileState`'s two catches, `unreadableWhy`, and `function uid()` sitting above `newSet` rather than beside the UI state). `hydrate(JSON.parse(raw))` is one `try`, so **an exception anywhere in `migrate` is indistinguishable from bytes that are not JSON**, and both come out as *the training saved on this device will not open*. v15 shipped and did exactly that to real saves: `uid` was a `const` four thousand lines below the `let state = loadState()` that runs at module level, nothing had ever called it that early before, and the first legacy row needing an id hit its temporal dead zone. Perfect data, every entry intact, reported to its owner as damaged. Two rules came out of it. **Anything a migration reaches for is declared above `newSet`, and `uid` is a `function` so that where it sits can never mean this again.** And **a migration assumes no shapes**: `rows()` in v15 drops what is not a record and coerces what is not a list, because a value that every screen reads as an array of records is not recoverable data in any other form, and passing it onward only moves the crash into a renderer. The failure is also now told apart from real corruption (`unreadableWhy`, `profiles.unmigratable`): the writes are still held either way, since a half-migrated state is not something to write back, but the app no longer blames somebody's training for a bug in its own upgrade code.
- **Compound vs isolation is gone, and so is `type`.** What a lift is logged in is `kind` (see above), declared by its group and overridable per exercise. `type` is only still READ, as the legacy path in `exKind` for library rows saved before v13 that carried `"Cardio"` there; nothing writes it any more, and old `"Compound"`/`"Isolation"` values are read by nothing at all.
- **1RM, Progress and Standards are three questions about your numbers behind one tab** (`renderProgress`, `ui.progSeg`). The calculator had a tab of its own in the bottom nav and did not earn one: it is a form you fill in twice a month, and it sat one row away from the two screens it belongs beside. All three are the same shape of thing — none writes to the log, all read it — so it is the Progress tab's FIRST segment now, first because it is the one that needs no history behind it. `resetTransient` still lands the tab on Progress, which is the tab's own name and what the nav icon promises, and `ui.calc` / `ui.calcResult` are still deliberately not cleared by it, exactly as the standards form is not: a question you asked should still have its answer when you come back. The segment control is handed INTO `renderCalc` rather than stacked above it, so there is one padded container and not two arguing about the gap under the pills. The slot it left in the nav is chat's.
- **CHAT IS THE ONE THING IN THE APP THAT IS NOT TRAINING, AND IT IS NOT IN `state`** (the CHAT block in `app.js` above the viewport engine, `api/src/chat.js`, migration `0006_chat.sql`, and the chat half of `zenofit-cloud.js`). Everything else here belongs to a PROFILE: a set, a goal, a check-in, even the roster those profiles sit in. A message belongs to an ACCOUNT — to the person — and it travels to somebody else. Putting it in `state` would have filed a conversation under whichever profile happened to be open, shared it with whoever holds that profile's code, sent it up as an `item`, and carried it away inside an exported backup that people hand to each other; restoring last month's backup would have restored last month's conversation. So it has its own tables, its own routes, its own client cache under `zenofit:chat`, and no contact with `items`, `profiles`, seeds or grants. **Nothing about chat is on the path of anything the app already did**: the log, the sync engine and the roster are untouched, and an account that never opens the tab pays one request per poll and nothing else.
  - **A chat needs an ACCOUNT, not a device** (`chatSignedIn`). A device token is enough to search — so the screen works while somebody is still deciding to sign up — but an install that never registered has no username, so there is nothing to find them under and nothing to address. The tab says that and offers the one thing that fixes it, rather than an empty list.
  - **Somebody is found by USERNAME, from the start of it** (`GET /v1/users/search`). A username is the only name an account has that is unique and typed by its owner. It is deliberately a PREFIX and not a contains: a substring search over every account is a directory, and "who is on this app" is not a question a stranger gets to ask. Under two characters is refused rather than answered, only claimed accounts appear, and you never find yourself.
  - **THE WHOLE TAB UNDER THE SEARCH FIELD IS ONE PATCHABLE BOX** (`chatBodyHTML` / `chatPatchBody`), and that is not tidiness, it is the fix for a bug this shipped with. The tab shows conversations with nothing typed and results with something, and that swap was done with `render()` — which rebuilds `#app`, throws away the input the caret is in, and drops focus. So the FIRST letter typed and the LAST one deleted each kicked you out of the field: you typed one character, the keyboard shut, and you had to tap back in for the second. The bullet above it in the source said "NOTHING here calls render()" while the code two lines below did, which is the whole lesson — **every search in this app patches a container and never renders** (`libq`, `pickq`, `stdq`, `attachq`, and now `chatFind`), and the clear button is always in the DOM and shown or hidden in place for the same reason, since drawing it only when there is something to clear changes the FIELD'S own markup on the first keystroke.
  - **Opening a chat is FIND-OR-CREATE and there is no second verb** (`POST /v1/chats`, `chat_threads.dm_key`). Tapping a name means "take me to the conversation with this person", which is the same request whether or not it exists yet. `dm_key` is both user ids sorted and joined, with a UNIQUE index on it, so the two people arriving in either order land on one thread and two phones tapping at the same moment cannot produce two half-conversations. The insert races against that index on purpose and takes whichever row won.
  - **THE SERVER STAMPS A MESSAGE, and `clientId` is what makes a retry safe.** `created_at` is the server's clock for the reason `items.updated_at` is: a phone three seconds off must not be able to sort itself above the reply it is answering. The app draws a message the instant it is typed (anything else shows an empty composer and no message for two seconds on gym wifi, which reads as having lost it) and sends it carrying its own id; the server refuses a second message under the same one and hands back the row that already landed, and `chatMerge` upserts by id **and** by `clientId` so the optimistic copy is replaced rather than duplicated. A send that fails **keeps the message on screen, marked, with Retry** — throwing away what somebody typed because a request failed is the one outcome that is never acceptable. A half-typed one is kept too, per thread, in the cache rather than in `state.drafts` for the reason above (`chatDraftOf` / `chatDraftSet`).
  - **UNREAD IS DERIVED, NEVER STORED.** `chat_members.last_read_at` is the only thing kept and the count is a `COUNT(*)` past it, because a stored counter is a second opinion about the messages and the one thing worse than a wrong badge is a wrong badge nobody can explain. **Sending is reading**, so your own message never comes back as something you have not seen; looking at a thread marks it read (only while the app is actually on screen — a thread left open behind a lock screen has not been read by anybody); and the mark only ever moves FORWARDS, so a late request from a screen that has since scrolled cannot bring the badge back. It shows as a count on the nav icon, beside where a running timer puts its dot, because "three waiting" is a different decision from "one".
  - **A NOTIFICATION IS SENT BY THE SERVER AND SHOWN BY `sw.js`, AND ONLY THE PHONE KNOWS WHETHER TO SHOW IT.** The push goes out from the send route rather than being polled for, because the whole point is reaching a phone with the app shut, and it never delays the reply: a push service being slow must not make sending slow, and a stored message has been sent whether or not the other phone rings. **`sw.js` skips the notification when a window of the app is FOCUSED** — the one case the spec allows — and posts the push to the page instead, which is what the user is already looking at; the page then polls, so a message travels exactly one road and there is no second copy of it to disagree. "A window exists" is deliberately not the test: an installed app behind the lock screen still has its window, and that is precisely when a message has to ring. **A timer is not treated this way**: it already rings locally when the page is alive (`fireTimer` cancels the server's copy on the way past), so a timer push arriving at all means the page did not get there. They also want opposite things from a notification and the server says which is which — a timer sets `requireInteraction` because missing it ends the set, a message does not, because it is still there when you pick the phone up and a notification that refuses to go away is one people turn off.
  - **ONE SWITCH, FOR THE WHOLE APP, ON THIS DEVICE** (the NOTIFICATIONS block above TIMERS: `notifyState` / `notifyEnable` / `notifyDisable` / `notifySetKind` / `renderNotifyWindow`, `zenofit:notify`, `off_kinds` on `push_subs`, `PUT /v1/push/prefs`). There were two buttons that looked like two features — *Turn on notifications* in Settings and a strip in the chat tab with its own *Turn on* — and they were the same button: both asked for the browser's permission and subscribed this device to push, and that ONE subscription is what a rest timer rings through AND what a message arrives through. A third place asked too: the first Start of a timer requested permission and stopped there, without the subscription, so "allow" bought nothing that worked with the app closed. Now there is one window, *Settings → Notifications*, holding the switch, a per-kind choice (rest timers, messages) and the check that used to be `push-test.html` — a separate document that looked like another app, now gone. The chat tab shows a **doorway** into that window, only while nobody has decided (`want === null`); somebody who switched notifications off made that choice in the place it is made. The first timer Start, on an undecided device, asks through the same `notifyEnable`. A device whose browser already granted permission (the old timer prompt) and was never switched off is subscribed quietly at launch — no prompt can appear once the answer is not `"default"`. **The choice is the DEVICE'S** (`zenofit:notify`, outside `state`, never synced, not in a backup), like a theme. A kind turned off is sent with the subscription and filtered in `sendToUser`, so a push the device said no to is never sent at all — the alternative, a push the phone has to swallow, is one Safari revokes the subscription over after a handful. It must come from a real tap (iOS refuses a prompt that was not, and Chrome penalises a site that asks on load), and every reason it cannot be offered is said in words somebody can act on: on iOS the app has to be installed to the home screen first, and a permission already refused can only be undone in the browser's own settings.
  - **Polling is three paces on one timer** (`chatWantedGap`): six seconds inside a conversation, twenty on the tab, ninety anywhere else, where all that is at stake is the nav badge. A hidden tab polls not at all, coming back to the app polls at once, and a push handed over by the service worker beats whatever the pace was. It is silent by design, exactly as `syncQuiet` is, and it never re-renders unless something landed — and not even then while a field has the caret in it (`syncTyping`), since `render()` rebuilds `#app` and a repaint mid-word from a timer nobody can see would throw away what somebody was typing. **A poll that WORKS also retires the error the last one put on screen**, or the offline banner outlives the outage and sits above the messages that just arrived.
  - **THE CACHE CARRIES THE ACCOUNT IT WAS BUILT FOR** (`chatRead`), and a cache stamped for somebody else is dropped rather than drawn. Two people share a phone; one signs out and a friend signs in. Signing in or out calls `chatForget()` outright, and this is the belt to that braces. **Messages are also the one thing signing out clears off the phone**, which is consistent rather than an exception: they are not this device's training, they are the account's conversations, and the server still has every one of them for whenever somebody signs back in. The cache is capped (`CHAT_KEEP`), pruned to the threads still in the list, and losing it loses nothing.
  - **A searchable username needs the other half of the deal, so there is a BLOCK** (`chat_blocks`). It is one direction in the table and both in effect — one that still let their side send would only be a filter on my own screen — it takes the person out of search for both of them, and the other end is told nothing. **Mute is quiet, not gone**: still delivered, still counted unread, just not announced. **Leaving is mine only**: the other person keeps their copy, the messages stay where they are, and writing to them again puts the same thread back rather than starting a second one, which is what the confirm says, because "delete" would promise something this cannot do.
  - **Every chat action is on `READ_OK`**, deliberately. A read grant is about somebody else's TRAINING being on your phone; a conversation is neither training nor theirs, and looking at a friend's log must not stop you answering your girlfriend. Nothing in the chat actions writes `state`, which is the test everything else on that list has to pass.
  - **The composer is the only control in the app the on-screen keyboard can bury, and `--pb-kb` is what lifts it.** `index.html` says why the keyboard is left to OVERLAY the app rather than resize it, and names the price; the rule stated there is to lift that one bar off a `visualViewport` measurement, and `applyViewport` now writes that measurement as a `--pb-*` token like every other number the device decides. It is divided by `vpScale` (both sides of the subtraction are screen pixels, the frame is laid out in its own) and written ABOVE applyViewport's early return, which fires precisely when neither the scale nor the width has changed — exactly what a keyboard opening looks like from there. It is spent as PADDING on the conversation layer rather than as a transform on the composer, so the list shrinks by the same amount instead of the composer being parked on top of the newest message; the scroll then chases the bottom (`chatStickBottom`). Anything else reaching for `--pb-kb` should first ask whether it really cannot scroll.
  - **A conversation is pinned to its newest message until somebody scrolls up** (`ui.chatStick`). `render()` restores the scrollTop of anything with a `data-scrollkey`, which is right for reading history and wrong the moment a message arrives, so this overrides it — and scrolling up turns it off, because somebody reading last week's messages has not asked to be thrown back down by a reply landing.
  - **A MESSAGE CAN CARRY A THING, NOT ONLY WORDS** (the THINGS IN A MESSAGE block: `chatBuildThing` / `chatThingCard` / `renderChatView` / `chatImport`, `renderChatAttach` from the composer's ＋, `renderShareTo` from an exercise window, the standards rank card and the preset editor; `kind` / `payload` on `chat_messages` in migration `0007`). An exercise, a preset, a logged day, a personal record, a strength rank, or a photo arrives as a CARD — the way a shared link or a game invite arrives in a messaging app — and tapping it opens it in full, laid out like the library's own exercise window, where an exercise or a preset can be added to your own library (a logged day is added as a preset: a preset keeps exercises, never numbers). **What travels is a SNAPSHOT, never a pointer**: the recipient cannot read your profile and never should. A built-in carries its `default-N` id so the other phone shows it in ITS language (`snapLabel`, exLabelOf's rule for a row not in your library), and a group carries its shipped `key` so "Chest" lands in their chest group even if they renamed it. **A payload is somebody else's data**: every field is read through `pStr` / `pNum` / `pColor` and still escaped, and the server checks only the kind, the size, and that a photo message names a photo uploaded INTO THAT THREAD. `body` is required for every kind: it is the one line the notification, the chat list and an older build show, so a phone a version behind reads "Exercise: Belt Squat" rather than a blank. **Adding one is the only write chat has**, and `chat-import` is therefore the one chat action deliberately NOT on `READ_OK`. It never overwrites: a name you already have is offered as *Open yours* or *Add a copy* (numbered beside it), because a name is an exercise's identity and your log is filed under it; a built-in you deleted comes back AS the built-in. A photo comes by id and `photoPass` fetches it, so an imported exercise arrives with its machine. **A chat photo is not a library photo**: it is uploaded into the thread (`POST /v1/chats/:id/photos`, id = hash of thread and picture), readable only by the thread's members, deleted with the message, scaled to 1280px, and held in memory — never in the chat cache, which lives in localStorage beside everybody's training — for as long as the send takes (`chatUploads`); a photo message the app closed on mid-send is marked failed on the next load and says to send it again (`chatRead` turns anything still *pending* at load into *failed*, which it is — nothing resumes a send across a reload).
  - **UNSEND IS DELETE FOR EVERYONE, AND NOTHING IS LEFT IN ITS PLACE** (`chatUnsend`, `DELETE /v1/chats/:thread/messages/:id`, `deleted_at`, `chatDrop` / `chatReconcile`). Sender only; the row stays on the server as a tombstone (body and payload gone) because the other phone may already hold the message and has to be told, and a row that is gone cannot be reported. No page ever carries an unsent message, not even as a "deleted" row. The other phone learns two ways: a `since` poll lists what was unsent since the newest message it holds (`unsent`), because that message was fetched long before and its `created_at` never moves; a tail or a history page is a COMPLETE WINDOW, so anything held inside it that the page does not mention is dropped — strictly inside, since messages sharing the boundary millisecond may have fallen just outside the page. Messages still leaving THIS phone (pending, failed, `local:` ids) are never touched by either. Everything that counts or previews reads live messages only, so the unread badge, the list's last line and its order fall back to what was there before; `last_message_at` is recomputed, and a thread with nothing live in it leaves the list of anybody who never opened it (`opened_at`, set on the row of whoever called `POST /v1/chats` — which also fixed tapping a name putting an empty chat in the OTHER person's list). The notification already in the shade is closed the moment the page hears (`chatCloseNotifs`); a phone cannot be un-rung, and a push to retract one is exactly the silent push Safari punishes. A failed unsend puts the message back and says why. **The actions on a message are behind a long press** (and a right click on a desktop), because a tap already opens a card or a photo: one delegated listener, a 460 ms timer cancelled by movement, and the click that lifting the finger lands on the menu's own backdrop is swallowed in the capture phase. `.pb-msg` turns off the browser's own long-press (selection, the iOS callout); *Copy* is in the menu instead.
  - Groups do not exist yet and the schema does not need changing for them: `chat_threads.kind`, `title` and a members table are already there, and the send route already fans out to every member. What a group needs is a UI and a decision about who may add whom, neither of which is in here.
- **Theming** is entirely CSS custom properties (`--bg`, `--text`, `--gold`, etc.) swapped via `data-theme="dark"|"light"` on `<html>`, set by `applyTheme()` and mirrored by the anti-flash inline script in `index.html` (reads the last saved theme before first paint to avoid a flicker).
- **Images** (exercise photos, chat photos) are downscaled and re-encoded client-side in `readImageScaled()` before being stored or sent — 1000px for an exercise, 1280px for a chat photo, WebP where the browser can encode it and JPEG where it cannot (Safari silently hands back a PNG for WebP, so the result is checked, and the smaller of the two is kept). A camera photo of about a megabyte goes up as roughly 60 KB.
