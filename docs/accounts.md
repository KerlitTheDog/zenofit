# Accounts

Usernames and passwords (`api/src/auth.js`), tokens, the limits on making identities, logging out, the account sheet, and deleting an account (`api/src/account.js`). Read this whole file before changing anything it describes, and update it in the same commit when that behaviour changes (CLAUDE.md, *Docs*).

- **An account is a device that got claimed** (`api/src/auth.js`, migration `0004_accounts.sql`, `register`/`signIn` in `zenofit-cloud.js`, `renderAccountSheet` in `app.js`). Identity started as one row per browser install: a token in `zenofit:device`, no way back in once it was gone, and a synced profile stranded on the server the moment a phone died. A username and a password are that **same user row**, claimed: nothing is moved and there is no second users table, so `profiles.owner_id` keeps pointing at what it always pointed at and somebody who registers today keeps what they synced yesterday. Registering *with* a device token claims it; registering without one makes a fresh account, which is what a second person on a shared phone wants. **The password never reaches the server.** A Worker on the free plan gets 10ms of CPU per request, which is less than any honest password hash needs, so the browser runs PBKDF2-SHA256 at 210,000 iterations and sends 256 bits of derived key; the server salts and SHA-256s that once, which is cheap and sound because the thing it hashes is no longer guessable. **The client's salt is the lower-cased username**, not a random value, so a login needs one request instead of two and there is no endpoint that answers "does this account exist" before a password is offered: the cost is that two identical passwords under different names share nothing, which is fine, and usernames are unique so no two people share a salt. If `PBKDF2_ITERS` ever changes on one side, `test/smoke_auth.py` must change with it or every login fails while every test passes. **Tokens moved to their own table** in the same migration: `users.token_hash` held exactly one, which was right while a user WAS a device and wrong the moment you can sign in somewhere else: the second phone's login would have silently signed the first one out. The migration back-fills every existing device's token into a row of its own, so deploying it signs nobody out. `username_lc` carries the UNIQUE index because nobody remembers the case they typed. **There is no password reset**: there is no email to send one to, and the sheet says so before you pick one. **Logging out ends the token on the server too** (`POST /v1/auth/logout`, sent by `signOut` and not awaited, so logging out with no signal still logs out): it used to forget the token on the phone only, and every token ever issued stayed good for ever. It revokes the one token it came in on, so the account's other devices stay signed in. **Wrong passwords are counted** (`overLimit` / `recordMiss` in `limits.js`, shared by login and Storage check's verify): ten per address and name, a hundred per address, per fifteen minutes, and successes are never counted, so somebody logging in correctly is never refused because of somebody else. **Only a miss on a name that has an account is counted**: the form always tries to log in first, so every new person's first try is a refused login for a name nobody owns, and counting those locked a gym's wifi out after a hundred sign-ups (the reply is the same either way, and whether a name is taken is no secret: `/v1/auth/available` answers it). The address is `addressKey`'s, so IPv6 counts by its /64 here too. The app says so in words (`acct.errTooMany`) rather than blaming the signal. **Making an identity is counted too** (`limited` keyed by `addressKey` in `POST /v1/devices`, `POST /v1/auth/register`, `GET /v1/auth/available` and `POST /v1/profiles`; per account in `GET /v1/users/search`, chat.js), because without it a script could mint accounts by the thousand, each with its own photo quota, out of the free plan's daily D1 writes. Per hour: 100 devices, 100 registrations, 200 name checks and 300 new profiles per address, 300 searches per account, as `[vars]` in `wrangler.toml` (`LIMIT_*_PER_HOUR`) with the same numbers in the code as the fallback; refused as 429 `too_many_signups` / `too_many_lookups` / `too_many_searches`. A profile create is cheap (a row and a seed) and was unbounded, so one device token could loop it until the table filled and every write failed for everyone; only a real create counts, so a lost-reply retry is free, and the ceiling clears a gym class each naming a first profile on one wifi. Sized so three full runs of the eight suites from one address fit in an hour (one run mints 28 devices and makes 24 registrations that count) and a gym class can sign up on its own wifi. Only a request that reaches the database is counted, and an IPv6 address counts by its /64. The checks that trip them run only against a local `wrangler dev` with `ZENOFIT_LIMITS=1`, each from an address of its own (`CF-Connecting-IP`, which wrangler dev passes through and Cloudflare overwrites), never against production, where they would lock the tester's own address. **The same `limited` guard caps three more loops**: booking a rest timer (`timer:<user>`, 30 a minute), asking for a test notification (`push:test:<user>`, 30 an hour) and the profile create above, none of them a number a person meets. **A push subscription has to name a real push service** (`pushEndpointOk` in `index.js`, checked in `POST /v1/push/subscribe`): the endpoint host must end in one of the browsers' four push suffixes (`PUSH_ENDPOINT_HOSTS`), its `p256dh` and `auth` are held to 256 characters (they are fixed-size crypto, not a place to park data), and only an account's newest `MAX_SUBS_PER_USER` (20) devices are kept, because the Worker signs and POSTs the encrypted payload to whatever host a subscription names and nothing else should ever be that host. **A spent counter does not stay** (`sweepLimits` in `limits.js`, run by the daily cron beside the photo sweep): `rate_limits` and `join_attempts` rows whose window began more than 25 hours ago (`LIMIT_ROW_KEEP_MS`, the longest window plus a day) are deleted, because a login key is an address and a username. **A login unused for half a year ends** (`sweepTokens` in `index.js`, the daily cron, `TOKEN_IDLE_MS`), and a push subscription under a user with no login left goes with it. **A phone whose token the server no longer knows is logged out, and nothing on it is deleted**: `zenofit-cloud.js` dispatches `zenofit:signed-out` on a 401 `unauthorized` (only for the token still stored), and `leaveAccount(true)` takes the account off the screen without telling the server, keeps the chat cache (a half-typed or unsent message survives logging back in; `chatRead` drops a cache built for somebody else), turns push off on that phone and shows `login.signedOut`. It used to stay signed in with the server's raw sentence on screen while three chat paths wiped the chat cache on any 401; those three `chatForget()` calls are gone.
- **An account is what holds the profiles, so there is no app without one.** Every profile belongs to exactly one account's list (`profiles.userId`), and the account's list is the same on every device it logs in on. Sharing is the one way a profile reaches a SECOND account, and it arrives there under *Shared with you*, never mixed in with that account's own.
  - **The account sheet is who you are, the account's profiles, and Log out** (`renderAccountSheet`, only ever drawn logged in). It used to list every profile on the PHONE with a status word each (*back up*, *get it*, *on this phone*, *synced but not to this account*) and a button for whichever needed doing; that was the app's bookkeeping on display, and it is gone along with acct-backup, acct-pull and refreshCloudProfiles. Under Log out, quieter than it and on the no-profiles screen too, sits *Delete account* (see the next bullet).
  - **DELETING AN ACCOUNT IS GLOBAL, AND IT IS THE ONE THING HERE THAT DESTROYS A SAVE ON PURPOSE** (`DELETE /v1/me` and `api/src/account.js`, migration `0010`; `renderDeleteAccount` / `acct-delete-go` / `accountErased` in `app.js`; `deleteAccount` / `forgetAccount` / `accountGone` in `zenofit-cloud.js`). Everything else in this app is built so that nothing destroys training quietly, and logging out deletes nothing from the phone; this is the explicit exception, behind the account's PASSWORD (a token is a thing left lying around on a borrowed phone), a confirm, and a sheet that says what goes and what stays before it asks. **The server goes first and the phone only after it**: `deleteAccount` in `account.js` is ONE D1 batch, so a failure leaves the account whole and signed in, and nothing on the phone is touched until the server says the account is gone. What goes: the user row (so the username is free again), every profile it owns (including ones it deleted earlier, which were only tombstoned), with their items, seeds, grants and photo holdings; its grants on other people's profiles; its push subscriptions, timers (their Durable Object alarms called off first), tokens and rate-limit rows; every picture it uploaded that nobody else holds; and its conversations. **A DM goes whole, for both people** (both sides' messages, its pictures, both member rows, the thread), because a DM exists because of the two of them and keeping half would leave somebody writing into a thread with nobody in it; a group (none can be made yet) would keep going, with this account's messages there unsent the way `chatUnsend` does it and only its membership gone. What stays, deliberately: sets it logged into somebody else's profile through a write grant (that is their log now), a picture another account's library or card still holds (content ids mean it is theirs as much as it was this one's; its `owner_id` is left naming nobody), and the copy of a shared profile on a grantee's phone, which leaves their list on their next roster pass exactly as when an owner deletes one profile. **The statements are set-based, never a loop per profile, thread or photo**: the free plan allows fifty D1 queries a request and the batch is ~23 whatever the account holds, and the ORDER inside it matters, since later statements find their rows through tables earlier ones have not emptied yet: see the comments there before moving one. **Every other phone signed in to it finds out** (`gone_tokens`): the account's token hashes are kept, and a request carrying one is answered `401 account_deleted` rather than the bare `unauthorized` a logged-out token gets, because that phone is holding the account's training and a plain 401 says only "log in again"; `zenofit-cloud.js` dispatches `zenofit:account-deleted` (only if the refused token is still the one stored) and `accountErased` takes the account off that phone too. **`accountErased` is the local half, on the deleting phone and every other one**: every save in the account's list AND every save the owner index or a sync record says is its (including ones it logged out of and left for Storage check), their sync records, its queued removals, its roster key, its chat cache and fetched pictures, everything in the shade, and the credential, while the phone's own things stay (theme, notification choice, push subscription) and so does every other account's save. `state` and `profiles` are emptied before the keys go so no debounced save writes the one on screen back, and `erasedIds` makes `writeProfileState`, `syncSet` and `ownerSet` refuse the erased ids for the rest of the session, because a pull or a roster pass already on the wire would otherwise put one straight back; `chatWrite` and `photoCachePut` likewise keep nothing with nobody signed in. A wrong password is **403 `bad_password`, never 401** (401 means the token is no good, and the app treats it that way), and the misses count against login's own limits (`loginMissed`), so this is not a way round them. `smoke_delete.py` pins the server half.
