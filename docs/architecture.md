# How the app is built

The single-file SPA in `app.js` and the machinery every screen shares: `state` and `ui`, `render()` and `patch()`, event delegation, sheets, drag to reorder and reorder modes, the viewport engine, accessibility, migrations, theming, the Refresh button and the update banner, and what the front-end files are. Read this whole file before changing anything it describes, and update it in the same commit when that behaviour changes (CLAUDE.md, *Docs*).

The app itself lives in five files: `index.html` (the shell and its Content Security Policy; its two small scripts are files of their own, `theme.js` for the theme-flash prevention and `sw-register.js` for the service worker and the update banner), `styles.css` (all styling, theme-driven via CSS custom properties), `i18n.js` (every string, in three languages), `standards.js` (pure data: the StrengthLevel strength-standards tables), and `app.js` (the entire application). Beside them, `zenofit-cloud.js` is the only code that talks to the network and `api/` is the Cloudflare Worker it talks to (accounts, sync, push, timers, chat), both optional by design: the app runs unchanged with the API unreachable. The icons are `icons.js`: only the glyphs the app draws (about 130), from Tabler Icons v3.49.0, outline, with `tabler-icons.LICENSE.txt` beside it, and it is in `SHELL`: nothing the app runs comes from a CDN, because a script from another server runs with the account token in reach. `icon()` writes the SVG straight into the template, so a glyph is in the frame the moment its HTML is and nothing draws icons in a second pass. A new icon is copied in by hand, as the comment at the top of `icons.js` says. It replaced the whole Lucide set (357 KB, 82 KB compressed, for the same icons; 23 KB and 6 KB now), whose look read as a template and which redrew every placeholder in the document after each render. **The fonts are ours too**: Barlow and Barlow Condensed are `fonts/*.woff2`, the very files Google Fonts served for the weights the app uses (latin and latin-ext subsets only, since no language here needs Vietnamese; Barlow has no Cyrillic, so Ukrainian uses the system font), declared at the top of `styles.css` with Google's own `unicode-range` blocks, all in `SHELL`, licence `fonts/OFL.txt`. Google Fonts was handed every user's IP address on every launch and needed a connection on the first one. A new weight is that weight's woff2 files fetched the same way, never an `@import`. **The page has a Content Security Policy** (the `<meta http-equiv>` at the top of `index.html`, a meta tag because GitHub Pages cannot send headers): scripts from this origin only and no inline script anywhere, inline styles allowed because the templates carry style attributes, images from here and `data:`/`blob:`, connections to the API and to a local Worker on port 8787, frames from YouTube's no-cookie player only (`www.youtube-nocookie.com`, the tutorial videos: the ordinary www.youtube.com embed let Google set its tracking cookies on anybody who merely opened an exercise). **Any new external origin, and any inline script, updates that policy in the same commit**, or it fails silently on every phone. A local test points the app at `wrangler dev` with a same-origin file setting `window.ZENOFIT_API`, never an inline one. It was proven by walking every tab and the main windows in headless Chrome with zero violations, plus a deliberate inline script being refused.

**Every dimension that answers to the device goes through the viewport engine, and nothing else measures the screen.** `applyViewport()` in `app.js` (the VIEWPORT ENGINE block above `render()`) is the only code that reads the device: it writes `--pb-scale` and `--pb-frame-w` onto `<html>`, and the matching block in `styles.css` derives everything else from them: the frame's height, the safe-area insets in the frame's own units (`--pb-sat` / `--pb-sab`), and the chrome measurements stacked on the bottom nav (`--pb-nav-h`, `--pb-header-pt`, `--pb-content-pb`, `--pb-fab-b`, `--pb-toast-b`). Three rules keep it honest:

- **Never write a raw pixel offset against the top or bottom of the screen again.** A top bar's first padding is `var(--pb-header-pt)`, not `14px`; anything sitting above the nav is `calc(<clearance> + var(--pb-sab))` or one of the `--pb-*-b` tokens. Those numbers are what the notch and the home indicator are subtracted from, and a hand-written `14px` is a control the user cannot reach on a notched iPhone, which is exactly the bug the engine was written for.
- **A phone renders at scale 1, by design.** The frame takes the full width it is given up to `VP_FLUID_MAX` (480pt) and only scales past that, so every handset draws the design at the size it was authored at; scaling exists for tablets and desktops, which are the only screens wider than that. If you change `VP_FLUID_MAX`, `VP_REF_H` or `VP_SCALE_MAX`, you are changing what happens on a tablet, and you should check a phone anyway.
- **A pinned footer's clearance is MEASURED, never written down** (`fitScrollFooters` / `FOOTER_CLEAR`, and the `data-footer-for` on the footers in `renderWorkoutSheet` and `renderEntryFields`). Both of those screens park their save button over a scrolling list and fade the list out under it with a gradient, and the clearance the list got underneath was a hand-written `120px`: the same species of raw offset as the rule above, just aimed at a piece of chrome instead of at the notch. It is right for a footer holding one button and wrong the moment it holds more: the workout sheet's grows by *Save as preset* and up to two lines saying what is still unlogged, copy that WRAPS, so the right number was never a number at all. Past 120px the bottom of the list came to rest under the *transparent* top of that gradient and the caption printed straight across the timer dials' labels. The footer now declares the list it sits over and its height is read off the finished frame, beside `flashLogDay`: the glyphs and charts settle the final heights. **This measures CONTENT, not the device**, which is why it is not in `applyViewport` and does not divide by `vpScale`: `offsetHeight` and the padding written back are both in the frame's own units, so the scale cancels, and the safe-area inset is already inside the height because the footer's own padding carries it. The `120px` still in the templates is what one pre-measure paint uses and nothing else; a third screen in this shape is an attribute, not another guess.
- **Pointer coordinates arrive in screen pixels; the frame is laid out in its own.** Anything doing arithmetic between an event's `clientX`/`clientY` and a laid-out size (`offsetHeight`, `clientWidth`, an SVG coordinate) has to divide the event side by `vpScale` first, see `moveRowDrag` and the chart gesture handlers. On a phone this divides by 1 and on a tablet it is the difference between a drag that tracks your finger and one that does not.

**`app.js` is a hand-rolled single-file SPA framework**, with no React/Vue/build tooling. Key pieces, in the order they appear in the file:

- **Pure calculation helpers** (`bestSet`, `syncEntry`, `computeBadges`, `dashboardRows`, `weeklyTotals`, `volumeForWeek`, `bodyTrend`, etc.): these are the spreadsheet-formula ports; keep them side-effect-free.
- **`state`** (persisted) vs **`ui`** (transient, in-memory only): two separate global objects. `state` holds workout log, library, muscle `groups`, presets, timers, goals, body measurements, `dayDrafts`, settings; it's loaded via `loadState()`/`migrate()` and written to `localStorage` under key `powerbuild-tracker:v1` via `persist()`/`writeNow()` (debounced autosave, flushed on visibility change / pagehide / beforeunload). `ui` holds open sheets, form drafts, filters, etc., and is never persisted directly, but in-progress drafts (open workout sheet, entry form, set form, body form) are snapshotted into `state.drafts` so a killed/reloaded tab restores exactly where the user left off (see `snapshotDrafts()` and the `restoreDrafts` IIFE at the bottom of the file).
- **One control means "show me what is actually there now"** (`refreshNow` / `swRefreshShell` / `refreshBtn`, the circular arrow in both headers, and the `refresh-shell` message in `sw.js`). Two different things go stale in here and both used to be fixed the same way: close the app, open it again, and if that did not do it, once more. **The training**: a live profile is fetched on the way in and then polled every few minutes, which is right for a phone in a pocket and no use to somebody stood there having just been told a set was logged on the other phone. **The app itself**: `sw.js` answers from cache first and re-fetches behind you, which is what makes it open instantly and work with no signal (and **a cache that fails is treated as no cache, never as a failed request**: a `cache.put` that throws (a full phone's QuotaExceededError) is swallowed and the response still goes to the page, and a Cache Storage that will not even open sends the request straight to the network; a failure to keep a copy used to become a network error, so on the phone with no room to spare the app would not open at all), and it also means a deploy appears on the SECOND launch: nothing on screen ever said so, so what it taught was exactly that habit. From the user's side those are one request, so they are one button: a waiting worker is taken (which reloads), otherwise the shell is re-fetched past both caches and the page reloads **only if something really came back different** (ETag first, an exact body comparison where there is none), and otherwise it pulls the profile in front of them. It is read-only in every sense (it is on `READ_OK`, and the debounce is flushed before a reload can happen), and it holds its spin for 450ms even when the answer is instant, because a spinner that flashes for 40ms is the same thing to a finger as a button that did nothing.
  - **A new version waits for a tap, or for nobody to be looking** (`updateReady` / `reloadOnce` in `sw-register.js`, `shell-updated` in `sw.js`). `sw.js` skips waiting, and the page used to reload on every `controllerchange`, so a deploy reloaded the app out from under whoever had it open (mid-set, keyboard up), and the banner never got to say anything; a phone's very first visit reloaded once for nothing too. Now a first install is ignored, and an update shows the banner and reloads when somebody taps *Reload* or Refresh, straight away if the app is off screen, or the moment it leaves the screen, which is the reload nobody sees (the crash snapshot puts an open form back). A deploy that forgot to bump `VERSION` is caught as well: the re-fetch behind a launch asks for shell files with `cache: "no-cache"` (a plain fetch was answered from the browser's HTTP cache with the very bytes it was checking) and tells every window when one came back different, so Refresh knows the page it is on is stale instead of comparing the network with a cache that already matches it.
- **Drag to reorder is one gesture serving several lists.** `startRowDrag`/`moveRowDrag`/`endRowDrag` use pointer events rather than HTML5 drag-and-drop, which never fires on touch, and run entirely on inline transforms without a re-render (`render()` rebuilds `#app` wholesale and would drop the node mid-gesture), committing only on release. A row declares which list it is in with `data-dragrow="<kind>"` and carries a `[data-drag-handle]`; **`DRAG_COMMIT` maps that kind to the function that persists the new order**: `group` → `reorderGroups`, `preset` → `reorderPresets`, `pinnedPreset` → `reorderPinnedPresets`, `pinnedTimer` → `reorderPinnedTimers`, `entry` → `reorderDraftEntries` (the lifts inside the open day), `libExercise` → `reorderLibraryExercises` (one group's lifts inside the flat library, via the same `reorderPinnedIn` move, keyed off the row's `data-group`), `set` → `reorderSets` (the sets inside the open entry, the one list whose order is read as data rather than shown as a choice), `variation` → `reorderVariations` (one lift's family, ranked from the *Ways you do this* panel, keyed off the row's `data-root`). Another reorderable list is a row attribute plus one line in that table, not another gesture. The two pinned strips share `reorderPinnedIn`, since "rearrange a filtered view of one master list without disturbing what it filtered out" is the same move either time. **`DRAG_READ_OK` is `READ_OK`'s other half**: the click dispatcher's allowlist never sees a drag, so a new reorderable list has to be decided about in both places, and the default in both is no. **Ranking variations moves them in `state.library` and nowhere else**, which is what keeps one drag honest in all three places a family is listed (the panel, the nested library list and the picker you add a lift from), with no ordinal field that could drift from the list it claims to describe; only the slots that family already occupies are rewritten (the `reorderPinnedIn` move again), so a variation filed under the family long after the fact, sitting forty rows away, still ranks without shifting a single row around it. The **base is not in the list**: every surface draws it first by construction, so a handle on it would promise a move nothing would carry out, and it sits above the draggable rows saying `ex.baseStays`. Each row carries how many DAYS you have trained it, because that is the thing anybody ranking these is ranking them by and it is sitting in the log unasked.
- **A dial is a control, so reordering is a mode.** The pinned strips (presets on Home, timer dials on Home *and* at the foot of the workout and exercise windows) swap their cards/dials for compact drag rows while `ui.presetOrder` / `ui.pinnedOrder` / `ui.timerOrder` is on, rather than wearing a permanent grip handle. You tap a preset card to start a workout and a timer dial to start a rest; a handle living on either is one mis-tap from doing the wrong thing mid-set. `orderToggle()` draws the Reorder/Done control into a `sectionTitle`'s right slot. Note the timer list renders **twice at once** when the entry form sits on top of the workout sheet: two independent containers of the same three rows, which is fine because a drag only ever walks `row.parentElement`.
- **Numbers accept a comma or a period.** Every numeric field is `${NUM}` (a text input with `data-num`, not `type="number"`, which discards the "wrong" separator). `handleBind()` strips non-numeric characters and stores the value period-separated via `decimalize()`; the field itself keeps whatever the user typed. Add new numeric fields with `${NUM}`, never `type="number"`.
- **`migrate(s)`**: schema migration for `state` loaded from localStorage. Bump/extend this whenever the persisted shape changes, rather than assuming a fresh shape.
- **`render()`**: rebuilds the `#app` innerHTML from `state`/`ui` on every change. Sub-renderers per tab/screen (`renderHome`, `renderLog`, `renderHistory`, `renderCalendarTab`, `renderProgress`, `renderCalc`, `renderLibrary`, `renderBody`, `renderTimers`, `renderProfile`, etc.) return HTML strings that `render()` assembles. `patch(p)` is the standard way to mutate `state` (shallow-merges, then persists + re-renders).
- **Event delegation, not per-element listeners.** Clicks are handled by a single `document.addEventListener("click", ...)` that dispatches on the closest `[data-action]` ancestor to the `actions` object (a big lookup table of action-name → handler, defined right before the click listener). Typed input is handled by delegated `input`/`change` listeners keyed on `data-bind` attributes, routed through `handleBind()`. When adding new interactive elements, follow this pattern (`data-action="…"` plus an entry under that name in `actions`, or `data-bind="path.to.field"` + a branch in `handleBind`) rather than attaching listeners directly to DOM nodes, since nodes are thrown away and re-created on every `render()`.
- **`data-stopprop`** marks elements (sheet backdrops, nested editors) where an outer `data-action` must not fire when a click lands on an inner one, see the click listener for the containment check.
- **Sheets/overlays** (`sheet()`, `fullScreen()`) are modal-style panels layered via `ui` flags (e.g. `ui.showProfile`, `ui.showBody`, `ui.workoutSheet`, `ui.entryForm`, `ui.groupSheet`) rather than routing. Body measurements is one of these windows, opened from the ruler button next to the header gear, and it is not a bottom-nav tab.
- **WHAT A SCREEN READER HEARS** (`a11yPass`, run at the end of every `render()`; `A11Y_ACTION`). `icon()` marks every glyph `aria-hidden`. A button that is only an icon and has no title gets a name from `A11Y_ACTION`: the net under the rule, not a replacement for putting an `aria-label` at the call site, which new code should do. Every `data-layer` overlay is a modal dialog named by its heading, **everything under the top one is `inert`** (a live `role=status` excepted), and a window that has just opened takes focus **itself** (the layer, `tabindex=-1`, no outline) when nothing asked for the caret, never a field, so no phone keyboard springs up. It used to focus the window's first button, which is its X, and Chrome draws a script focus that no tap came before as keyboard focus: whenever the app came back with a sheet open (relaunched after the phone killed it, an update reload, Refresh) the X wore the gold ring. A screen reader still hears the window's name, Tab still reaches the X, and `a11yFocusKey` hands focus back to the window itself across a render. `<html lang>` follows the app's language, the nav is a `<nav>` with `aria-current`, the content a `<main>`, and a keyboard focus ring shows on `:focus-visible` only. The audit that drove it (every button on every main screen checked for an accessible name) is cheap to rerun and worth rerunning after a big UI change. A field is named after the words `field()` prints above it (a div, which a screen reader does not connect to the input), and a window whose heading is a search field is named by that field. **Focus is handed back across a render** (`a11yFocusKey`): a frame is a new DOM, so the button that had the keyboard went with the old one and every data refresh sent a screen reader back to the top of the page; it is found again by its action and ids inside the same window. Buttons and switches only, never a text field, which would be the phone keyboard springing up.
- **First-set-best-set is gone, shape and all** (migration v15). v5 took the SETTING away and left the SHAPE: an entry logged in that mode was a total-set count plus the numbers of one top set, with no `setList`, and every screen that could meet one carried a second branch for it: a second set of form fields, a *Convert* button, a "top set of 4" caption, its own word in the summary line. Ten code paths and eight strings kept alive for a prototype that was never chosen and that nothing had written to since v5. v15 brings the rows across instead of leaving them behind: the recorded top set becomes set 1 and the entry is re-derived from it, in the log, the plans, the parked days, the unlogged rows and the crash snapshot. **The sets that were never written down are NOT invented**: four sets of which one was recorded come back as the one that was recorded, which is the same claim the old row made in words said as data instead; repeating the top set four times would put three sets in somebody's history that nobody logged. Weekly volume for those weeks therefore counts what was recorded rather than what was claimed, and nothing else moves, because est. 1RM, the PR badges and the graph all read the best set and the best set is the set that came across. `isDetailed` survives, and the question it now asks is about **cardio**: a cardio session is minutes × effort and is the one kind that legitimately has no set list.
- **A MIGRATION IS THE ONE PLACE WITH NOBODY WATCHING, AND IT MUST NOT THROW** (`readProfileState`'s two catches, `unreadableWhy`, and `function uid()` sitting above `newSet` rather than beside the UI state). `hydrate(JSON.parse(raw))` is one `try`, so **an exception anywhere in `migrate` is indistinguishable from bytes that are not JSON**, and both come out as *the training saved on this device will not open*. v15 shipped and did exactly that to real saves: `uid` was a `const` four thousand lines below the `let state = loadState()` that runs at module level, nothing had ever called it that early before, and the first legacy row needing an id hit its temporal dead zone. Perfect data, every entry intact, reported to its owner as damaged. Two rules came out of it. **Anything a migration reaches for is declared above `newSet`, and `uid` is a `function` so that where it sits can never mean this again.** And **a migration assumes no shapes**: `rows()` in v15 drops what is not a record and coerces what is not a list, because a value that every screen reads as an array of records is not recoverable data in any other form, and passing it onward only moves the crash into a renderer. The failure is also now told apart from real corruption (`unreadableWhy`, `profiles.unmigratable`): the writes are still held either way, since a half-migrated state is not something to write back, but the app no longer blames somebody's training for a bug in its own upgrade code.
- **Theming** is entirely CSS custom properties (`--bg`, `--text`, `--gold`, etc.) swapped via `data-theme="dark"|"light"` on `<html>`, set by `applyTheme()` and mirrored by `theme.js`, the one script in `index.html`'s `<head>` (reads the last saved theme before first paint to avoid a flicker; a file rather than inline because of the Content Security Policy, and still a plain blocking script so it runs before the body exists). `applyTheme` writes it to **`zenofit:theme`**, a device key outside `state`, and that is what `theme.js` reads: it used to read the theme out of `powerbuild-tracker:v1`, which nothing has written since profiles arrived, so every light-theme user got a dark first frame on every launch.
- **The back button closes a window, not the app** (`backTarget` / `backSync`, the `popstate` listener, `BACK_CLOSE`). Nothing touched the browser's history, so Android's back button closed the whole app from inside any window. While there is something to go back from (a window open, or a tab other than Home) the page keeps ONE extra history entry; a back press spends it by pressing the top window's own close control, so each window keeps its own rules (a filled-in exercise still asks, the workout window still parks the day), and with no window open it goes Home; only from Home does back leave. That works because every window has a close control by one convention: a sheet's X (`overlay-close`), and a full screen's first header button whose action says close, cancel, back or exit. **A new window keeps that convention or back cannot close it.** A window closed by hand gives the entry back, so the next press is never a dud. The pinned footers' fade (`data-footer-for`) is a fixed 18px band ABOVE their words, not 30% of their height: on a tall footer the first caption sat inside the fade, over the scrolling text, and read as two paragraphs printed on top of each other.
