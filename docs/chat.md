# Chat

Conversations between accounts (`api/src/chat.js`, the CHAT block in `app.js`): search, threads, sending, unread, blocks, things in a message, unsend, and the invite link. Read this whole file before changing anything it describes, and update it in the same commit when that behaviour changes (CLAUDE.md, *Docs*).

- **BRING A FRIEND** (`inviteShare` / `inviteRun`, the button under the chat list). A link with your username; opened by somebody new it lands on the login screen saying who sent it (`link.invited`), and once they are in with a profile, the conversation with you is open (through `chat-start`, the one road into a conversation). Exact username only, through the same prefix search chat uses. **The link is the only thing `captureLink` reads** (`?invite=`), taken off the address at once and kept in `sessionStorage` until somebody is signed in with a profile open (`linkWaiting`, run at the end of `render()`); `sw.js` answers any navigation from the cached shell with the query ignored (`ignoreSearch`) and never caches a page with a query on it, so an invite opened with no signal is still the app. Copying the link when there is no share sheet says so in `appToast`, the app's one short-lived note (role=status).
- **CHAT IS THE ONE THING IN THE APP THAT IS NOT TRAINING, AND IT IS NOT IN `state`** (the CHAT block in `app.js` above the viewport engine, `api/src/chat.js`, migration `0006_chat.sql`, and the chat half of `zenofit-cloud.js`). Everything else here belongs to a PROFILE: a set, a goal, a check-in, even the roster those profiles sit in. A message belongs to an ACCOUNT (to the person), and it travels to somebody else. Putting it in `state` would have filed a conversation under whichever profile happened to be open, shared it with whoever holds that profile's code, sent it up as an `item`, and carried it away inside an exported backup that people hand to each other; restoring last month's backup would have restored last month's conversation. So it has its own tables, its own routes, its own client cache under `zenofit:chat`, and no contact with `items`, `profiles`, seeds or grants. **Nothing about chat is on the path of anything the app already did**: the log, the sync engine and the roster are untouched, and an account that never opens the tab pays one request per poll and nothing else.
  - **A chat needs an ACCOUNT, not a device** (`chatSignedIn`, and on the server one guard in front of every chat route, search included: a token with no username behind it is 403 `account_required`). An install that never registered has no username, so there is nothing to find them under and nothing to address, and a device token costs nothing to mint; it used to be enough to search, to open a DM with anybody and to upload chat photos, though the app never did any of that. The tab says that and offers the one thing that fixes it, rather than an empty list.
  - **Somebody is found by USERNAME, from the start of it** (`GET /v1/users/search`). A username is the only name an account has that is unique and typed by its owner. It is deliberately a PREFIX and not a contains: a substring search over every account is a directory, and "who is on this app" is not a question a stranger gets to ask. Under two characters is refused rather than answered, only claimed accounts appear, and you never find yourself.
  - **THE WHOLE TAB UNDER THE SEARCH FIELD IS ONE PATCHABLE BOX** (`chatBodyHTML` / `chatPatchBody`), and that is not tidiness, it is the fix for a bug this shipped with. The tab shows conversations with nothing typed and results with something, and that swap was done with `render()`, which rebuilds `#app`, throws away the input the caret is in, and drops focus. So the FIRST letter typed and the LAST one deleted each kicked you out of the field: you typed one character, the keyboard shut, and you had to tap back in for the second. The bullet above it in the source said "NOTHING here calls render()" while the code two lines below did, which is the whole lesson: **every search in this app patches a container and never renders** (`libq`, `pickq`, `stdq`, `attachq`, and now `chatFind`), and the clear button is always in the DOM and shown or hidden in place for the same reason, since drawing it only when there is something to clear changes the FIELD'S own markup on the first keystroke.
  - **Opening a chat is FIND-OR-CREATE and there is no second verb** (`POST /v1/chats`, `chat_threads.dm_key`). Tapping a name means "take me to the conversation with this person", which is the same request whether or not it exists yet. `dm_key` is both user ids sorted and joined, with a UNIQUE index on it, so the two people arriving in either order land on one thread and two phones tapping at the same moment cannot produce two half-conversations. The insert races against that index on purpose and takes whichever row won.
  - **THE SERVER STAMPS A MESSAGE, and `clientId` is what makes a retry safe.** `created_at` is the server's clock for the reason `items.updated_at` is: a phone three seconds off must not be able to sort itself above the reply it is answering. The app draws a message the instant it is typed (anything else shows an empty composer and no message for two seconds on gym wifi, which reads as having lost it) and sends it carrying its own id; the server refuses a second message under the same one and hands back the row that already landed, and `chatMerge` upserts by id **and** by `clientId` so the optimistic copy is replaced rather than duplicated. A send that fails **keeps the message on screen, marked, with Retry**: throwing away what somebody typed because a request failed is the one outcome that is never acceptable. A half-typed one is kept too, per thread, in the cache rather than in `state.drafts` for the reason above (`chatDraftOf` / `chatDraftSet`).
  - **UNREAD IS DERIVED, NEVER STORED.** `chat_members.last_read_at` is the only thing kept and the count is a `COUNT(*)` past it, because a stored counter is a second opinion about the messages and the one thing worse than a wrong badge is a wrong badge nobody can explain. **Sending is reading**, so your own message never comes back as something you have not seen; looking at a thread marks it read (only while the app is actually on screen: a thread left open behind a lock screen has not been read by anybody); and the mark only ever moves FORWARDS, so a late request from a screen that has since scrolled cannot bring the badge back. It shows as a count on the nav icon, beside where a running timer puts its dot, because "three waiting" is a different decision from "one". **A read is remembered on the phone until the server has said it back** (`chatReadMarks` / `chatApplyMarks`): a thread list the server answered before a conversation was marked read, landing after it, used to put the old count straight back on the badge until the next poll, up to a minute and a half away; now a list cannot resurrect a count for messages this phone has already read, and a mark the server never took is resent by every poll rather than only while the conversation stays open. **Reading also takes the notification down** (`chatMarkRead` → `chatCloseNotifs`, and `chatCloseRead` for a conversation read on ANOTHER device, by the `at` stamp every chat push carries, so a newer message's notification stays): it used to sit in the shade, and as the dot on an Android app icon, after the messages it announced had been read. A conversation that leaves the list (removed here or on another phone, or deleted with the other person's account) takes its notifications with it (the `had` / `listed` check in `chatPoll`).
  - **Polling is three paces on one timer** (`chatWantedGap`): six seconds inside a conversation, twenty on the tab, ninety anywhere else, where all that is at stake is the nav badge. A hidden tab polls not at all, coming back to the app polls at once, and a push handed over by the service worker beats whatever the pace was. It is silent by design, exactly as `syncQuiet` is, and it never re-renders unless something landed, and not even then while a field has the caret in it (`syncTyping`), since `render()` rebuilds `#app` and a repaint mid-word from a timer nobody can see would throw away what somebody was typing. **While a field has the caret, what landed is PATCHED in place instead** (`chatRepaint`: the open conversation's messages via `chatThreadBodyHTML`, its error line via `chatErrHTML`, the chat list, and the nav count via `chatBadgeHTML` / `chatPatchBadge`). Skipping the repaint used to mean a reply that arrived while the composer was focused was merged, marked read and never drawn, and never announced either, since the next poll found nothing new; the nav count likewise stood still while a set was being typed in. **A poll that WORKS also retires the error the last one put on screen**, or the offline banner outlives the outage and sits above the messages that just arrived.
  - **THE CACHE CARRIES THE ACCOUNT IT WAS BUILT FOR** (`chatRead`), and a cache stamped for somebody else is dropped rather than drawn. Two people share a phone; one signs out and a friend signs in. Logging out calls `chatForget()` outright, and signing in (`enterAccount`) drops any cache not built for the account signing in, which is the belt to that braces. The one cache that outlives a sign-out is the one a sign-out UNDER us keeps (`leaveAccount(true)`, a token the server no longer knows), and only the same account picks it back up. **Messages are also the one thing logging out clears off the phone**, which is consistent rather than an exception: they are not this device's training, they are the account's conversations, and the server still has every one of them for whenever somebody signs back in. The cache is capped (`CHAT_KEEP`), pruned to the threads still in the list, and losing it loses nothing.
  - **A searchable username needs the other half of the deal, so there is a BLOCK** (`chat_blocks`). It is one direction in the table and both in effect (one that still let their side send would only be a filter on my own screen); it takes the person out of search for both of them, and the other end is told nothing. **Mute is quiet, not gone**: still delivered, still counted unread, just not announced. **Leaving is mine only**: the other person keeps their copy, the messages stay where they are, and writing to them again puts the same thread back rather than starting a second one, which is what the confirm says, because "delete" would promise something this cannot do. **Either side writing brings it back**: the send route clears `left_at` for everybody else in the thread. It used to count only members still listing it, so a message to somebody who had removed the chat reached nobody (no list entry, no badge, no push), while the sender saw it sent. The block check reads every member for the same reason, or a block stopped holding the moment the blocker also removed the chat and the messages piled up for them to find.
  - **Every chat action is on `READ_OK`**, deliberately. A read grant is about somebody else's TRAINING being on your phone; a conversation is neither training nor theirs, and looking at a friend's log must not stop you answering your girlfriend. Nothing in the chat actions writes `state`, which is the test everything else on that list has to pass.
  - **The composer is the only control in the app the on-screen keyboard can bury, and `--pb-kb` is what lifts it.** `index.html` says why the keyboard is left to OVERLAY the app rather than resize it, and names the price; the rule stated there is to lift that one bar off a `visualViewport` measurement, and `applyViewport` now writes that measurement as a `--pb-*` token like every other number the device decides. It is divided by `vpScale` (both sides of the subtraction are screen pixels, the frame is laid out in its own) and written ABOVE applyViewport's early return, which fires precisely when neither the scale nor the width has changed: exactly what a keyboard opening looks like from there. It is spent as PADDING on the conversation layer rather than as a transform on the composer, so the list shrinks by the same amount instead of the composer being parked on top of the newest message; the scroll then chases the bottom (`chatStickBottom`). Anything else reaching for `--pb-kb` should first ask whether it really cannot scroll.
  - **A conversation is pinned to its newest message until somebody scrolls up** (`ui.chatStick`). `render()` restores the scrollTop of anything with a `data-scrollkey`, which is right for reading history and wrong the moment a message arrives, so this overrides it, and scrolling up turns it off, because somebody reading last week's messages has not asked to be thrown back down by a reply landing.
  - **A MESSAGE CAN CARRY A THING, NOT ONLY WORDS** (the THINGS IN A MESSAGE block: `chatBuildThing` / `chatThingCard` / `renderChatView` / `chatImport`, `renderChatAttach` from the composer's ＋, `renderShareTo` from an exercise window, the standards rank card, the preset editor and a plan in the calendar; `kind` / `payload` on `chat_messages` in migration `0007`). An exercise, a preset, a logged day, a planned day, a personal record, a strength rank, or a photo arrives as a CARD (the way a shared link or a game invite arrives in a messaging app), and tapping it opens it in full, laid out like the library's own exercise window, where an exercise or a preset can be added to your own library (a logged day is added as a preset: a preset keeps exercises, never numbers). **What travels is a SNAPSHOT, never a pointer**: the recipient cannot read your profile and never should. A built-in carries its `default-N` id so the other phone shows it in ITS language (`snapLabel`, exLabelOf's rule for a row not in your library), and a group carries its shipped `key` so "Chest" lands in their chest group even if they renamed it. **A payload is somebody else's data**: every field is read through `pStr` / `pNum` / `pColor` and still escaped, and the server checks only the kind, the size, and that a photo message names a photo uploaded INTO THAT THREAD. `body` is required for every kind: it is the one line the notification, the chat list and an older build show, so a phone a version behind reads "Exercise: Belt Squat" rather than a blank. **Adding one is the only write chat has**, and `chat-import` is therefore the one chat action deliberately NOT on `READ_OK`. It never overwrites: a name you already have is offered as *Open yours* or *Add a copy* (numbered beside it), because a name is an exercise's identity and your log is filed under it; a built-in you deleted comes back AS the built-in. A photo comes by id and `photoPass` fetches it, so an imported exercise arrives with its machine. **A chat photo is not a library photo**: it is uploaded into the thread (`POST /v1/chats/:id/photos`, id = hash of thread and picture), readable only by the thread's members, deleted with the message, scaled to 1280px, and held in memory (never in the chat cache, which lives in localStorage beside everybody's training) for as long as the send takes (`chatUploads`); a photo message the app closed on mid-send is marked failed on the next load and says to send it again (`chatRead` turns anything still *pending* at load into *failed*, which it is: nothing resumes a send across a reload).
  - **A PLANNED DAY CAN BE SENT, AND LANDS AS THE RECIPIENT'S OWN PLAN** (kind `plan`: `chatBuildThing` / `chatImport`, the ＋ sheet's *Planned day*, and the send button on a plan in the calendar's day card). What travels is exactly what the plan holds: each lift with its targets set by set (drops included), cardio as minutes × effort, and a lift planned with no numbers travelling with none. Importing makes an ordinary entry of `state.plans` on a day the recipient picks (the planned day by default, today if that has gone by), so it is indistinguishable from a plan they made themselves: nothing in it counts until the day is logged, it is started from the calendar like any other, and the calendar's rules hold: **one plan per day** (a day that has one is refused, never overwritten; the viewer says so and disables the button, and `chatImport` refuses again on its own) and **no plans in the past**. A target only rides along while it fits the shape the lift is logged in on the RECEIVING side (planTargetUsable's rule): a lift they log in seconds is handed "numbers on the day", not reps and kilos. The imported marker for a plan carries the day (`profileId@date`), so the card can say where it went.
  - **A THING ARRIVES WITH EVERYTHING IT DEPENDS ON** (`chatSnapOf` / `chatExSnap` on the way out, `chatFind` / `chatAddEx` / `chatGroupFor` / `kindAmong` on the way in). The other library has none of the sender's context, so a snapshot carries it: the lift's **group** with its colour, kind and shipped key (made for them if they have nothing like it, so a "Forearms" they never had arrives with the exercise; matched by key first, so "Chest" lands in their chest group even if renamed); its **kind**, stored on their side only where it differs from the group it lands in; its **parent** when it is a variation, which is filed under THEIR copy of the parent, or brings the parent along, and is named the way this app names a variation (from their parent's name), so it stays unique and reads right; its hand-made **strength-standard link** (`ex.std`, only if the tables have that slug); and its **photo**. **A built-in is matched by its id before its name**, on both sides of the screen: a squat they renamed "Back Squat" is theirs, not a second squat under the shipped name. `chatFind` is the one answer to "do they already have this", used by the import AND by the viewer's *new to you* labels and counts, so the screen can never promise a different import from the one that happens. Two traps worth remembering: an import can create a group in the same breath, so a lift's kind is read against the WORKING groups (`kindAmong`): `exKind` asks `state.groups`, which does not have the new group yet, and answered "strength" for every lift of a brand-new cardio group; and a variation's parent is followed exactly one level, because a family is a base and its variations, and a payload that nests parents is somebody else's data. A payload's standards slug goes through `stdOf`, because `STD_BY_SLUG` is a plain object and "constructor" is a key of every one.
  - **UNSEND IS DELETE FOR EVERYONE, AND NOTHING IS LEFT IN ITS PLACE** (`chatUnsend`, `DELETE /v1/chats/:thread/messages/:id`, `deleted_at`, `chatDrop` / `chatReconcile`). Sender only; the row stays on the server as a tombstone (body and payload gone) because the other phone may already hold the message and has to be told, and a row that is gone cannot be reported. No page ever carries an unsent message, not even as a "deleted" row. The other phone learns two ways: a `since` poll lists what was unsent since the newest message it holds (`unsent`), because that message was fetched long before and its `created_at` never moves; a tail or a history page is a COMPLETE WINDOW, so anything held inside it that the page does not mention is dropped: strictly inside, since messages sharing the boundary millisecond may have fallen just outside the page. Messages still leaving THIS phone (pending, failed, `local:` ids) are never touched by either. Everything that counts or previews reads live messages only, so the unread badge, the list's last line and its order fall back to what was there before; `last_message_at` is recomputed, and a thread with nothing live in it leaves the list of anybody who never opened it (`opened_at`, set on the row of whoever called `POST /v1/chats`, which also fixed tapping a name putting an empty chat in the OTHER person's list). The notification already in the shade is closed the moment the page hears (`chatCloseNotifs`); a phone cannot be un-rung, and a push to retract one is exactly the silent push Safari punishes. A failed unsend puts the message back and says why. **The actions on a message are behind a long press** (and a right click on a desktop), because a tap already opens a card or a photo: one delegated listener, a 460 ms timer cancelled by movement, and the click that lifting the finger lands on the menu's own backdrop is swallowed in the capture phase. `.pb-msg` turns off the browser's own long-press (selection, the iOS callout); *Copy* is in the menu instead.
  - Groups do not exist yet and the schema does not need changing for them: `chat_threads.kind`, `title` and a members table are already there, and the send route already fans out to every member. What a group needs is a UI and a decision about who may add whom, neither of which is in here.
