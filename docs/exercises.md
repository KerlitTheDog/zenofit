# Exercises, groups and kinds

The library (`DEFAULT_LIBRARY`), what a lift is logged in (`KIND`), renames (`renameExerciseIn`), search, variations and re-parenting, muscle groups and the `UNCATEGORIZED` bucket. Read this whole file before changing anything it describes, and update it in the same commit when that behaviour changes (CLAUDE.md, *Docs*).

- **Renaming an exercise is a cascade, not a field edit, and the cascade is `renameExerciseIn`.** The name IS the identity, so a rename carries through `log`, `plans`, `dayDrafts`, `unlogged`, `presets` and `goals`, plus the open workout sheet, the open entry form and `ui.progressSelected`, exactly as `actions["group-save"]` does for a group. Writing it into the library alone left every one of those pointing at a lift that no longer existed: the session still rendered in the day, and opening it found nothing to edit. **The sweep lives in that one function and anything added later that stores an exercise name is added THERE, not at a call site**: it used to be inline in `exwin-save`, which was fine while there was one way to rename and became a second copy waiting to drift the moment `reparentUnder` needed the same move. It folds into a *patch object* rather than committing, so re-parenting a family can rename several rows in one write with each reading what the one before it left. A name already in the library is refused rather than merged, since two rows under one name is the same desync arrived at from the other end.
- **A group declares WHAT IT IS FOR, and the name is just a name** (`KIND` at the top of `app.js`, `groupKind` / `exKind` / `kindOf`). The Cardio group used to be identified by being called "Cardio", so calling it "Hell" broke the form. Four kinds now: **strength** (sets of reps × weight), **bodyweight** (sets of reps), **hold** (sets of seconds), **cardio** (minutes × effort). A kind earns a place in that table only by passing both halves of one test: **it changes what you write down, AND it has one axis on which more is unambiguously better.** The second half is the strict one: the PR badge, the graph, beat-last-time, the set verdicts and the suggestion card all need a direction to point in. Two shapes people ask for fail it and are deliberately absent: **rounds**, where "5 rounds for time" wants less time and "AMRAP 20" wants more rounds, and **distance**, where a longer run and a faster run are both better. Neither is hard to store; both would make the app decide what you meant. Don't add them without solving that first.
- **Everything that differs between the set-shaped kinds is three questions**, and every call site asks one of them rather than testing the kind: `setHasData` (is it filled in), `setScore` (what is it worth), `setLine` (how is it written). `sets: false` is the real fault line: cardio is the only kind not logged set by set, which is why so much of the app reads `kind === "cardio"` and stays correct, and why bodyweight and hold got the set list, dropset chains, ghost rows, last-time verdicts, PR badges, the graph and sets-per-week for free. `metricOf` is the converted, cross-session number and `setScore` the raw one you read back; `metricUnit` / `metricLabel` name it, since "est. 1RM" is a claim only the strength curve gets to make.
- **A hold is stored in seconds and read as a clock** (`fmtHold`, `metricShow`, `metricWithUnit`, and the time box `DUR` / `durValue` / `durFromDigits` with its `data-dur` branch in `handleBind`). Nobody thinks of a dead hang as 80 seconds: it is 1:20, and typing it used to mean doing that sum first. So **every hold number the app prints is a clock** ("0:45", "1:20", "1:02:05", the face the timers already wear) with no unit after it, which is why `metricUnit` has none for a hold and the sentences that used to say "{n} {unit}" take one composed figure instead: set lines, last time, the suggestion card, the set editor and entry card figures, the Progress rows and goal, the graph (see docs/progress.md), chat cards and the picture studio. **Input is one box typed like a phone's timer**: a number pad whose digits fill in from the right as h:mm:ss, so 4, 5 reads 0:45 and 1, 2, 0 reads 1:20, with no hours or minutes box to fill or skip. It lands selected, so the first digit starts a prefilled time over instead of shifting it (1:30 then 1 would read 13:01). **What is stored did not change**: whole seconds in `secs`, so nothing on record moved and everything that reads a hold reads it as before; "80" typed is 0:80, which is 80 seconds and is drawn back as 1:20. The set editor, the plan sheet and a hold's Progress goal all use it.
- **The kind lives at three levels, and only two of them store anything.** A group ALWAYS carries one. An exercise carries one only while it is an EXCEPTION to its group (`withKind` writes it, `exKind` reads it): **absent means "whatever my group is for"**, which is what makes filing a lift under a cardio group make it cardio and what carries a group's exercises along when the group is re-declared. v13 stamped a kind onto every row instead, which made the group setting inert (every exercise already had its own answer and never asked), and v14 undoes that, keeping a stamp only where it disagrees. Tapping the group's own option in the exercise editor CLEARS the exception rather than setting one. An entry, by contrast, has its kind frozen on it when logged: **re-declaring anything never reaches back into the log.** That is also why the seeded pull-ups and plank are still strength: flipping them would change the form under everyone who already has reps × weight on record for them.
- **A lift is READ in the kind it is logged in today, and only sessions in that kind are compared** (`readKind`, and the kind filter in `earlierOutings`). Change what an exercise is logged in and its old sessions do not change with it, which leaves two sets of numbers under one name; a rep count is not a kilo. So the graph, the best-ever, the PR flags (`computeBadges` keys on lift AND kind), the Progress row, the suggestion card, "last time" and the set verdicts all read one kind only. **The older sessions are still listed** in the exercise window, labelled with how they were logged and carrying no number or badge, with a line saying how many are off the graph: they happened, and a ledger that hides them is worse than one that labels them. Presets follow the same rule (`presetToEntries` takes the kind from the LIBRARY, never from the copy stored on the preset), and a plan hands over its target only while it still fits the lift's current shape (`planTargetUsable`).
- **Search reads the label as well as the stored name** (`exMatches` / `exIsNamed`). Filtering on `ex.name` alone meant the library search and the exercise picker found nothing at all in Ukrainian or Svenska, and the picker, seeing no exact match either, then offered to add a lift you already had under its translated name as a second row keyed by a name nothing points at. Any new search over exercises has to try both. **`nameMatches(name, q)` is the same test where all that is to hand is a stored NAME** rather than a library row (a dashboard row, a log entry), and it is what the Progress tab's *Your lifts* search runs on. That search **filters the list and nothing else**: the selected lift is worked out from the whole list before the filter runs, so typing never moves the graph out from under you, and the dropdown above the graph still offers every lift, because narrowing a control that owns the selection would leave the lift on screen missing from the only thing that can change it. Tapping a result is what moves the graph, as tapping a row always has. **The exercise picker has the Library's group chips too** (`pickerChips` / `ui.pickerFilter`, a scrolling strip under Exercises/Presets, only groups with something in them, back on *All* every time the picker opens): they narrow what is SHOWN and never what "is this name new" is asked of, so a lift filed under another group is not offered as an addition, and a search whose matches are all outside the chosen group says how many and offers *show all* instead of looking empty. A chip tap patches the strip and the list rather than rendering, because `render()` re-focuses the picker's search field, which on a phone throws the keyboard back up over the list the chip was pressed to look at.
- **`DEFAULT_LIBRARY`**: the seeded exercise library (name, muscle, kind, equipment, alternative, cue notes), ported verbatim from the spreadsheet's Exercise Library sheet. Three of its stored names carry the sheet's "Cardio: " prefix, which was how the sheet told a cardio row apart; a group says that now, so the LABEL drops it in every language (`EX_LABEL_EN` for English, the `EX` rows for the others) while the stored name, which is identity, is untouched, and a search for "cardio" still finds them by it.
- **A variation is a library row of its own** (`variantOf` / `variantName`, `exWindowVariations`). A wide-grip pulldown and a close-grip one are the same movement and not the same lift: the weights differ, and averaging them into one history describes neither. So each gets its own row, its own log, its own best set, PRs and graph, and everything downstream keeps working because everything downstream only ever knew about library rows. What the link buys is the two things separate rows cannot do for themselves: they are **shown together** (nested under the parent in the library AND in the exercise picker you add a lift from: `nestVariations`, indented behind the arrow and called by the short name, which the picker did not do for a long time and so listed a variation flat at the bottom of its group under its whole name; one whose base is not in the list, because a search or a filter left it out, keeps its full name and no indent in both, and listed in each other's window), and **the label is composed live**: `exLabelOf` builds "Pulldown · Wide grip" from the parent's current label, so renaming the parent re-labels every variation at once while not one stored name moves. Stored name is identity and must never shift under the log; the label is display, exactly as it is for a translated built-in. `exwin-save` composes the stored name from the parent so it stays unique, which is exactly why **`exDraftReady` is the one place that decides whether Save is live**, read by `renderExerciseWindow` to draw the button and by `handleBind` to flip it as you type. A variation's draft `name` is empty and STAYS empty until save composes it, so a second copy of the rule checking `name` greyed the button out for every variation there has ever been, however completely the form was filled in; the field that has to be filled is whichever one is on screen. A new field that gates saving goes in that helper, not beside it. A variation of a variation attaches to the ROOT, since nobody wants a tree of grips, and **deleting a parent never takes its variations with it**: they are separate lifts with their own history, so they simply stop being listed as a family.
  - **WHICH END OF A FAMILY IS THE BASE IS AN ACCIDENT, SO IT CAN BE MOVED** (`reparentUnder` / `shortUnder`, *File under another lift* on the variations panel). The base is whichever row existed before variations did, which is a fact about the order somebody started logging in and not about the movement: log the one-arm machine for a year and every ordinary pulldown afterwards has to hang off *it*, with the machine (the variation) sitting where the movement should be. There was no way out of that but deleting a lift and its history. So an existing row can be filed under another after the fact, and **its own variations come with it**, re-attached to the new base beside it rather than left pointing at a row that is no longer one. Each moved row's stored name is recomposed from the new parent's, which makes this a RENAME and sends it through `renameExerciseIn`, unless that name is taken, where the row keeps the one it already answers to, because a unique name it answers to is worth more than a tidy one. The short part is guessed by stripping the parent's name off the front ("Lat Pulldown (OA machine)" under "Lat Pulldown" is an *OA machine*) and then **shown in a field before anything is written**, since it is arithmetic on a string and the person reading it knows what the lift is. Only BASES are offered as a parent, so a cycle cannot be built; picking a variation resolves to its root. The inverse (*Make it a lift of its own again*) is deliberately there and needs no confirm: it is what deleting a parent has always done to what it leaves behind, nothing is lost, and a move you cannot undo is a move most people will not make. `reparentUnder` hands back a patch instead of committing one, because `patch()` renders and the window that called it is still looking at the row by its old name.
- **Muscle groups are records, not a colour map.** `state.groups` is `[{name, key?, color, kind}]`, seeded from `DEFAULT_GROUPS`; `colorFor()` reads it, so recolouring a group repaints every surface at once. **Its order is the order groups appear in everywhere**, and the user sets that by dragging in the group manager (see *Drag to reorder* in docs/architecture.md). Renaming a group in `actions["group-save"]` has to carry the library, log, **plans, day drafts**, presets, volume goals and the active filter with it, the same sweep the exercise rename does and with the same standing rule: **a new place that files something under a group name belongs in that list.** The log's `muscle` is only a fallback (`muscleOf` reads the library row first), which is why a miss there stayed invisible for so long and exactly why it is worth keeping true, since the fallback is what answers for an exercise no longer in the library at all. There is no sweep of the open workout sheet or entry form as there is for a rename of an exercise, because the group manager opens from the Library tab only and nothing of the sort can be on screen. A rename does not change what a group is FOR: that is its `kind`, which rides on the record (see *A group declares WHAT IT IS FOR* above), so a renamed cardio group still logs in minutes. Deleting a group never takes exercises down with it, and tips whatever is still in it into the bucket rather than refusing, over that same list and unconditionally, since `groupUseCount` counts library rows only while a logged entry can still name a group after its exercise has gone. **`group-delete` rebuilds the survivors from their RECORDS, never from a list of names**: mapping names back into fresh `{name, color}` objects dropped every remaining group's `key`, so deleting one group you invented un-translated all seven shipped ones and lost track of which was cardio. Migration v12 repairs that damage with the same back-fill v5 used.
- **`UNCATEGORIZED` is a bucket, not a group.** It is never in `state.groups`, and exercises land in it two ways: their group got deleted, or they were quick-added mid-workout and the muscle question was skipped (`pick.skipMuscle` → `quick-add-muscle` with the bucket as its `data-g`). Two list functions keep the distinction: **`libraryGroups()`** is what the user can *choose* (filter chips, the muscle dropdown, quick-add chips, the group manager) and never contains it; **`allGroups()`** is what must be *shown* (library sections, the exercise picker) and appends it last when anything is in it. It has no target control in the volume list, its name is refused in the group editor, and it disappears on its own once every exercise has been re-filed. Adding an exercise *from the Library* still requires a group, and Skip exists because you were mid-set, not as a way to leave the form blank.
- **Compound vs isolation is gone, and so is `type`.** What a lift is logged in is `kind` (see above), declared by its group and overridable per exercise. `type` is only still READ, as the legacy path in `exKind` for library rows saved before v13 that carried `"Cardio"` there; nothing writes it any more, and old `"Compound"`/`"Isolation"` values are read by nothing at all.
