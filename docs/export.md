# Backups, spreadsheets and pictures

What leaves the app as a file: the backup (`backupText`), the spreadsheet (`csvText`) and the picture studio (`picBuild`). Read this whole file before changing anything it describes, and update it in the same commit when that behaviour changes (CLAUDE.md, *Docs*).

- **A backup is `state`, not a list of things to back up** (`backupText` / `importBackup`, Settings → Data). Everything the user has is one object under one localStorage key, so the export is that object serialised and nothing is enumerated, which is the point: a hand-listed backup silently stops covering whatever is added next, and the first anyone hears of it is a restore missing their custom exercises. **Adding a field to `defaultState()` is all it takes to be included.** The one exclusion is `drafts`, the crash snapshot of whichever form was open at the moment of export: it is a picture of the UI, not of anyone's training, and restoring it drops the person on the other end into a half-typed set editor from a session they were never in. `dayDrafts` is not that and travels. Import goes through the same `hydrate()` the first load uses, so a file written by an older version comes up exactly as that data would if it had been sitting in localStorage, since a restore must never be a downgrade. It accepts a bare state object as well as the envelope, refuses anything without a `log` array and a `settings` object, and asks before it writes, because overwriting a training history with a file that merely parsed is the one failure here that cannot be undone.
  - **The same file goes out two ways, and there is only one file** (`backupName` / `backupText` feed both `exportBackup` and `shareBackup`). Download is the wrong shape for what people do with a backup on a phone (send it to somebody), so the bytes also go to the system share sheet (Web Share Level 2), where a chat or a mail is one tap instead of Downloads plus a file picker. **Never add a second export format for it**: the share and the download must stay the same file or a restore starts depending on which button was pressed. Whether the sheet takes files is *asked*, never assumed: `shareFileType()` probes `navigator.canShare({files})` with a real `File` (it needs a secure context, and some platforms take a `.json` only as `text/plain`, so it tries both and the winner is what the file is built with), memoises the answer, and the button is not drawn when the answer is null: a share button that cannot share is worse than none. `navigator.share` is called with nothing awaited before it, or the browser drops the tap's activation and refuses. A dismissed sheet is `AbortError` and says nothing, since that is an answer; any other failure says so once and falls back to the download, because the sheet is a convenience on top of the file and the file still has to arrive. **One share sheet at a time** (`shareSheet`, used by the backup, Storage check, the CSV, the picture studio and an invite): a second `navigator.share()` while a sheet is up is refused with `InvalidStateError`, and a quick double tap used to read that as failure, so a backup apologised and downloaded itself, a CSV or picture downloaded and an invite copied its link, all behind a sheet that was working. A tap during a share is now ignored, and `InvalidStateError` is never a failure. The other actions that create, send or delete were checked for double taps and need no guard: the network ones carry a busy flag (login, create account, join, codes, delete account, chat start, share to chat, log out, notifications) or are made safe by the server (a message's `clientId`, a profile's `clientKey`, a photo's content id, and removing, leaving, blocking or unsending twice changing nothing), and the local ones (save day, delete day, plan save, presets, every chat import) close or replace their button in the same synchronous step.
- **WHAT YOU DID, AS A PICTURE** (the block of that name before the Storage check screen: `picOpen` / `picData` / `picDraw` / `PIC_DRAW` / `picBuild` / `renderPicStudio`, actions `pic-*`, strings `pic.*`). The Strava idea: anything the log can say about you becomes an image for a story or a post, handed to the phone's share sheet (or saved). Opened from the share icon on a history day, *Share* in a lift's progress section, and *Share* over the Progress graph; inside, the card can be about any of six things: a **workout** (one logged day: groups, totals, each lift as best set / every set / name only), a lift's **progress** (the line from the first session, over all time or the last year/6/3/1 months), its **1RM** (one big number, "1RM" only when the best set really was a single, otherwise "est."), **one set** (picked from every set ever logged on the lift, best-first or recent-first, flagged when it was a record at the time and when it is the best of all), **records** (up to five lifts' bests, as est. 1RM or best set, with the est. total of the strength ones; defaults to squat/bench/deadlift by their built-in ids, then the lifts trained most) and a **month** (the trained days as a calendar, coloured by accent or by each day's main group). And how it looks: story 1080×1920 / post 1080×1350 / square 1080×1080; seven backgrounds (midnight, black, light, gold, colour, your own **photo** with a darken slider (or the lift's own photo), and **clear**, a transparent PNG to lay over a photo in the story editor); seven accents including the muscle group's colour (deepened on paper, dark ink on gold, white-or-black ink by luminance on colour); left or centred; content at the top (the card is FILLED: rows spread, the chart grows, a one-number card centres its number in the room under the title, `picCentre`), middle or bottom (everything at natural size: the default over a photo); a free headline (40 characters) in place of the kicker; switches for weights, dates, your name, record marks, the chart, totals, the set behind a 1RM, a set's est. 1RM; and the Zenofit signature as logo + link or a small mark. **What it says is only what the log says**: `exerciseHistory`, `computeBadges`, `bestSet`, `est1RM`, read exactly as the app reads them; the one added figure is weight moved (arithmetic on what was logged) and a total is labelled *est.* because it is a sum of estimates; a logged weight is printed at two decimals (`picKg`), never rounded the way a derived figure is (106.25 is not 106.3). **It never leaves the phone by itself**: drawn on a canvas, the photo read into memory and dropped with the window (`picClose`), nothing uploaded; how you like your cards (`PIC_ONE_OF` + `PIC_SWITCHES` + dim) is remembered per DEVICE under `zenofit:pic`, like the theme: what a card is about (day, lift, set, headline, photo) is not. Every remembered value is checked against its allowlist on the way in. **Mechanics worth keeping**: the picture is kept BUILT (`picBlob`) so *Share* calls `navigator.share` with nothing awaited, as `shareFile` does; builds supersede each other by `picJob`; the preview `<img>` is patched in place (`picPaint`) and the headline and dim slider rebuild without a render, so the caret and the finger stay put; content is drawn on its own layer canvas and then placed (top/middle/bottom), which is also what lets a photo/clear card cast one shadow under everything; story content keeps clear of the top and bottom bands where Instagram/Snapchat draw their own bars. Text for the canvas goes through `plainOf` (a `<template>`, so nothing in it can load); `T()` reads its emphasis off the template before any value goes in (see `.claude/rules/i18n.md`), so a name passed in as a variable keeps its underscores. A photo is only drawn or put in a style attribute if `picSafeSrc` says it is a base64 PNG/JPEG/WebP data URL (anything else would taint the canvas, or put somebody else's string inside `url('…')`). The switch for dates is `dates`: `date` is the chosen DAY, and one name for both turned the day into `false` the first time the switch was tapped. The preview's height is a share of the frame (`PIC_PREVIEW_H`, from `--pb-vh` / `--pb-scale`), so a short phone keeps room for the controls. Nothing writes `state`, so every `pic-*` action is on `READ_OK`.
- **THE LOG AS A SPREADSHEET** (`csvText` / `exportCsv`, Settings → Data). One row per set, as logged, the unit it was logged in, plus the est. 1RM off the app's own curve. A warm-up is a row like any other set with `1` in the `warmup` column (beside `drop`), since a spreadsheet is the whole record and the reader decides what to add up. In Svenska and Українська it is semicolon-separated with decimal commas, which is what Excel and Sheets in those locales open cleanly. **It is for people, and never read back**: the backup is still the only file a restore takes, and must stay the only one. A cell is quoted only when the SEPARATOR is in it (quoting on every comma wrapped each decimal-comma number). **Words people typed never reach a spreadsheet as a formula**: a name, group or note starting with `= + - @` gets a leading apostrophe, because Excel and Sheets run one the moment the file opens, and on a shared profile the notes were typed by somebody else. The week column is blank in rolling mode, as the week chips are.
