# Notifications

The one notifications switch per device (`notifyEnable`) and how `sw.js` decides to show or skip a chat push, including WebKit's rules. How push delivery is tested, since the smoke suites cannot, is in `.claude/rules/server.md`. Read this whole file before changing anything it describes, and update it in the same commit when that behaviour changes (CLAUDE.md, *Docs*).

- **A NOTIFICATION IS SENT BY THE SERVER AND SHOWN BY `sw.js`, AND ONLY THE PHONE KNOWS WHETHER TO SHOW IT.** The push goes out from the send route rather than being polled for, because the whole point is reaching a phone with the app shut, and it never delays the reply: a push service being slow must not make sending slow, and a stored message has been sent whether or not the other phone rings. **`sw.js` skips the notification only for somebody LOOKING AT THAT CONVERSATION, and it asks the page rather than guessing** (`tellAndAsk` in `sw.js`, `chatShowing` in `app.js`): the push is posted to every window, a visible one also gets a port to answer on, and no answer within `ASK_MS` means ring. The page then polls, so a message travels exactly one road and there is no second copy of it to disagree. It used to be "any window of the app is FOCUSED", which silenced every message that arrived while the app was open on Home mid-workout or in a different conversation: nothing announced them but a count on the nav. "A window exists" is deliberately not the test either: an installed app behind the lock screen still has its window, and that is precisely when a message has to ring. **On WebKit there is no exception at all** (`STRICT_PUSH`): Safari and every iPhone web app count a push that shows nothing as silent whatever the app is doing, and revoke the subscription after a handful, so even the conversation on screen gets a notification there, shown silently and closed at once. Each chat push **closes the conversation's previous notification before showing its own**, because `renotify` is Chrome-only and a same-tag replacement arrives without a sound in Safari and Firefox. A chat push is held **a day** for a phone that cannot be reached (`CHAT_PUSH_TTL`), a timer five minutes (`sendToUser`'s `opts.ttl`): the phone in a basement gym is the one that most needs to hear what came in while it was down there. **A timer is not treated this way**: it already rings locally when the page is alive (`fireTimer` cancels the server's copy on the way past), so a timer push arriving at all means the page did not get there. They also want opposite things from a notification and the server says which is which: a timer sets `requireInteraction` because missing it ends the set, a message does not, because it is still there when you pick the phone up and a notification that refuses to go away is one people turn off.
- **ONE SWITCH, FOR THE WHOLE APP, ON THIS DEVICE** (the NOTIFICATIONS block above TIMERS: `notifyState` / `notifyEnable` / `notifyDisable` / `notifySetKind` / `renderNotifyWindow`, `zenofit:notify`, `off_kinds` on `push_subs`, `PUT /v1/push/prefs`). There were two buttons that looked like two features (*Turn on notifications* in Settings and a strip in the chat tab with its own *Turn on*), and they were the same button: both asked for the browser's permission and subscribed this device to push, and that ONE subscription is what a rest timer rings through AND what a message arrives through. A third place asked too: the first Start of a timer requested permission and stopped there, without the subscription, so "allow" bought nothing that worked with the app closed. Now there is one window, *Settings → Notifications*, holding the switch, a per-kind choice (rest timers, messages) and the check that used to be push-test.html: a separate document that looked like another app, now gone. The chat tab shows a **doorway** into that window, only while nobody has decided (`want === null`); somebody who switched notifications off made that choice in the place it is made. The first timer Start, on an undecided device, asks through the same `notifyEnable`. A device whose browser already granted permission (the old timer prompt) and was never switched off is subscribed quietly at launch: no prompt can appear once the answer is not `"default"`. **The subscription rings for whoever is SIGNED IN, and is filed again at every launch and every login** (`notifyAttach` → `refilePush`): the server's row follows the endpoint and used to be written only by the switch, so after logging out and in as somebody else the phone went on ringing for the first account and never for the second, and relaunching did not fix it. Logging out names the endpoint (`signOut` → `POST /v1/auth/logout {endpoint}`), so the account leaving stops ringing a phone nobody is signed in to, and nothing is subscribed while logged out: that used to mint an anonymous device just to have somewhere to file the subscription, which then took the phone over. `enablePush` is single-flight: the quiet launch subscribe and a tap on the switch could each find no subscription and each make one. **The choice is the DEVICE'S** (`zenofit:notify`, outside `state`, never synced, not in a backup), like a theme. A kind turned off is sent with the subscription and filtered in `sendToUser`, so a push the device said no to is never sent at all: the alternative, a push the phone has to swallow, is one Safari revokes the subscription over after a handful. It must come from a real tap (iOS refuses a prompt that was not, and Chrome penalises a site that asks on load), and every reason it cannot be offered is said in words somebody can act on: on iOS the app has to be installed to the home screen first, and a permission already refused can only be undone in the browser's own settings.
