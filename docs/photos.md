# Photos

Exercise and chat photos: the photo store (`api/src/photos.js`), ids, upload and download, holders and the sweep, the storage ceilings, the R2 option, and how pictures are scaled before they are stored (`readImageScaled`). Read this whole file before changing anything it describes, and update it in the same commit when that behaviour changes (CLAUDE.md, *Docs*).

- **PHOTOS HAVE A STORE OF THEIR OWN, AND A ROW NEVER CARRIES ONE** (the PHOTOS block beside sync: `photoPass` / `photoUpload` / `photoLoad` / `photoSlot`, `libraryWire`, `api/src/photos.js`, the `photos` table in migration `0007`). A photo used to ride inside its library row, so a row over the item limit went up *without* it and the other phone got the lift and a placeholder, and every pull re-sent every photo on its page. Now each photo has an **id: the SHA-256 of its data URL** (`ex.photoId`). It goes up to the photo store once (`PUT /v1/photos/:id`, which checks the bytes hash to the id, so nobody can store a different picture under an id somebody's library names), and the row travels with the id and without the picture. **Locally nothing changed**: `ex.image` is still the data URL, every screen draws from it, a backup still carries it, the app still works in a basement. **A lift wears its library photo in every list that names it** (`exThumb` from a library row, `nameThumb` from a stored name, both beside `photoSlot`): the Library, the exercise picker, the day being built, the Log history, the Progress lifts and the entry window's own header all draw the one square `exThumb` returns, in the four states the Library always knew (the picture; a slot that fills itself when it arrives, never a render; a dashed marker for one still on an old device, drawn only where `away` is asked, which is the Library alone; nothing when there is no photo). `nameThumb` resolves the name through a `state.library` map rebuilt only when that array changes, so a long log is not a `find()` per row, and it writes nothing, so it is safe on every `READ_OK` surface. The dense one-line day summaries (the calendar day card, the history day lines) keep their colour dot and draw no thumbnail, since a row of 34px pictures is not a summary. One pass does three jobs for the profile on screen: *identify* (a picture with no id gets one: new photos, and every photo saved before this existed), *upload* (asking `POST /v1/photos/have` first, and remembering confirmed ids per device in `zenofit:photos-up`), *download* (an id with no picture is fetched and written into the row), after every sync, on switching profile, after a live profile's fetch, and straight after a photo is saved, so the id exists before the push's own debounce fires. `syncPush` uploads before it sends any row naming a photo, so the other phone is never handed an id it cannot fetch yet; a photo that fails to upload never holds the row back. Four rules keep it honest, and all of them are load-bearing. **The wire row is built in `syncLocalItems`, before `__i`**, with the image taken out wherever it sat and `imageMissing: true` put back on the end, so the change hash is identical on the phone that sent it and the phone that later filled the picture in: two devices disagreeing about that hash is a row that pushes itself back and forth for ever. **`imageMissing` still rides on every photo row** for the builds that came before the store: to one of those the flag means "keep yours", so an old phone that holds the picture keeps it instead of deleting it on the strength of a row it half understands. **`syncApply` keeps the picture it holds when the incoming row names the SAME photo** (same id, or, from an old build, the bare flag): the server does not filter a pull by who wrote it, so without this the phone that took a photo deletes it the moment it syncs; a *different* id is a photo changed elsewhere and the local one makes way; a row with neither is a photo removed. **A row with no photo at all goes up exactly as it always did** (`libraryWire` returns it untouched), so shipping this re-sent nothing that never had a picture. Fetched pictures also live in Cache Storage under `zenofit-photos` (sw.js keeps that cache across deploys; the id is the content, so nothing in it can go stale), which is what lets a live profile and a chat show a picture twice without fetching it twice; signing out clears it with the chat cache. `photoAway` / `photoComing` tell the two placeholders apart: an id with no picture is *on its way* and draws a slot that fills itself in place (`photoPaint`, never a render); `imageMissing` with no id is a photo still on a device running an old build. Readable by anybody signed in who holds the id (256 bits nobody can guess, travelling only inside a profile or a message), with a per-account cap (`MAX_ACCOUNT_PHOTO_CHARS`) and an upload rate limit. **Only an account uploads one**: `PUT /v1/photos/:id` refuses a token with no username behind it (403 `account_required`, before the body is read), because a device token costs nothing to mint and each had a quota of its own; the app only ever uploads for a profile in a signed-in account, so nothing it does is refused. **The whole store has a ceiling too** (`PHOTO_BUDGET_CHARS` in `photos.js`, a `[var]`, 300 million characters: 60% of the free plan's 500 MB database), because a handful of accounts at 150 MB each could fill the database and every write would then fail for everyone. Past it an upload is 507 `photo_storage_full` and nothing else is refused: sync and chat carry on, the phone keeps the picture, stops offering uploads for six hours (`photoStoreFull`, `zenofit:photo-full`, per device) and says so once (`photo.storeFull`); a chat photo says it under the failed message. The total and the account's own share are one query read off the `(owner_id, size)` index of migration `0011`; without it adding up `size` read every picture in the table. **D1 is the store today** (bound to the Worker already, no new infrastructure, 2 MB per row).
  - **A PHOTO LEAVES THE SERVER ONCE NOTHING HOLDS IT** (`photo_refs` and `orphaned_at` in migration `0008`, `setHoldings` / `dropHoldingsUnder` / `payloadPhotoIds` / `sweepPhotos` in `photos.js`, the `scheduled` handler and the cron in `wrangler.toml`). The store used to only ever grow: a photo removed from an exercise, replaced, or left behind by a deleted exercise or profile stayed in the cloud for ever and counted against its uploader's cap. It cannot simply be deleted when one row lets go, because a photo's id is its content and several things can hold the same picture at once: another profile, another account that added the exercise from a chat, a chat card still showing it. So every **holder** is written down: `item:<profileId>:<itemId>` for a library row (set on every push of a library row, so a row naming a new photo lets go of the old one, and a tombstone lets go of everything), and `msg:<messageId>` for a card showing a library photo (an exercise's, its parent's, every lift of a preset, logged day or planned day; set on send, dropped on unsend). Deleting a profile drops everything under its prefix: a key RANGE, not LIKE, so the holder index answers it. A photo left with no holder is only **marked** (`orphaned_at`), and the daily sweep deletes it once `PHOTO_GRACE_MS` (3 days) has passed and it is STILL unheld, rechecked in the DELETE itself. The grace exists for one ordinary moment: the app uploads a picture BEFORE it pushes the row that names it, so every new library photo starts out unheld (`orphaned_at` = upload time) and the push stops the clock; asking `have` about an orphan, or uploading it again, restarts it. **Nothing is ever left pointing at a hole**: every push reports any photo its rows name that the store does not have (`missingPhotos`), and the phone that pushed it (which remembers what it uploaded in `zenofit:photos-up`, precisely so it never asks twice) forgets that id and sends the picture again on its next pass (`syncPush`). A **chat** photo is not in `photo_refs`: it belongs to its one message, is deleted on unsend, is deleted straight away when a failed, never-sent photo message is discarded (`DELETE /v1/chats/:thread/photos/:id`, uploader only, refused while a message shows it), and anything the sweep finds in a thread that no live message shows is deleted a week after upload. **D1 TRAP, and it bit:** D1 refuses a LIKE or GLOB pattern longer than 50 characters, and `'%' || <64-char id> || '%'` is 66. It only throws when SQLite actually evaluates the LIKE, so a query that usually has no candidate rows passes every test and then fails in production on the first thread holding a second photo. Match a photo inside a payload with `json_extract(payload, '$.photo') = ?`, never LIKE.
  - **R2 IS THE FUTURE OPTION FOR PHOTOS: KEEP IT IN MIND, DO NOT DO IT UNPROMPTED.** Cloudflare R2 is object storage made for exactly this, and it is where photos should move once D1 stops being comfortable. Signs it is time: the `photos` table is a large share of the database (D1's per-database cap on the free plan is a few hundred MB: check the current limits rather than trusting this line), uploads start failing on size, the per-account cap (`MAX_ACCOUNT_PHOTO_CHARS`) is being hit by ordinary use, or the store's own ceiling (`PHOTO_BUDGET_CHARS`) is reached. It is a small change because the design was built for it: the id scheme (SHA-256 of the data URL for a library photo, hash of thread + picture for a chat photo), the routes, the `have` check, the per-account cap and the client are all unchanged, and only `api/src/photos.js` (`storePhoto` and the GET) plus the unsend branch in `chat.js` would move from SQL rows to `env.PHOTOS.put/get/delete`. Keep a small `photos` table in D1 for the metadata (id, size, owner, thread, `orphaned_at`) and keep `photo_refs` where it is, so the cap, the thread check and the sweep stay queries; the sweep then deletes the R2 object as well as the row. It needs things only the user can do: **R2 has to be enabled on their Cloudflare account** (it asks for a payment method even inside the free tier), a bucket made (`wrangler r2 bucket create`) and bound in `wrangler.toml`. So raise it with the user when the signs appear and let them decide; moving the existing rows across is a one-off copy script, and nothing on a phone has to change.
- **Images** (exercise photos, chat photos) are downscaled and re-encoded client-side in `readImageScaled()` before being stored or sent: 1000px for an exercise, 1280px for a chat photo, WebP where the browser can encode it and JPEG where it cannot (Safari silently hands back a PNG for WebP, so the result is checked, and the smaller of the two is kept). A camera photo of about a megabyte goes up as roughly 60 KB. Don't store or send raw uploaded file data: the photo store accepts JPEG, PNG and WebP data URLs only, never SVG, since a data URL goes straight into an `<img>`.
