# Profiles

A profile is a whole `state`: the account's list of them (the roster), adding, removing and switching, a save that will not open, Storage check, and live profiles. Read this whole file before changing anything it describes, and update it in the same commit when that behaviour changes (CLAUDE.md, *Docs*).

- **A profile is a whole `state`, and there are several of them** (`loadProfiles` / `switchProfile`, Settings → Profiles). Trying a different block without giving up the one you are in, or logging for somebody whose phone is at home, needs a second everything: log, library, groups, presets, timers, goals, body, plans, settings. So a profile IS a state, the same object the backup file carries, and switching swaps it whole. **Storage is one small list per ACCOUNT plus one key per profile** (`powerbuild-tracker:roster:<userId>`, `powerbuild-tracker:state:<id>`) rather than all of them under one key, because every save rewrites its key and localStorage is a few megabytes with exercise photos already in it: writing four profiles because one gained a set would be four times the quota risk on every debounce. Export and Import act on the profile you are in, unchanged, since `state` is still `state`.
  - **A PROFILE LIST BELONGS TO AN ACCOUNT, NEVER TO A PHONE** (the PROFILES block: `readRoster` / `saveProfiles` / `signedInAs`, `profiles.userId`). There used to be one list per device, read by every account ever signed in on it, and that one fact produced every roster bug on record: another account's profile in your list, a sign-out that left a list for whoever came next, a sign-in that uploaded somebody else's training. Now logged in, `profiles` is that account's list and nothing else; **logged out it is EMPTY and the whole app is the login screen** (`renderGate` → `renderLoginGate`, early in `render()`); logged in to an account with no profiles, it is `renderNoProfiles` (name a first one, join a shared one, Storage check, log out). Log out of one account and in to another and you get the second account's list, never a merge; log back in to the first and its list is there instantly with no signal needed, and the roster brings it up to date. **Nothing is deleted from the disk by logging out**: the state keys and the account's list stay, reachable only through Storage check behind that account's password. `migrateDeviceList` moved the old device-wide `powerbuild-tracker:profiles` once: linked profiles to the account their record names, never-uploaded ones with content to whoever was signed in, the first-run blank deleted, and everything else (sync turned off, signed out) into no list at all, for Storage check.
  - **THE LIST ITSELF IS ACCOUNT DATA, NOT DEVICE DATA** (the ROSTER block in `app.js`: `rosterSync` / `rosterPushOrder` / `dropLocalProfile`, `profiles.position` and `profiles.name_updated_at` in migration `0005`, `GET /v1/profiles` and `POST /v1/profiles/order`). `profiles` on the server IS the roster, and every device builds the account's list from it and pushes its own changes back, which is the deal the items inside a profile have always had, one level up. Every pass ends with this device's list matching the account: what the account has is fetched, what was made here goes up, what left the account leaves the list. **Every await in `rosterSync` re-checks `stillMe()`**, because a pass that outlives a log-out would file one account's listing under the next account's list. **What stays local, deliberately: which profile you are LOOKING at**. That belongs to the person holding the phone, and syncing it would mean opening a laptop changed what the phone was showing mid-set.
  - **LOGGING IN ASKS BEFORE IT MAKES AN ACCOUNT** (`login-go` / `login-create`). **The fields are a real `<form>`**: Enter, or a phone keyboard's Go, presses Log in (its button is the form's one submit button), the create step stays its own tap (Log in is disabled while it is up, so Enter does nothing there), and the password field says `new-password` while an account is being made, so a password manager offers to save it, which matters with no password reset. One `submit` listener stops the page ever really submitting. One form, and it always tries to log in first; only a refused login whose name is really free (`/v1/auth/available`) offers to create it, as its own tap, because a typo in your own username ("testng1") used to become an empty new account on the spot, which looks exactly like every profile having vanished. **Logging out sends first** (`flushAccount` → `accountUnsynced`, counted the way a push would count: rows whose hash moved, marks whose row is gone, a profile not yet in the account, a queued removal, an unsent rename) and the confirm says how many changes could not go and that they stay on the phone. `enterAccount` / `leaveAccount` are the one place a change of account is handled; `restoreDrafts` is a named function because entering an account puts that account's half-typed forms back too.
  - **YOURS, OR SHARED WITH YOU, AND NOTHING ELSE** (`profileShared` / `profileShareLine` / `sharedLast`). The Profiles screen and the account sheet draw two groups: *Your profiles* and *Shared with you*, each shared row naming whose it is and the level (`ownerName` comes from the server's `LEFT JOIN`). The rows used to carry a line about where each profile physically was (on this phone only, backed up, synced but not to this account, get it), which described machinery and read as a list of faults; that is gone, and so is every cloud icon. Your own profiles are always ahead of shared ones in the stored order (`sharedLast`, applied by the roster and by `reorderProfiles`), so the list and the screen cannot disagree about where a row is. On a shared profile the red button is *Remove from my profiles* (leave), never *Delete*.
  - **Offline is untouched, which is the only reason this is safe.** Nothing in the roster is on the path of anything the app does: a profile is still a whole `state` under its own key, a set is still written to disk the moment it is typed, and every roster call fails soft and retries on the next pass. Train for three hours in a basement and the list reconciles itself when the signal returns, exactly as the log does.
  - **There are exactly two ways two devices can disagree, and both are settled without inventing anything.** A NAME carries the moment it was typed (`nameAt` locally, `name_updated_at` on the server) and the later one wins, not the last device to reconnect, which would let a phone coming back from a week in flight mode silently undo yesterday's rename on the laptop. A rename refused as stale comes back **200 with the name that won**, not an error, so the client takes that as the answer instead of retrying forever. The ORDER is whatever the server says and dragging pushes it (`reorderProfiles` → `rosterPushOrder`, one call for the whole list because a drag renumbers every row after the one that moved); positions the server never set sort **last**, so a list that predates all of this does not shuffle itself. **A shared profile's place in YOUR list lives on your own grant** (`grants.position`, migration `0009`), never on the profile: `profiles.position` is the owner's order, and the order route used to write it for anybody who could write to the profile, so somebody you shared with dragging two of THEIR OWN profiles moved yours down your list.
  - **Adoption is automatic and so is enrolment.** A profile in the account that this device does not hold becomes a local profile (a read grant arrives live, as joining one does); a profile in this account's list with no link yet (made here, often with no signal) goes up the next time there is a connection (the poll, coming back to the app, and the `online` event). Nothing outside the signed-in account's list is ever looked at, so there is no first-run-blank exception and no "signing in adds this phone's profiles" any more. When anything goes up the whole order is pushed (`rosterPushOrder`), because a new position can tie with an old one and the server and the phone break ties differently. **A create carries the local profile id as `clientKey`** (`profiles.client_key`, migration `0009`), so one whose reply was lost on gym wifi is handed back on the retry rather than made twice, and step 1 of the roster pass does not adopt a listing whose `clientKey` is an unlinked profile of this device's own, or the same lost reply would still end up as two.
  - **Removal takes a profile out of the list and leaves the save on the disk** (`dropLocalProfile`). **On the server a deleted profile stays 30 days and then goes for good** (`purgeProfiles` in `index.js`, run by the daily cron, `PROFILE_PURGE_MS`): its rows, codes and grants with it. They used to stay until the whole account was deleted, and most of the database was training somebody had deleted. Every route already treats a deleted profile as one that was never there, so no phone can tell the difference; the delete confirm (`profiles.confirmDelete`) says it in words. A profile deleted on one device leaves the account and therefore every device's list (that is what "the same everywhere" means), but its key stays, so Storage check still has it. An **empty** one is removed key and all, because a trail of blank keys is how that screen stops being worth reading. A removal only ever acts on a profile a listing has confirmed present before (`rec.seen`), so a listing that predates a join cannot delete what it has not heard of yet. **The list CAN end up empty** (it used to keep the last profile even after the account had lost it, which is precisely a profile in the list that is not in the account), and an empty account gets the no-profiles screen. Deleting your last profile by hand is allowed for the same reason.
  - **REMOVING A PROFILE IS A PROMISE, NOT A REQUEST** (`queueRemoval` / `runPendingRemovals` / `zenofit:pending`, and `DELETE /v1/profiles/:id/grants/me`). A removal is queued, survives being closed, is drained at the top of every roster pass, and only leaves the queue when the server agrees, or answers 404, which is the same thing said differently. **Each entry carries the account that made it (`acct`) and is only ever sent as that account** (`pendingMine`): a delete made offline, followed by logging in as somebody else, used to go out with the second account's token, get the 404 that "not yours" earns, and be dropped as done. Adoption skips anything queued, or the next pass would helpfully undo the delete.
  - **Two verbs, because "not in my account any more" is two different facts.** Yours is DELETED and tombstoned for everybody; somebody else's is LEFT, which revokes your own grant and touches their profile not at all. Sending the wrong one is what made this local-only: `deleteProfile` went out for anything not marked "read", so a WRITE grant got a delete the server rightly refused as not-yours into a `.catch` that said nothing, and a READ grant got no request at all. Either way the grant survived, the profile stayed in the listing, and the laptop kept its copy of something deleted on the phone hours earlier. `owned` is refreshed from the listing's `isOwner` on every pass and is the only thing that decides which verb goes.
  - **A profile you only READ wears its owner's name.** Renaming one locally was allowed and went nowhere (the server will not take a name for somebody else's profile), so one profile read "Em" on the phone, "Profile 1" on the laptop and "Profile 1" in both account sheets. Three names for one thing, on a screen whose whole claim is that the list is the same everywhere. A read grant now follows the owner's name, and `profile-form-save` refuses the rename rather than accepting one it knows it cannot keep.
- **A save that will not OPEN must never become a save that gets replaced** (`unreadable` / `allowOverwrite` beside `readProfileState`, checked in `writeNow`). This was the one way the app could destroy a training history entirely by itself, with no bug anywhere else: a stored state that would not parse (a write cut off by a dying battery, a browser truncating under quota) came back from `readProfileState` as `defaultState()`, the app came up blank and perfectly happy, and the very next autosave wrote that blank over the only copy. One bad read, permanent loss, no warning. Now a key that is THERE and will not parse poisons the WRITE instead: `unreadable` holds that profile's id, `writeNow` returns without touching its key (saying so once, the way the quota warning does), and the bytes stay exactly where they are for Storage check to hand back out: it lists one as DAMAGED and exports it raw. **A MISSING key is not this**: a first run and a new profile have no key and must not be flagged, or nothing could ever be saved. The app still runs rather than refusing to open, because a locked-out user cannot reach the screen that rescues them. The lock is deliberate, not absolute: `importBackup` and `reset-all` call `allowOverwrite()` because both are the user saying "replace what is there" out loud, behind a confirm. What is forbidden is the app deciding that quietly on their behalf, so anything added later that can write a whole profile belongs on that short list, and nothing else does.
- **An app whose only copy is one origin's localStorage owes its user a way to look at that** (`storageScan` / `adoptStorage` / `renderStorage`, Settings → Data → Storage check). When the app comes up empty, three very different things look identical from the inside: the data is gone, the data is fine but this is not the address it was saved at, or the data is fine and right here while no list names it. So the screen reads **every** Zenofit save, says how much training each holds and whose account it belongs to (`zenofit:owners`, written the moment a profile joins a list, plus every account's roster key), and prints the origin first. **It is a back pocket, isolated from the rest of the app**: nothing outside the screen reads what it finds (the account sheet used to list every save on the phone, and that is how one account's training kept surfacing in another's list), and nothing it finds goes anywhere unless somebody presses Recover there. **It is locked per account** (`storLocked` / `storAskPassword` / `renderStorUnlock`): Recover, Export and Share on a save belonging to another account ask for that account's password, checked by `POST /v1/auth/verify` (login's check without minting a token), and remembered only for that visit to the screen. Saves of the account you are in, and saves no account ever owned, open without asking. **The lock is a door, not a safe**: the bytes are plain JSON and developer tools can read them; the comment above `STATE_PREFIX` says so and describes the stronger version (encrypt on logout with a key derived from the password) and its catch. **Recover only ever ADDS, and always into the account logged in now**: a save no list names is put in this account's list; one still in another account's list, or the legacy key, is COPIED to a key of its own; recovering another account's save warns in as many words that it belongs to them. What lands has no link, so the roster puts it into the account as a new profile. **Every row also carries Export, and Share where the platform takes files** (damaged saves included), and `storageFileFor` reads and nothing else, because a full store is exactly when Recover cannot finish and the file matters most.
- **A profile is somebody's training, and its person's name travels with it** (`settings.name`, *Your name* in Settings, synced like any setting). Opening Lika's profile greets Lika, on the coach's phone and on hers. A new profile asks **whose training it is** first (`profiles.who` on the add sheet and on the no-profiles screen; `addProfile` takes it as `who`), and its label follows that name unless one is typed. **The Profiles window names the person first** (`profileStats` reads each profile's `who`) and the label under it, so you switch to somebody, not to a file.
- **Switching is one tap, everywhere** (`profile-switch`, `pin-switch`). There is no "are you sure": switching loses nothing, and a coach logging their own sets and somebody else's switches every few minutes.
- **Pinned profiles are badges across the top** (the PINNED PROFILES block: `pinStrip`, `badgeLook`, `badgeHTML`, `badgeSection`). A profile pinned in Settings → Profiles (`profile-pin`) is a badge in the logo's place on Home and every tab, and in the workout window's header; one tap on another badge switches, one tap on the badge on screen opens that profile's sheet. **Each badge is the person's choice** (`badge-color`, `badge-icon`, `badge-shape`, `badge-style`, and up to three characters typed in, emoji counted as one by `graphemes`), because two profiles that both start with L are two Ls; the default is the person's initials (`badgeInitials`, from `who`, which `pinWhoSync` keeps current) on a colour of the group palette picked from the profile's id in the account (`badgeColorOf`) and stored when it is pinned. Text on a filled badge is black or white, whichever reads (`badgeInk`), and an outlined badge's text goes through `inkFor`. **Pins are the ACCOUNT'S, like its profile list** (`users.pins` and `pins_at`, migration `0014_pins.sql`; `POST /v1/me/pins`, and the listing of `GET /v1/profiles` carries them): log in to an account on any phone and its badges are there, and another account on the same phone has its own. They are keyed by the server's profile id (`pinKeyOf`), because every phone has its own local ids; a profile made with no signal keeps its pin under `local:<id>` until it is in the account (`pinsMigrate`), then it travels too. Each roster pass brings them (`pinsFromServer`), an edit goes up whole a moment later (`pinsPush`), and the later edit wins, as a name's does: an older one comes back `stale` with what is kept, and the server holds a stamp to its own clock so a phone set in the future cannot outrank everything after it. Stored here per account (`zenofit:pins:<userId>`) so they draw with no signal, and gone with the account. `pinWhoSync` never writes an empty name over a known one: a profile whose rows have not arrived on a phone yet reads as nameless, and that used to wipe the initials the other phones had given its badge.
- **Switching from inside a workout carries the workout over** (`switchProfile`'s `carry`): the day you were logging is parked as always, and the profile you switch to opens ITS day for the same date through `sheetForDay`, picked up where it was parked or a fresh one. Two people training together log a set each, back and forth, and neither day goes anywhere. Not from an edit of a logged day or a plan (they keep their own rules), and not into a profile you only read.
- **Switching is a bigger event than it looks.** `ui` is full of things belonging to the profile being left (an open workout, a half-typed set, a chart selection), so `closeEverything()` clears the screen back to Home rather than leaving it pointing at rows that no longer exist, and an open day is **parked first** (`closeWorksheet`, the same back-out its own arrow does) so it is waiting in the Log tab rather than living on invisibly inside the crash snapshot (and, switched to from a workout, comes straight back, above). Every profile operation flushes with `writeNow()` before it touches anything, because `state` is only written on a debounce. With no profile open (`profiles.active === null`: logged out, or an empty account) `writeNow` writes nothing, since the `state` the gate sits on belongs to nobody.
- **A live profile is not on this phone at all** (`syncLive` / `liveEnter` / `liveAdopt`, with the `writeNow` guard). This is the one deliberate exception to local-first, and it exists for a real person: a phone too full to save anything and a training log she still wants to look at. `state` is filled from the server into memory on switching in, `writeNow` refuses to write its key, and closing the app forgets it entirely: there is no clever eviction, just a profile the save path declines to save. **Only ever a READ grant**, never a profile you own: the trade is that no signal means no profile, and losing your own log to a dead connection is not a trade anybody would take, while somebody else's log is still whole on the phone that owns it. Read-only is what makes it safe: with nothing of yours in there, a failed fetch can lose nothing. It starts from a **blank state and no cursor**, so what you end up looking at is exactly what the server holds, tombstones and all, rather than a merge with leftovers; and a failed fetch **puts back whatever was on screen** rather than leaving somebody staring at an empty log and drawing the obvious wrong conclusion, with the strip at the top saying so and offering Retry. `liveAdopt` moves an existing read-only copy over on first launch **without deleting its key**: `liveEnter` drops that only once a fetch has proved the server hands the same thing back, so a phone with no signal on the day this ships still opens the copy it already had. It is also reached mid-session now: a pull that reports the grant has dropped to read hands `syncDemoted` the profile, which adopts it and re-enters it, and a pull that reports the opposite clears `live` so the save path starts keeping it again.
