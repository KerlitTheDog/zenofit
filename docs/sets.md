# Sets and comparisons

Everything that measures a set against something: the set suggestions (`setSuggestion`), the opening set (`openingSetFor`), dropsets and supersets with their chain keys (`chainKeys`), verdicts against a plan and against last time, the entry card, the set editor's references, and set order. Read this whole file before changing anything it describes, and update it in the same commit when that behaviour changes (CLAUDE.md, *Docs*).

- **Set suggestions are built on last time, not your best ever** (`setSuggestion`, and the `SUG_*` constants above it). The card at the top of the entry window, above *Add set*, deliberately, because that window is where you decide what to do while the set editor is where you write down what you already decided, offers two ways past the previous session's best set: one more rep at the same weight, or the smallest real weight step (`weightStep`) at the same reps. Holding the reps on the heavier option is deliberate: dropping reps as weight goes up is normal training but would not raise the estimate, and the card only ever offers something that scores higher (every option is filtered through `metricFor`). **Neither option is recommended over the other**: they render identically, and `bySmallestStep` only ranks them by the one thing the app can compute exactly: which raises the estimate least, tagged `sug.smaller` (and tagged on neither when they tie). That lands on the extra rep in the 8-12 range and on the extra weight down on heavy triples, where one more rep is worth far more than a plate. This replaced an inferred double progression that was broken twice over: mechanically (the rep ceiling was a median of a window including last session, so "you're under your range" required your reps to have just *dropped*, which following the app could never cause, making the answer "add weight" forever) and in principle (**a rep range is an intention, and the log only records what you did**, and crowning an option on a guess about someone's programming is the same mistake as a progress bar filling toward a goal they never set). If you reintroduce double progression, it has to run off a range the user actually set, not one read out of their history. The set editor shows the same two buttons, minus whichever the open set already *is*. **Under that card sits `renderLastTime`, the session it is arguing from, set by set** (`lastOuting`). The card names one set because that is the bar it offers two ways over, but four sets that fell apart and four that held share a best set and were not the same day’s work, and it is the second and third you are stood there trying to match. Read-only (everything else tappable in that window puts a number in the log) and in the unit each set was *logged* in, never converted; it renders under a plan target too, since a plan does not make last time less worth knowing. **Both are tap-to-load, never auto-filled**: the log records what you did, never what the app hoped you would do.
- **A new set opens on the set that stood in its place last time** (`openingSetFor`, read off the same `lastOuting` rows the panel above draws). Set three opens on last week's third SET (by chain coordinate, so never on the drop that happened to be third in the list), converted into the unit this entry is being logged in, and *Drop* says so on the way in (`asDrop`) so it is offered last week's drop rather than last week's set. It used to open on the set above it, which is right exactly once (the first set, where there is nothing above) and wrong from the second onward: somebody working up 60/80/90 was handed 60/60/60 and retyped two thirds of their own session. Past where last time ran out it falls back to the set above, which is that old behaviour and the only honest guess left, and with no history at all it opens blank. This is a starting point in an editor, not a number in the log (nothing is written until the set is saved) so it does not violate the tap-to-load rule above, which is about the app never *committing* a number a finger did not put there. The suggestion card still overrides it, because taking the card is a decision and the default is only a guess.
- **Supersets and dropsets are the same idea at two levels** (`isDrop`/`isSuper`, `linkMarks`, `dropMarks`, `superMarks`). A dropset is one exercise straight into a lighter set of itself; a superset is one exercise straight into a different one. Both are a single boolean on the item that CONTINUES the one above it: `set.drop` and `entry.superWith`. **Nothing stores a group id**, deliberately: an id is a second source of truth about an order the list already knows, and both lists are draggable, so the two would start disagreeing the first time somebody rearranged one. Runs are read upward from the order instead, a mark on the first item means nothing and is ignored, and deleting or reordering silently reshapes the runs into whatever the new order says. `commitWorkout` clears a link left stranded on what became the day's first entry, which is tidying the record rather than fixing a read. **Neither does any arithmetic**: no volume multiplier, no intensity adjustment, no fatigue discount. A drop is a set and counts as one set; a supersetted lift is a lift. est. 1RM, PRs, weekly volume, the graph and the last-time comparison all read exactly what they read before, because the app does not know what a dropset is worth and neither does anybody else. They say what you DID, which is the only claim the log is allowed to make. Drawn as an indented chain off the row above, with the label on the head of a run only, in the set list, the day sheet and **every surface that reads a session back**. That last part was a claim these notes made and the code did not keep: `outingRows` dropped the flag on the way out, so the three sets you logged as a dropset came back a week later in *Last time* and in the exercise window's ledger as three ordinary sets, indistinguishable from three separate efforts. The flag now rides on the row (`drop`, read upward from the order so a set that opens an entry can never continue the last set of the entry before it) and `dropMarks` draws it in all four places. Where the reading is a row (`renderLastTime`) it is the same indent and arrow the editor uses; where it is a *chip* that wraps (the exercise window's ledger, the chart's point detail) the chip takes the chain's arrow in place of its number and the chain's colour, which is the same sentence in the space a chip has. **AND A DROP IS ONLY EVER MEASURED AGAINST A DROP** (`chainKeys` / `chainKeyAt`, read by `outingRows`, `lastTimeSets`, `entryLastResult`, `openingSetFor` and `lastSetMetric`). Everything that holds today against last time used to match by ROW NUMBER, which is right until one of the two rows is a dropset and is then wrong in the direction that flatters you: 8 x 80, 9 x 70, drop to 6 x 60 last week, and a third real set of 6 x 60 today reads as a MATCH: a full set graded against a burnout set taken with no rest. A set is addressed by where it sits in the order of EFFORTS instead: `chain` counts the real sets (a drop does not open one), `pos` counts how deep into a chain it is, and `chain.pos` is what the two sessions are matched on. A normal set is always `pos 0` and can only meet another normal set; the first drop off your second set is `1.1` and can only meet last week's first drop off its second set. No counterpart means UNJUDGED, which is the answer the app already gave a fourth set on a day that had three, and `extra` counts those as bonus sets. The key is computed from the order every time, never stored, so rearranging the list reshapes it (the same rule the marks live under), and `chainKeyAt` works out the key a set WOULD have so the two Add buttons can ask before the set exists.
- **A warm-up is logged, never measured** (`isWarm` / `workSets` / `setNumbers` / `warmMark`, actions `set-kinds`, `add-warm` and `add-drop`). `set.warm` marks a set done to get ready for the work (the empty bar, 60 on the way to 100), because people were writing them into the lift's note instead. It is a record of what you did, so it stays on the entry, syncs, exports and is drawn wherever a session is read back; but nothing measures it. **`syncEntry` counts and ranks `workSets` only**, so weekly volume, the PR badge, the est. 1RM, the graph, the dashboard, the strength standards, the chat record card and the picture studio never see one; **`chainKeys` gives it null and does not move the chain**, so it is never graded against last time and never the bar a set is graded against (`lastTimeSets` and `bestEverMetric` skip `warm` rows, the set editor shows it no reference, no suggestion and no est. 1RM card); **a plan's sets answer work sets by their place among them** (`entryPlanResult`, `targetMoment`, the ghost rows, the editor's still-planned check); and `earlierOutings` skips a day of warm-ups only, which would otherwise stand in front of the real last time with nothing in it. **`filledSets` still includes warm-ups, on purpose**: it is what a save keeps (save-entry-form, `mergeLift`) and what a readback draws, and a helper that dropped them there would delete them on the next save; a progress figure reads `workSets`. The set list, *Last time*, the lift's history and the graph's point detail draw a warm-up with the flame in place of its number (`warmMark`, which also says the word to a screen reader, and the word itself where a row has room), work sets are numbered 1, 2, 3 past them (`setNumbers`), and `entrySummary` names them beside the sets ("3 sets + 2 warm-ups"; a lift that only got as far as its warm-ups says just that). **Where they come from: one *Add set*, and an arrow beside it** (`set-kinds`, `ui.setKinds` keyed by the entry like `ui.setOrder`) that opens the special kinds of set, a warm-up and a drop, in a row under it, so the row never grows a button per kind. It replaced a Warm-up button that sat beside *Add set* until the first work set and then made way for *Drop*, which hid the warm-up from anybody working up to a heavier weight after a set, and then a warm-up switch in the set editor, which the user removed as clutter: a row on every set for a choice made once or twice a lift. So **the editor has no warm-up switch**: a warm-up is chosen on the way in and its title says so (*Add warm-up 2*); a set logged as the wrong kind is removed and added again. A new warm-up goes at the end, where it was done, and opens on last time's warm-up in the same place among the warm-ups (`openingSetFor` with `asWarm`). The drop switch stays in the editor, as it always was. **A warm-up is never a drop**: *Drop set* waits, disabled, until the last set is a work set, the editor offers no drop under a warm-up, and a drop flag that ends up under one after a drag reads as a set of its own (`chainKeys`, `dropMarks`). Warm-up set is not offered while writing a plan, which names the work (the arrow then holds *Drop set* alone). Chat workout cards carry `warm: true` and leave warm-ups out of their set count.
- **Cardio in bouts** (CARDIO IN BOUTS: `renderBouts`, `boutsTotals`, `boutsSettle`, `boutHalf`, actions `bout-add` / `bout-remove`, the `bout.<i>.<field>` branch of `handleBind`). Ten minutes on the bike, a rest and fifteen more used to be one time and one intensity typed as a guess at both. *Add a bout* under the pair makes the pair bout 1 and opens an empty bout 2 (a number still reaches the log from a finger); each bout has its own time and intensity and an ×. **The entry's own `minutes` and `intensity` stay what the rest of the app reads**, as a strength entry's headline numbers do off its sets: the time added up and the intensity weighted by it, so the cardio score (minutes × intensity) is the bouts' scores added up (to within the intensity's one decimal), and suggestions, plans, the week's minutes, the pictures and a phone still on an older build all keep working from those. `bouts` is stored only with two or more; one is the entry exactly as it always was, and removing down to one turns it back into that. A bout with only one of its numbers holds Save rather than being dropped quietly. Return walks the boxes (time, intensity, the next bout's time) as it walks the set editor, and closes the keyboard from the last. A session holds at most `BOUTS_MAX` (40), which is what `cleanEntry` keeps: a 41st would have made the cleaned list stop adding up and lose them all. *Last time* shows last session's bouts under its total (`boutsLine`, off the `bouts` that `outingRows` carries), and the History chips say how many. The suggestion card's own *last time* is said as logged, since a session in bouts is rarely a whole intensity and it used to read "23 min × RPE 7" over a Last time card saying 22.5 × 6.7; its targets stay whole numbers, something to aim at. While a session is in bouts, a suggestion or a cardio plan (both for the whole session) no longer loads into the boxes, where it would land on top of bouts already typed: the suggestion's options are drawn as targets rather than taps, under a caption that says they are for all the bouts together and that the session load card shows how close you are (`sug.hintBouts`), and *Fill from plan* is not offered. *Fill the next bout with what is left* was weighed against how somebody who does cardio every week would use it and dropped: the +1 intensity option has no honest per-bout answer (after twenty minutes at 6, the rest would have to be ridden at a 9 to lift the average), and at bout 2 the question is how far off last time you are, which the load card answers live. Writing a plan offers no bouts at all. **`cleanEntry` keeps bouts only while they still add up to the totals**: an older phone edits the totals and carries the bouts along untouched, and the totals it wrote win.
- **Return on the phone's keyboard walks the set editor's boxes: reps, weight, RPE, then the keyboard closes** (`enterkeyhint` on those inputs, read by the keydown listener). The unit select sits inside the weight's label, so the browser's own Next went reps, unit, weight. Chrome on Android hands the page a Return instead of moving focus itself once a field names its key, and the listener moves to the next number box of the same window and selects it (typing replaces what the set opened on, as the browser's own Next does). It answers only number boxes that carry an `enterkeyhint`, so another window opts in by the attribute.
- **Planned vs done is three verdicts and no cleverness.** `setVerdict` says **beat** (more on one axis, short on neither), **hit** (matched) or **under**, matching planned set *i* to logged set *i* by position, with anything past the end of the plan a bonus set. **A planned set may name only part of itself** (`targetHasData`): a weight alone ("80 kg, reps on the day"), reps at an RPE, or an RPE alone, because that is how people decide a set before doing it, and dropping such a set as blank was silently losing the plan. It is written as what it names and nothing else (`targetLine`, `cardioTargetLine`; a part-set is never folded into "2 × 80 kg", which would read as two reps) and judged only on the axes it named: RPE is shown and carried but never graded (a set that felt harder than planned is not under it), and a plan of RPE alone is met by doing the set. While writing a plan the set editor saves any part of a set (`setReady`); a LOGGED set still needs the whole set. Only a whole planned set gets a ✓ on its ghost row (✓ logs its RPE too); a part-set's row opens the editor with what it names loaded. It deliberately does **not** judge on estimated 1RM: a heavy triple outscores the eight you planned, and calling that "target hit" would be the app deciding what you meant. **That rule is for plans only** (see the next bullet: measured against last time, the same trade reads as the improvement it is). `entryPlanResult`/`dayPlanResult` aggregate it for the set list, the entry card, the history row, the day chip and the result sheet (`renderPlanResult`), which is shown once on saving a planned day and never volunteered again. Under is never scolded anywhere it appears.
- **You can plan your sets from inside the entry window** (`renderTargetForm`, actions `target-open` / `target-add` / `target-remove` / `target-last` / `target-save` / `target-clear`). Most targets are decided at the rack, not on the Calendar days before: you look at last time and settle on "three of ten at 80". *Plan your sets* (under the suggestion card, *Plan this session* on cardio, absent while writing a plan) opens a sheet of one row per set in the lift's own boxes (reps × weight, reps, or the time box for a hold, each with an RPE box; minutes and effort for cardio), any of which may stay empty (see the planned-vs-done bullet), where a new row copies the one above and *Start from last time* loads last session's sets as the plan, a target and never a set. **What it writes is exactly a plan's target**, `f.plan` in the shape `planTargetOf` builds, so everything a planned lift has comes with it: the plan card in the suggestion's slot (with a pencil to change it), the ghost rows with ✓, the planned/beat/under words, the count, the line in your history. It carries no `planFrom`, so `prunePlans` never takes it for a calendar plan and `renderPlanResult` never fires for it; on an entry that came from a calendar plan the same sheet edits that entry's frozen copy, never the plan. Saving it empty, or *Remove the plan*, takes `plan` off and the suggestion card comes back. **There is no setting to turn it off** because there is nothing to turn off: nothing appears until somebody plans something. **The moment a set reaches its plan is said, once, right then** (`targetMoment`, from `save-set`, `plan-tick` and the stopwatch): `appToast` names the set and the number ("Plan hit · set 2 · 10 × 80 kg", green; beaten, gold) and the row lights up (`flashSetRows`, spent on the frame like `flashLogDay`); once every planned set is hit it says that instead. A cardio plan is typed straight into the form, so `cardioTargetMoment` says it from `updateEntryPreview` the first time both numbers reach it, once per opening of the form, and paints the line in without a render (one would take the caret). Under says nothing, as everywhere.
- **The verdict, pointed at last time** (`setProgress` / `lastTimeSets` / `entryLastResult`, drawn in `renderSetList`). Est. 1RM speaks for an *exercise* through its BEST set, which is the right answer to "what could I lift for a single" and the wrong answer to "did today go better than last time": match your top set, add a rep to your second, and the headline estimate does not move even though the session was strictly better. So with no plan to answer to, each set is compared with **the set that stood in its place last session**: by chain coordinate, not by row number, so a drop only ever answers to a drop (see the dropset bullet above). It is graded by `setProgress`, **not** by the plan's `setVerdict`, and that distinction is the whole point: the two-axis rule calls a set under the moment it is short on either axis, so 14 × 60 kg followed a week later by 11 × 65 kg read **under** on the strength of the reps alone, while that set is 88.5 kg of estimated max against 87.4, and the est. 1RM card open on it said "1.1 higher than set 2" in gold at the same moment. Trading reps for plates and coming out ahead is the shape of getting stronger, not a step backwards, and the app was contradicting itself on one screen to say otherwise. `setProgress` asks the per-set score instead, **rounded, so the verdict is checkable against the two numbers actually printed**, and the one-axis kinds are unaffected because for reps and for seconds the score IS the axis. **Against a plan the two-axis rule stays**: a plan is a sentence you wrote down and 11 reps is not the 14 you said, which is a different question with a different right answer. Sets past where last time ran out are simply **unjudged**: no verdict, no penalty, so a session can never score worse for containing more work, which is the trap any average over sets falls into (adding a real back-off set drops a mean by several kg and quietly teaches people not to log it). **A plan does not switch it off**: "did I do what I said" and "did I beat last time" are two questions, so a planned set wears the same last-time word on the right as every other set, and the plan's own verdict sits beside the target it answers in the line underneath ("planned 11 × 80 ✓"). It used to be one or the other, and a planned set never said whether it beat last week. Cardio and first outings return null, and last time's weights are brought into the unit being typed in by **`weightAs`, which rounds to TWO decimals**, so a kg set and the same set logged in lbs cannot disagree by a float hair. That rounding used to be one decimal, and it invented verdicts of its own: 26.25 kg came back as 26.3, so a set that repeated last session exactly was logged as less than the number it was being measured against and read **under**, with the card above it simultaneously reporting a *higher* estimate off the same rounding. Two decimals hold every step a plate tree can make (1.25 kg, 2.5 lb), which is all the precision a weight off the log ever claims; `weightAs` is now the one road every past weight travels to sit beside a present one (`lastTimeSets`, `openingSetFor`, `setSuggestion`), so they cannot round differently from each other again, and the row's own "last time 7 × 26.25" prints at that same precision. **Under is never counted up at you**: the tally above the list names only what was beaten or matched. Nothing here touches the exercise's est. 1RM, the PR badge or the graph.
- **The entry card names two numbers, and no longer offers an opinion** (`entryComputed` → `entryRefCols`, kept live by `updateEntryPreview`). Beside the exercise's est. 1RM sit **LAST TIME** and **BEST EVER**, in that order because that is the order they are useful in: last week's number is the one you can do something about tonight, and putting the all-time ceiling first would make every ordinary session read as a failure. Each wears the set list's own `VERDICT_COLOR` against its own bar (gold once today's figure is past it, green when level, muted until then), so *did I beat it* is answered by the colour and *by how much* by the two numbers, with no sentence in between. This replaced a single word out of BADGE_TEXT ("Beat your best 💪", "Below best, normal, keep going"), which is gone along with those strings: **encouragement is not information.** It never said what the best actually WAS, so the one question it provoked was the one it could not answer, and the only bar it implied was an all-time one that most sessions are nowhere near. A bar that does not exist yet prints an em dash rather than vanishing, so the row keeps its shape the moment history arrives, and no unit is repeated on either: they are the same quantity as the figure beside them, whose label already carries it. **The window is filtered by KIND as well as by name**, which the word never was: that mattered less when the output was a sentence and matters completely now that it is a number, since `metricOf` answers in kilos for a strength session and in reps for a bodyweight one, and pooling them put a rep count in a kilo column. It is otherwise deliberately wider than `earlierOutings` (it includes the entries in the open day sheet, which are not in `state.log` yet), so a lift logged twice in one session is measured against its own earlier card. `BADGE_SHORT` is untouched and still labels the rows in your history, which is a label on a list rather than a verdict delivered mid-set.
- **The est. 1RM in the set editor is measured against the set in the same position, with the all-time best beside it** (`lastSetMetric` / `bestEverMetric` / `vsLastLine` / `bestEverBlock`, kept live by `updateSetPreview`). On its own that figure answers nothing, because nobody carries last week's estimate around in their head, and the whole point of typing your own numbers is that you did not want either option the suggestion card offered. Two references, because they answer two different questions and conflating them was the bug. **The main one is positional**: set two is measured against last session's *set two*, on the same per-set score `setProgress` grades the row behind the sheet with and on the same chain coordinate it matches on (`lastSetMetric` takes the open set so it knows whether it is a drop), so the number and the beat/under badge on the row can never disagree. It used to be measured against last session's **best** set, which made the card say "1.2 lower than last time" on a back-off set that had just beaten the back-off set it was actually repeating: true statement, wrong question. It therefore names the position as well as the number ("set 2 last time 29.1 · 23 Aug"), or the figure reads as the session's, which is exactly what it stopped being. Sets past where last session ran out are **unjudged**, the same rule `entryLastResult` follows, and the card says so in a faint line rather than going blank, because a card that silently drops its comparison reads like a bug. **The side one is all-time**, small and muted: the best this lift has ever been worth, over the same strictly-earlier window the PR badge reads (`earlierOutings`), so the two can never disagree about what "best" was. It is the ceiling and not a target, which is why it is second and quiet, and it goes gold and says *new best* the moment the set in the boxes clears it, which is the same claim the badge will make when the entry is saved. Both are read in the unit being typed in (the positional one through `lastTimeSets`, the all-time one through `weightAs`), because a kg estimate held against an lbs one is not a comparison. Both are computed **once per render** and parked in the module-level `setRefs`: neither can move while the sheet is open (typing does not write to the log, and the unit select does a full render), and each otherwise costs a sort of the whole log per keystroke. It wears the set list's own `VERDICT_COLOR` (beat/hit/under), stays put under a plan because it states a fact about a number rather than proposing one, and is text and colour only, because it is rewritten in place while you type.
- **Set order is data, which is why the set list is draggable** (`reorderSets`, `data-dragrow="set"`). Everywhere else an order is presentation; here `entryLastResult` reads it, so a session worked up and logged bottom-first comes back as a row of "under" verdicts describing nothing but the order it was typed in. Dragging it into the order the sets actually happened is what makes those verdicts mean anything. Reordering is a **mode** for the same reason it is one everywhere else (a set row is what you tap to correct a number), and `ui.setOrder` holds the ENTRY'S ID rather than a boolean, so opening a different lift stops matching instead of leaving a mode for twenty call sites to remember to clear. Nothing derived moves with it: `bestSet()` takes the highest estimate wherever it sits.
