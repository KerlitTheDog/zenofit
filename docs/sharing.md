# Sharing a profile

Join codes, read grants and what they lock (`READ_OK`, `DRAG_READ_OK`), levels, removal, and the trainer's glance. Read this whole file before changing anything it describes, and update it in the same commit when that behaviour changes (CLAUDE.md, *Docs*).

- **A join code types itself** (the `joinCode` branch of `handleBind`). Ten characters from a 32-letter alphabet, printed `XXXX-XXXX-XX`, and usually copied off another phone a character at a time while somebody reads it out. So the field upper-cases, inserts the dashes after the fourth and eighth, and refuses an eleventh. None of it is *required*: `normalizeSeed` on the server already forgives lower case, missing dashes and the excluded letters. It is there so the thing being typed looks like the thing being read. **The caret is placed by hand**, because rewriting `value` sends it to the end, which on a phone means the cursor jumping past a dash the field just inserted and the next backspace eating the wrong character.
- **A read grant is a constraint, not a label** (`syncReadOnly` / `READ_OK` / `toastReadOnly`, checked in the one click dispatcher). Enforcement is an **allowlist** rather than a list of things to block, so it fails the safe way: an action added next year is refused until somebody decides it is safe, instead of quietly becoming a hole. On the list is navigation and looking (tabs, sheets, filters, the chart, the calculator, the accordion, Storage check, export), plus the sync sheet itself, because *Leave* has to stay reachable from inside a profile you cannot write to, and the timers, which belong to the phone rather than to the training. A strip at the top of every tab says whose profile it is, on Home too, where there is no header to hang it under. The server refuses the write as well; this side is the courtesy that stops somebody logging a session into a profile that will throw it away on the next pull. **Joining always makes a NEW local profile, and a BLANK one** (`join-go` / the roster's adoption → `addProfile(name, {forRemote: true})`), never a merge into one that already has your training in it: that is the one outcome here nobody could undo. `forRemote` empties the seeded `library` and `groups`, and it is not tidiness: the seeds used to survive the pull as unmatched, unmarked rows and then get pushed up as the joining device's own, so five built-ins the owner had deleted years ago **reappeared in the owner's library** with nobody having asked for them. A profile that is a copy of another one starts from nothing or it is not a copy, it is a merge; live profiles have always done exactly this (`liveEnter`), and this is the same rule applied to the copies kept on disk. The timers stay seeded, because they never sync and belong to the phone.

    Your own code typed on the phone that made it is refused outright (`alreadyMine` → `sync.joinOwn`) rather than becoming a second, read-only, live copy of a profile already in the list.
  - **THE LEVEL IS DECIDED BY THE CODE SOMEBODY CAME IN ON, IN BOTH DIRECTIONS** (`/v1/join`). This is the bug that made read-only look like a lie. `ON CONFLICT` used to keep the better of the two levels (a write grant survived a later join on a read code), on the reasoning that only revoking should take access away. But it is the OWNER who mints a code, so handing somebody a read code IS the owner taking write access away, and nobody can promote themselves with a code they were never given. Getting it backwards meant sharing read-only to somebody who had *ever* been given write changed nothing at all: her app said "read only" because that is what the code said, the server kept taking her pushes because the grant still said write, and her sets landed in his log. `PUT /v1/profiles/:id/grants/:userId` is the direct version of the same decision, owner only, wired to *Move to read only* / *Let them edit* in the people list, because "I'd rather she just looked at it now" should not cost her the profile and a new code.
  - **Making a code RETIRES the old ones** (`sync-make-code` → `rotateSeeds`, which retires them rather than minting a code beside them). The line under those two buttons always said so and the code never did: every profile is minted with a write seed it never shows anybody (`POST /v1/profiles`), a read code made afterwards left that one live, and nothing in the app had ever revoked a seed. So a profile "shared read-only" still had a working write code hanging off it. Nobody already in is touched: a grant is a person, a seed is only the doorway, which is the difference between this and *Remove*.
  - **REMOVED MEANS REMOVED, AND LEAVING IS NOT REMOVAL** (`grants.removed_at`, migration `0009`, checked in `/v1/join`). *Remove* says "They lose access straight away" and used to revoke the grant only, so the person typed the same code again and was straight back in, writing. The owner removing somebody now shuts every code that existed at that moment to THAT person; a code made afterwards is the owner inviting them back and works as any code does. Leaving on your own sets no `removed_at`, so changing your mind on the same code is still free. The people list names people by **username** (`username`, and `displayName` falling back to it): `display_name` is NULL for every account made with a username, and the list read "Someone" for all of them.
  - **A change of level is learned on the next pull, and acted on** (`syncPull`'s `demoted` / `syncDemoted`, and the `live` half of the same patch). Dropping to read turns the local copy into a live profile there and then: the screen locks on the next frame, the copy leaves the phone, and it is re-fetched from the server. Rising above read does the reverse and **clears `live`**, or the profile would be one `writeNow` refuses to save, and a week of her sessions would exist only on the server.
  - **A DRAG IS NOT A CLICK, AND THE ALLOWLIST ONLY GUARDS CLICKS** (`DRAG_READ_OK`, checked in the `pointerdown` handler). Reordering arrives as `pointerdown`, so on a profile whose every button said no, dragging the library, the groups or the presets into a different order went straight through and the next pull silently put it back. Only `profile` and `pinnedTimer` are allowed, which is the same line `READ_OK` draws: the profile index and the timers belong to the phone. (`dismiss-new` was on `READ_OK` and is not any more: it writes the library row, which is training.) It is refused *before* the gesture starts, because a row that picks up, follows your finger and springs back reads as a bug rather than as a rule.
- **A TRAINER'S GLANCE** (`GET /v1/profiles/activity`, `sharedActivityLoad` / `sharedActivityLine` in the Profiles window). For each profile shared WITH you: when it was last trained and on how many of the last seven days (the client sends its own date for "seven days ago"). A read grant is a live profile and is never on the phone, so only the server can say; it reports dates only, counts a lined-up blank row as nothing (the `sets`/`minutes` filter mirrors `entryHasData`), and answers only for profiles the caller already has a live grant to read. The row's own "0 days · 0 entries" is hidden for a live profile, since nothing of it is on the phone to count. The route is pinned by the trainer's-glance section of `smoke_sync.py` (dates and day counts, a lined-up blank and a deleted row not counted, outsiders and the owner seeing nothing, leaving the share removing it).
