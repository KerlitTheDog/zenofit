# Sync

How a profile is copied to the server and back, on both sides: `SYNC_COLLECTIONS`, change detection, pull and push, ordering, cleaning what comes in, the wipe guard, errors, and the automatic schedule. Photos travel separately: docs/photos.md. Read this whole file before changing anything it describes, and update it in the same commit when that behaviour changes (CLAUDE.md, *Docs*).

- **Sync is a copy, never the store** (the SYNC block above `backupText`: `SYNC_COLLECTIONS` / `syncLocalItems` / `syncApply` / `syncPull` / `syncPush` / `syncNow`, with the sheets in `renderSyncSheet` / `renderJoinSheet`). Everything local-first stays exactly as it was: nothing waits on a network to be counted and the app works the same in a basement. It is **always on, for every profile in the account, and there is no switch and no word for it in the interface**: it used to be off until turned on per profile, which is exactly what made "the same profiles on every device" impossible to promise. The only per-profile decision left is SHARING it with another account (`renderSyncSheet`, titled *Sharing*: codes, the people list, and for a shared profile, leaving it). What is done offline is kept on the phone and goes up when there is a connection, the way an online document editor behaves. Locally a profile is a whole `state` under its own key; on the server it is a row plus items of `{collection, itemId, json}`, and the bridge is a `remoteId` in **`zenofit:profiles`, outside `state`** for the same reason `zenofit:device` is: `backupText` serialises `state`, a backup is a file people share, and restoring one onto a second phone must not hand it the keys to the original. **What travels is `SYNC_COLLECTIONS` and nothing else**, and the server enforces the same list and refuses an unknown collection *by name* rather than dropping it, so the two disagreeing is loud. Deliberately absent: `drafts` (a photograph of a half-typed set editor) and `timers` (they carry a `cloudId` naming a push alarm booked for ONE device). Of `settings` only the training half goes (`units`, `startDate`, `weekMode`, `sex`, `name`), because theme and language are properties of a phone, not of a person's training. **Change detection is a hash per item** (`marks`, in the sync record), because nothing in this app stamps an edit: a log entry has `createdAt` and has never had an `updatedAt`, and adding one would mean touching every one of the hundreds of places that write. A push is whatever no longer matches its mark, plus a tombstone for any mark that outlived its item; that cannot miss an edit made by code that has never heard of sync, and a second push with nothing changed sends zero. The `clientUpdatedAt` beside it is stamped when the change is **detected**, which is honest for the one thing the server uses it for (refusing to go backwards) and is **not a merge policy**: two people editing the same set between two syncs is not a case this resolves, and dressing it up as one would be worse than saying so. `syncNow` **pulls before it pushes**, since writing over the server before reading it is how an edit made elsewhere disappears unseen. **A pulled row whose hash equals its mark is this device's own echo and is NOT applied** (the filter at the top of `syncPull`'s page loop): the server does not filter a pull by who wrote it and a push does not move the cursor, so the next pull hands back this device's own last push, and applying it overwrote whatever had been done to that row since (a set added to an already-synced lift, a corrected weight), whenever a poll or Refresh landed inside the push debounce (which every keystroke re-arms); a lift deleted in that window came back. A row equal to its mark carries nothing this device has not already reconciled, so the local row, edited or deleted, stands. Deletions always apply, and anything really changed elsewhere has a different hash and lands as before. **`syncApply(items, into)` and `syncPull` can target a profile that is NOT on screen**, which is what makes a freshly signed-in device arrive holding real profiles rather than a list of empty names: an off-screen profile is read off its own key, filled, and written back with `writeProfileState` (same two guards as `writeNow`: a save that will not parse is not written over, a full store is reported); `state` is never touched for one, and a LIVE profile is never pulled this way at all, since the whole point of one is that nothing of it is on this phone. The three lists whose order the user set and can see (`groups`, `presets`, `library`) carry their index as `__i` and are sorted back into it on the way in, because an item store has no order; `__i` is stripped before the row reaches `state`. **A PAGE IS NOT THE WHOLE LIST, and a row it does not mention keeps the place it already has**: falling back to "sorts last" is correct only when the page IS the collection, and it almost never is: renaming one exercise on the other phone pushes exactly one library row, which then sorted itself to the top of the library while everything else fell in behind it, and the shuffled order went back up as if somebody had meant it. A move really made elsewhere still lands whole, because moving one row renumbers every row after it and pushes all of them, so the page carries the part of the list that actually changed.
  - **DATA FROM ANYWHERE ELSE IS DATA, NEVER MARKUP** (`cleanState` / `cleanRow` / `cleanMapValue` above `hydrate`, called by `hydrate()` and by `syncApply` for every pulled row; `groupColor` / `unitOf` / `cleanHref` at the other end). Every name and note in a template goes through `esc()`; the fields the app only ever writes itself (ids, dates, units, colours, kinds, the numbers in a set) did not, and a shared profile's rows come from whoever else can write to it, a backup is a file people hand each other. A group colour of `#fff"><img onerror=…>` pushed by somebody with a write grant ran script on the owner's phone, where the account token sits in localStorage. Those fields are now held to the one shape this app gives them wherever data comes IN, and nothing the app writes itself is ever changed by it (all eleven historical saves hydrate byte-identical with and without it), which is what makes it safe to run on somebody's whole history at every launch. **A new field that a template prints raw belongs in `cleanRow`**, the same standing rule `renameExerciseIn` states for names.
  - **The server stamps rows in the order they land** (`profiles.item_seq`, migration `0009`): each chunk of a push is one D1 batch whose first statement moves the profile's counter to `MAX(counter + 1, now)`, and every row of the chunk takes that value as `updated_at`. It used to be `Date.now()` read before any chunk was written, so two pushes racing, or one push's later chunks against somebody's pull, could commit rows stamped OLDER than a cursor another device had already moved past. The cursor's shape is unchanged. A client's `clientUpdatedAt` is also held to at most ten minutes past the server's clock, on the way in and when read back, or one device with a clock in the next century locks a row against every honest edit for good.
  - **The server's wipe guard counts a run of deletions, not a batch** (`WIPE_WINDOW_MS` in `sync.js`, the `wipe:<profileId>` key in `rate_limits`): judged one 200-row batch at a time it let 800 of a 1,000-row profile go before tripping, so the biggest profiles were the least protected. Deletions over the last minute are summed and judged against what the profile held when the run began, so the run stops once it has taken half. A person deleting things by hand is spread over the debounce and never sums up to it; `allowWipe` still opens it for a restore or a reset.
  - **One row the server would refuse must not stop the other four hundred** (`SYNC_MAX_ITEM`, `SYNC_MAX_ID`, the `tooBig` list in `syncPush`). With the photos handled in docs/photos.md, two things can still make a row unsendable: its SIZE, which now means a genuinely enormous row rather than a picture, and its ITEMID, which for a goal or a volume target is an exercise or a group NAME and is capped at 200 characters by the server: a longer one failed **every** push, for ever, silently. Either is left behind and **named** instead: everything else syncs, the sheet counts the two cases separately (a photo left behind is a shrug, a row left behind is a job), and neither is marked as sent, so fixing the row sends it next time with no extra bookkeeping.
  - **The server's message is the useful half, and it used to be thrown away** (`syncErrText`). Errors were reported as `e.code` alone, so `bad_item` appeared on screen while the message beside it read "library/default-0 is 700 KB, over the 512 KB limit": the app knew exactly which row was the problem and said none of it. The code is now only substituted where the raw word actively misleads: **`not_found` on a profile you are linked to does not mean it is gone**, it means THIS device cannot see it, which is what happens when a share is withdrawn or the phone is signed in as somebody else; same for `read_only`. Everything else keeps the server's own sentence. **Which is safe because the server's sentences are always its own words, never an exception's**: `/health` says `ok` or `error` and nothing more, anything unhandled is the generic `server_error`, and the detail (a database message can name tables and limits) goes to `wrangler tail` only. A new route keeps to that: `fail()` with a sentence written for the person reading it, never `e.message`. **Everywhere outside the sync sheet the CODE decides the words** (`apiErrText` / `API_ERR_KEY`, and `chatErrText` / `CHAT_ERR_KEY` for chat's own): logging in, registering, Storage check's password, deleting the account, joining, chat and photo refusals say a known code in the person's language, a request that never reached the server in the caller's own offline line, a fault on the server's side as one (never as "no connection"), and only a code nothing in the app knows falls back to the server's sentence. A refused name check after a refused login is no longer reported as a wrong password. A new API code a person can meet gets its key in all three languages in the same commit.
  - **A profile's name on the server is set once and has to be kept up** (`renameProfile` from `profile-form-save`). Renaming locally never reached it, so the account sheet listed profiles under names that existed nowhere on the phone. It is fire and forget (the name is display only, nothing is filed under it), and the account list **prefers the name this phone knows a profile by** wherever it is on this phone at all, so a rename that has not reached the server yet cannot make that list disagree with the Profiles screen two taps away.
- **A COLLECTION ADDED LATER IS SAFE FROM THE BUILD BEFORE IT** (`SYNC_SINCE_V1` / `syncLearn` in `app.js`, `knows` on every push, `LATER_COLLECTIONS` in `api/src/sync.js`). A build that has never heard of a collection still records a mark for every row of it that it pulls, applies none of them, and moves its cursor past them, and its push reads a mark with no row behind it as a deletion. Adding `notes` would therefore have let any phone still on the previous build (the version a phone runs until it reloads after a deploy) delete the notes made on an updated one, on every device. Two halves: **the server ignores a deletion in a later collection from a push that does not name it in `knows`**, answered as skipped, so the old build simply forgets its mark; and **an updated phone drops its marks for the collections its sync record was not kept with and pulls that profile once from the start** (`syncLearn`, run before every pull and push), because those marks would otherwise read as deletions and its cursor would never hand the skipped rows over again. The full pull skips everything it already has (a row equal to its mark is an echo) and lands only what was missed. Proven locally with the committed build and the new one on the same profile, the old phone then updated in place. **A new collection goes into both lists in the same commit.**
- **Sync runs itself** (`syncTouch` / `syncQuiet` / `syncPollStart`, hooked into `persist()` and `visibilitychange`). There is no button for it any more; Refresh in the header is the one way to ask for a pass now. **Pushing is debounced**, not immediate: saving one workout writes state a dozen times in a minute and a push per write would be a dozen requests for one session, so `SYNC_PUSH_AFTER` waits for the typing to stop, and a push that finds nothing changed sends zero rows anyway, so being slightly eager costs one cheap request while being late costs an upload the phone may close before making, hence the `pagehide` flush. **The debounce belongs to the profile that armed it** (`syncFlush`, called by `switchProfile` before `profiles.active` moves): the timer names no profile and pushes whichever one is active when it fires, so leaving one inside the window armed a push for the profile you arrived at and dropped the one you left, whose last few sets then sat on the phone until something happened to touch that profile again, which, for one you switched away from, can be weeks. Anything else that changes which profile is active belongs in front of that same flush. **Pulling is polled** (`SYNC_POLL_EVERY`, only while the app is on screen, plus straight away on coming back, throttled by `SYNC_PULL_GAP`), because nothing pushes us: a rest timer gets a real web push, a set logged on the other phone does not. The one hook is `persist()`, which every mutation already goes through, so automatic sync sees every change without a single call site knowing it exists, and `syncApplying` stops a pull's own `writeNow` from scheduling a push straight back. **Nothing here re-renders unless something landed, and not even then while a field has the caret in it** (`syncTyping`): `render()` rebuilds `#app` wholesale, and a sync that repainted mid-word would throw away the input somebody was typing in, from a timer they cannot see. It is silent by design (an unattended failure that raises an alert is a phone interrupting a set to say the wifi is bad), so errors are recorded for the sync sheet and nothing else.
