# Timers

The countdown timers and the stopwatch, the server-booked second alarm (`cloudTimerStart`), keeping notifications in step with the app, and the synthesised sounds (`SOUND_LIB`). Read this whole file before changing anything it describes, and update it in the same commit when that behaviour changes (CLAUDE.md, *Docs*).

- **Timers** run on their own interval engine (`startTimerEngine`, `sweepTimers`, `fireTimer`) independent of `render()`, with notifications through the one switch (`notifyFirstAsk`, `notifyDone`, see *ONE SWITCH* in docs/notifications.md). `notifyDone` shows through the service worker's `showNotification` (Chrome on Android refuses `new Notification()` from a page outright), and only when nobody is looking: on screen, the chime, the buzz and the banner have already said it. One timer can be on screen several times at once: its card on the Timer tab, and its round dial (`pinnedTimerDial`) both on Home and at the bottom of the workout and entry windows, where `renderTimerList()` repeats the same up-to-3 `pinnedTimers()`, so `paintTimers()` addresses every copy by `[data-tmr-time]` / `[data-tmr-ring]`, never by a single element id. Every dial carries the same pause/reset pair the Timer tab's cards have, wherever it appears; an *idle* dial has nothing to pause, so it stays bare and the row doesn't jump when one of three timers starts. Because those dials sit inside overlays, the timer editor sheet sits at `z-index` 120, above all of them.
- **The stopwatch counts the other way, and is the Timer tab's second half** (the STOPWATCH block: `newStopwatch` / `swElapsed` / `paintStopwatch` / `renderStopwatch`, behind the `ui.timerSeg` segment control in `renderTimers`, with the countdowns moved into `timersBody`). Every timer in the app counts DOWN to something; nothing counted up, which is what you want for how long a circuit took or how long the whole session ran. It is `{startedAt, acc, laps}` and the clock is **arithmetic, never a ticking number** (`acc` is what the last pause banked, `startedAt` is when the current run began), which is the same trick `endsAt` plays for the countdowns, pointed the other way, and is what makes the reading survive a re-render, a backgrounded tab and the app being closed and reopened. **Nothing is written while it runs**: only start, stop, lap and reset write, because the paint can work the number out for itself. It has **its own rAF loop** rather than riding the 250ms timer engine (at four frames a second the hundredths column would flicker through values it never showed), it paints in place like `paintTimers` for the same reason, and the loop ends the moment the digits leave the screen, so one left running in the background costs nothing. `laps` holds the **cumulative** reading at each lap, so a split is the difference with the one before and no lap can disagree with the total above it; fastest and slowest are marked once there are three, because with two the marks say nothing the two numbers do not. It lives in `state` (so it is per profile, exactly as the timers are) and **writes nothing to the log by itself**. It is on `READ_OK` for the same reason the timers are, and it feeds the nav's own running dot beside them: the countdowns and the clock that counts up are the same question asked in opposite directions and belong behind one icon, which is why it is **not** a third mini tab on the workout log, where it was first built and did not belong.
  - **A STOPPED STOPWATCH CAN PUT ITS TIME ON A TIMED LIFT** (`renderSwLog` / `swSplits` / `swLogTimes`, actions `sw-log-open` / `sw-log-mode` / `sw-log-tick` / `sw-log-pick`). It used to say a time worth keeping was one you typed into a set yourself, which meant reading 1:20 off the clock and converting it to 80 for a box that wanted seconds. Now *Log to exercise* (shown only while stopped with at least a second on it) opens a sheet: the time, or with laps a choice of **each lap as its own set** (the default, every split with a tick, so a lapped rest can be left out) or the total as one; a date, today by default; and every hold-kind lift, the most recently logged first. Splits are whole seconds, the precision a hold is stored at, and a split under a second is not offered. **The sets land where the lift already is that day, never as a second row of it**, in this order: the lift in the workout already open on that date, else in the day parked for it, else the lift as SAVED that day (opened the way the Log tab opens a row, `isDraft: false`, and saved straight back to it, which is also what keeps a saved row and a separate parked day from both gaining the lift), else a new entry in that day's workout through `sheetForDay`. It is still a tap that puts each number there, the entry and the day are still saved by the ordinary buttons, the new rows light up (`flashSetRows`), and a set that reaches a planned set says so like any other (docs/sets.md). The stopwatch itself is left exactly as it was. None of the four actions is on `READ_OK`: unlike the clock, they write training.
- **A rest timer is two alarms, and the local one wins wherever it can** (`cloudTimerStart` / `cloudTimerCancel` beside `startTimer`). `startTimerEngine` ticks every 250ms and `fireTimer` does the chime, the buzz and the notification, all of which need a living tab, so locking the phone mid-rest, which is exactly what people do, throttles that tab and then discards it, and the alert the timer existed for never happens. So every start also books the same deadline with the server (`ZenofitCloud.scheduleTimer`), which pushes a notification whether this app is alive or not. Three rules keep the pair from both going off in your ear: **the local one is scheduled to win**: the server's copy is booked `PUSH_GRACE_MS` (2s) late and `fireTimer` cancels it on the way past, so the push only ever speaks when the page was not there to; the gap is already in our favour, since the server starts counting when the request lands and we started when we sent it, but leaning on network latency for correctness is not a plan. **It is a second chance, never a prerequisite**: nothing is awaited, every failure is silent, and every degraded path (no `ZenofitCloud` at all, push blocked, push not enabled, the call throwing, a timer longer than the API's one-day ceiling) leaves the local timer running exactly as before: a rest timer starts the instant it is tapped, in a basement gym with no signal. **The deadline goes as a duration, never a wall-clock moment** (`inMs`, which the client puts on the wire as `durationMs`): a real phone tested here was 2.8 seconds off the server, and `inMs` means the phone's idea of the time never enters the arithmetic. Every transition that stops a countdown hands the server's copy back: pause, reset/stop, `fireTimer`, editing a running timer's length (`timer-save` restarts it, so the old deadline is stale), and `timer-delete` before the row leaves state. The cancel itself is allowed to fail quietly on the way to the Durable Object, so the alarm checks the timer's row before it rings (`TimerAlarm.alarm`): a rest somebody stopped is `cancelled` there and stays silent. The handle is `t.cloudId`, which **persists in state on purpose**: start a rest, let the app die, reopen, tap Stop, and that is the only way the stray push can still be called off. Because it persists, `backupText` strips it next to `drafts`: it names an alarm booked for THIS device, on a server that will only cancel it for the device that booked it, and a backup is a file people share.
  - **A FINISHED REST STANDS IN THE SHADE EXACTLY AS LONG AS IN THE APP** (`timerRef` / `timerTag` / `timerCloseNotifs` / `timerNotifsTidy` beside `notifyDone`; `ref` and `endpoint` on `POST /v1/timers`; the timer branch of the push handler and `closeUnmatchedTimers` in `sw.js`). Pressing Done cleared the app and left the notification in the shade (and, on Android, the dot on the app's icon on the home screen) until it was swiped away by hand, because nothing ever closed one and nothing COULD: the push was tagged `timer-<server id>`, an id the page forgets when the rest runs out, and it rang every device on the account, including ones that never knew the timer existed. So **a rest has one tag wherever it is announced from**, `"pbt-" + timerRef(t)`, the profile and the timer's own id (timers are per profile and every profile is seeded with the same ids): `notifyDone` uses it, and `cloudTimerStart` hands it to the server as `ref`, which tags the push with it and carries it in the notification's `data.ref`. Closing by tag closes both, and a push landing on a rest already in the shade replaces it without ringing twice (`again` in `sw.js`; `notifyDone` likewise shows nothing over one already there). **`timerCloseNotifs` runs on every way of dealing with a rest**: Done/Reset/Stop (`timer-reset`), starting it again (`startTimer`), editing it (`timer-save`), deleting it (`timer-delete`) and closing the banner (`toast-dismiss`). **`timerNotifsTidy` is the net under it**: every timer notification this profile's timers can answer for is closed unless that timer is finished right now (due counts as finished, since a page back from the background can ask before the engine has swept), run at launch, on every visibility change both ways, on focus, and when `sw.js` reports a timer push (`timer-push`, posted only AFTER the notification is shown), because a push can still land after the rest was dealt with when the cancel lost its two-second race. Notifications it cannot match are left alone: another profile's rest, and the Notifications window's test timer. **Only the phone that started a rest rings** (`endpoint`, the device's push subscription, checked in `sendToUser`): a timer never syncs, so another device ringing for it could never acknowledge it, and an endpoint no longer this account's sends nothing rather than falling back to the account's other devices. A build before `ref` existed left notifications with no `ref`, which nothing can match; the v32 worker clears those when it activates (`closeUnmatchedTimers`). Proven locally with real pushes to headless Chrome (the old build left the notification after Done, and rang both of an account's phones); the Android icon dot itself needs a real phone.
  - **A REST IS ANNOUNCED ONCE, BY WHOEVER WAS THERE WHEN IT RAN OUT** (`fireTimer`, `visibleSince` / `heldChime` / `dropHeldChime` beside it, the `visibilitychange` listener under `startTimerEngine`). It rang twice: lock the phone mid-rest, the page is frozen, the server's push rings at the deadline, then you open the app (or tap the notification, which focuses it), the page wakes, finds the rest overdue and `fireTimer` buzzed and chimed again at somebody holding the phone that had just told them. Same on a launch after the OS killed the app. So `fireTimer` asks WHERE THE APP WAS AT THE DEADLINE, not only whether it has passed. **On screen at the deadline** (`visibleSince <= endsAt`): the page is the alarm, as before (buzz, chime, the shade if unfocused, and the push called off). **Come back to it afterwards** (`visibleSince` later than the deadline, or null because the app is visible and its visibility event has not landed yet; `visibleSince` starts at load, which is what covers a launch): SILENT. The banner and the Done state say it, and the push is still called off in case it is about to land on top. **Still hidden and later than `PUSH_GRACE_MS` with a push booked** (`pushHasIt`): the push is ringing or has rung, so the page says nothing AND leaves the push alone, since a cancel arriving a moment before the alarm would leave the rest announced by nobody. Hidden and late with NO push booked (notifications off): the page is the only alarm and goes off as before. A buzz is only ever asked for on screen (a hidden page's vibrate does nothing anyway), and a chime started while hidden is scheduled only on a RUNNING audio context and remembered (`heldChime`): iOS suspends the context in the background and a suspended context plays its queue the moment it resumes, which was the same double from another angle, so `dropHeldChime` stops whatever has not played yet when the app comes back. `playSound` returns `{nodes, end}` for exactly this. Proven locally with real pushes to headless Chrome, old build against new (the page's JS stopped with DevTools' Debugger.pause, which leaves the service worker free; Page.setWebLifecycleState frozen also stalls the worker and the push never shows, so it is useless for this): asleep-then-opened, killed-then-launched and woke-late-while-hidden each rang twice before and once after; on screen, hidden-but-alive and notifications-off still ring exactly once. A real phone is still the only proof of the lock screen itself.
- **Alert sounds are synthesised, never files.** `SOUND_LIB` is a dozen alerts written as note lists (`[start, freq, length, waveform, gain, glideTo?]`) that `playSound(id, volume)` schedules on the Web Audio context, with no mp3s to download, cache, miss offline or license. **Sound and volume are per timer** (`t.sound`, `t.volume`, defaults `DEFAULT_SOUND`/`DEFAULT_VOLUME`, which live in the storage section because `seedTimers()` runs before the audio code is reached), edited in `renderSoundPicker()` inside the timer sheet, and read through `soundOf()`/`volumeOf()` so a malformed or missing value can never silence a timer. Volume 0 is a real choice and schedules nothing.
